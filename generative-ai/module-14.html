Real-World Case Study: Customer Support Routing

A mid-size SaaS company handles 2 million support queries per month averaging 400 input tokens and 200 output tokens each.

  • Before routing: 100% to GPT-4o → ~$3,600/month in API costs
  • After routing: 70% simple queries to Claude Haiku 3.5, 20% medium to GPT-4o-mini, 10% complex to GPT-4o
  • New cost: $420 + $360 + $360 = ~$1,140/month — a 68% reduction with no measurable CSAT degradation

Routing is not an optimisation: at scale it is table stakes for AI product economics.

Beyond cost, routing gives you:

  • Reliability: if one provider is down, traffic automatically shifts to another
  • Compliance: PII-sensitive queries can be routed to on-premises models that never leave your VPC
  • Speed: short, simple queries finish in <500 ms on small models vs. 3-5 s on large ones
  • Experimentation: a routing layer is a natural A/B testing point for new models

2. API Gateway Patterns for LLMs

Single-Provider vs. Multi-Provider Architecture ▼

Single-Provider Gateway

A thin proxy in front of one provider (e.g., OpenAI). Its primary jobs are auth normalization, logging, and rate-limit enforcement for internal teams.

  • Simple — one set of API semantics to implement
  • Risk: vendor lock-in, no cost optimisation across providers
  • Appropriate when: very early stage, single model use-case, strict data locality with one provider

Multi-Provider Gateway

A unified API surface that speaks to OpenAI, Anthropic, Cohere, Mistral, Bedrock, VertexAI, and self-hosted models. Internally normalises request/response formats, tracks per-provider quotas, and applies routing logic.

  • The foundation for cost optimisation and high availability
  • More complex — you maintain model capability matrices and schema translators
  • The de-facto standard for any serious production AI system (>$500/month spend)

Gateway Responsibilities

A well-designed LLM gateway handles concerns that should never be scattered across individual service call sites:

Authentication & Authorization

Internal JWT / API key → gateway translates to provider-specific API keys. Services never hold provider credentials directly.

Rate Limiting

Per-tenant, per-feature token-bucket limits. Prevents one noisy service from exhausting your provider quota and incurring throttling errors.

Retry & Timeout

Exponential back-off with jitter on transient 429/500 errors. Streaming vs. non-streaming timeout policies differ significantly.

Fallback Orchestration

Declarative fallback chains: if primary errors, promote secondary within the same request lifecycle.

Observability

Token counts, latency percentiles, cost attribution, error rates, and model-specific quality scores — all emitted as structured events.

Caching

Semantic caching for repeated or near-identical prompts. Exact-match prompt caching (OpenAI/Anthropic native) + semantic similarity (embedding-based) layers.

OpenAI-Compatible API Standard

The /v1/chat/completions format has become the de-facto lingua franca for LLM APIs. Anthropic, Mistral, Together.ai, Ollama, and LiteLLM all expose an OpenAI-compatible endpoint. A well-designed gateway translates everything to and from this standard internally, letting your application code remain provider-agnostic.

Key fields that vary across providers and require normalisation:

  • System prompt: OpenAI uses {"role":"system"}; Anthropic has a top-level system field
  • Tool/function calling: Schema differences between OpenAI tools format and Anthropic tool_use blocks
  • Streaming chunks: SSE formats differ (delta structure, finish_reason placement)
  • Token counting: Different tokenizers; always normalise to cost-equivalent units for billing
  • Context window limits: Must be part of routing metadata (GPT-4o: 128K, Claude 3.5 Sonnet: 200K, Gemini 1.5 Pro: 1M)

3. Routing Strategies

Complexity-Based Routing ▼

The most impactful strategy: classify query difficulty before routing. Simple factual look-ups, greetings, and template-fill tasks do not need GPT-4 — a 7B parameter model handles them with equivalent quality at a fraction of the cost.

Complexity Signals

  • Token count: <200 tokens → likely simple; >2000 tokens → complex context required
  • Question type: yes/no, single-hop factual, multi-hop reasoning, code generation with tests, creative writing
  • Domain: general knowledge vs. specialised technical vs. legal/medical
  • Explicit markers: "step by step", "explain why", "write unit tests" → complexity signal
  • Conversation depth: turn N in a long conversation usually requires a model with larger context

Classifier Implementation

You have two options for building the classifier itself:

  1. Lightweight ML model: Train a small BERT/DistilBERT binary or multi-class classifier on labelled query pairs. Adds ~5 ms latency, extremely cheap per-token.
  2. Heuristic rules + small LLM: Rule-based pre-filter (token count, keyword detection) followed by a fast cheap model (e.g., GPT-4o-mini) for borderline cases. No training data needed.
"""
Complexity-based routing classifier.
Returns one of: 'simple', 'medium', 'complex'
"""
import re
from dataclasses import dataclass
from typing import Literal

ComplexityLevel = Literal["simple", "medium", "complex"]

COMPLEX_KEYWORDS = {
    "step by step", "explain why", "compare and contrast",
    "write unit tests", "debug", "refactor", "analyse", "analyze",
    "pros and cons", "tradeoffs", "trade-offs",
}

SIMPLE_PATTERNS = [
    r"^(hi|hello|hey|thanks|thank you|ok|okay|yes|no|sure)\b",
    r"^what is \w+\??$",
    r"^(translate|convert) .{1,80}$",
]

@dataclass
class ClassifierResult:
    level: ComplexityLevel
    confidence: float
    reason: str

class ComplexityClassifier:
    def __init__(self, medium_threshold: int = 300, complex_threshold: int = 800):
        self.medium_threshold = medium_threshold
        self.complex_threshold = complex_threshold

    def classify(self, prompt: str, conversation_turns: int = 0) -> ClassifierResult:
        token_estimate = len(prompt.split())  # rough whitespace tokenisation

        # 1. Simple pattern shortcuts
        lowered = prompt.lower().strip()
        for pattern in SIMPLE_PATTERNS:
            if re.match(pattern, lowered):
                return ClassifierResult("simple", 0.95, "matched simple pattern")

        # 2. Long conversations require larger context window
        if conversation_turns > 10:
            return ClassifierResult("complex", 0.85, "long conversation history")

        # 3. Complex keyword presence
        for kw in COMPLEX_KEYWORDS:
            if kw in lowered:
                return ClassifierResult("complex", 0.80, f"keyword: {kw!r}")

        # 4. Token-length heuristic
        if token_estimate < self.medium_threshold:
            return ClassifierResult("simple", 0.75, f"short prompt ({token_estimate} tokens)")
        elif token_estimate < self.complex_threshold:
            return ClassifierResult("medium", 0.70, f"medium prompt ({token_estimate} tokens)")
        else:
            return ClassifierResult("complex", 0.75, f"long prompt ({token_estimate} tokens)")

    def model_for(self, result: ClassifierResult) -> str:
        return {
            "simple":  "claude-haiku-3-5",
            "medium":  "gpt-4o-mini",
            "complex": "gpt-4o",
        }[result.level]
Cost-Based, Latency-Based & Quality-Based Routing ▼

Cost-Based Routing

Each incoming request carries a budget ceiling (set by the feature team or derived from the tenant's pricing tier). The router selects the most capable model whose projected cost (input_tokens * price_in + output_tokens * price_out) fits within that budget.

  • Requires token estimation before the call — use tiktoken or cl100k heuristics
  • Freemium users → Haiku / Llama-3.1-8B; enterprise users → GPT-4o
  • Add a daily/monthly spend accumulator per tenant; cut over to cheaper models when budget threshold is reached

Latency-Based Routing (SLA-Driven)

Some product surfaces have hard latency requirements. A real-time autocomplete must respond in <200 ms; a background report generation can take 30 s.

  • Tag each feature/endpoint with a latency SLA
  • Router maintains an exponential-moving-average of p50/p95 latency per model per region
  • If the fastest eligible model is currently running above its p95 SLA (based on recent metrics), fall back to a geographically closer endpoint or a smaller model
  • Streaming is the default for any SLA < 2 s — first token latency (TTFT) is what users perceive

Quality-Based Routing (Task-Specific Strengths)

Different models have different strengths. Route to the model that is empirically best for the task type, not just the most expensive one.

Hybrid Routing: Combining Multiple Signals

Production systems combine all four dimensions into a scoring function:

def score_model(model: ModelSpec, request: RoutingRequest) -> float:
    """
    Returns a score (higher = better fit). Router picks the highest-scoring
    model that also passes hard constraints.
    """
    # Hard constraints (reject entirely if violated)
    if request.max_context_tokens > model.context_window:
        return -1.0  # disqualified
    if request.required_modality not in model.capabilities:
        return -1.0

    # Soft scores (0..1 range, weighted)
    cost_score    = 1.0 - (model.cost_per_1k / MAX_COST_PER_1K)
    latency_score = 1.0 - (model.p95_latency_ms / SLA_TARGET_MS)
    quality_score = model.quality_matrix.get(request.task_type, 0.5)

    # Weights are tunable; can be per-tenant or per-feature
    return (
        0.4 * cost_score +
        0.3 * latency_score +
        0.3 * quality_score
    )

4. Fallback Chains & Reliability

Primary → Fallback → Emergency Chains ▼

LLM providers have >99.9% uptime targets but real-world availability is lower. Outages lasting 5-60 minutes are not rare. A fallback chain is declarative configuration specifying what to do when a provider fails.

Example: Customer-Facing Chat Feature

1. Claude Sonnet 3.5

→
2. GPT-4o-mini
fallback on 429/5xx
→
3. Llama-3.1-8B (self-hosted)

Trigger conditions for chain promotion:

  • HTTP 429 (rate limit exhausted) or 529 (overloaded)
  • HTTP 500/503 after retry budget exhausted
  • Timeout exceeded (streaming: 30 s for first token; non-streaming: 60 s total)
  • Circuit breaker in OPEN state

Timeout Handling: Streaming vs. Non-Streaming

Streaming calls require two separate timeout thresholds:

  • Time-to-first-token (TTFT): If no chunk arrives within X ms, abort and fall back. Typical: 5-15 s for large models, 1-3 s for small ones.
  • Inter-chunk timeout: If streaming stalls mid-response (no chunk for Y ms), you cannot simply retry — the partial response must be discarded or the stream must be resumed if the provider supports it. Typical: 10-30 s.

Non-streaming: a single wall-clock deadline for the complete response. Simpler to implement but gives users a blank wait screen — prefer streaming for any user-facing surface.

Rate Limit Detection & Provider Switching

Rate limits manifest in several forms:

  • RPM (requests per minute): Classic 429 with Retry-After header
  • TPM (tokens per minute): 429 but your retry-after period may be very short (1-10 s)
  • Concurrent requests: Some providers limit parallel connections per key
  • Soft capacity limits: 529 on Anthropic — provider is overloaded, not your quota

The gateway should parse x-ratelimit-remaining-requests, x-ratelimit-remaining-tokens, and retry-after headers (where present) to proactively route around exhausted keys rather than waiting for a 429.

Circuit Breaker Pattern for LLM Providers ▼

The circuit breaker prevents cascading failures when a provider is degraded. It exists in three states:

CLOSED

Normal operation. Requests pass through. Failure rate tracked in a sliding window.

OPEN

Provider is tripped. All requests immediately fail fast to the next fallback. No requests hit the degraded provider.

HALF-OPEN

After cool-down period, one probe request is allowed through. If it succeeds, circuit closes. If it fails, circuit re-opens.

"""
Circuit breaker implementation for LLM provider calls.
Thread-safe using threading.Lock for multi-threaded gateway servers.
"""
import time
import threading
from enum import Enum, auto
from dataclasses import dataclass, field

class State(Enum):
    CLOSED    = auto()
    OPEN      = auto()
    HALF_OPEN = auto()

@dataclass
class CircuitBreakerConfig:
    failure_threshold: int   = 5      # failures in window to trip
    success_threshold: int   = 2      # consecutive successes to close from half-open
    window_seconds:    float = 60.0   # sliding window duration
    recovery_timeout:  float = 30.0   # seconds before attempting half-open probe

class CircuitBreaker:
    def __init__(self, name: str, config: CircuitBreakerConfig = CircuitBreakerConfig()):
        self.name   = name
        self.config = config
        self._state = State.CLOSED
        self._failures: list[float] = []   # timestamps of recent failures
        self._successes_since_half_open = 0
        self._opened_at: float | None = None
        self._lock = threading.Lock()

    @property
    def state(self) -> State:
        with self._lock:
            if self._state == State.OPEN:
                if time.monotonic() - self._opened_at >= self.config.recovery_timeout:
                    self._state = State.HALF_OPEN
                    self._successes_since_half_open = 0
            return self._state

    def is_open(self) -> bool:
        return self.state == State.OPEN

    def record_success(self) -> None:
        with self._lock:
            if self._state == State.HALF_OPEN:
                self._successes_since_half_open += 1
                if self._successes_since_half_open >= self.config.success_threshold:
                    self._state = State.CLOSED
                    self._failures.clear()
            elif self._state == State.CLOSED:
                # prune stale failures
                now = time.monotonic()
                self._failures = [t for t in self._failures
                                  if now - t < self.config.window_seconds]

    def record_failure(self) -> None:
        with self._lock:
            now = time.monotonic()
            self._failures.append(now)
            # prune outside window
            self._failures = [t for t in self._failures
                              if now - t < self.config.window_seconds]
            if (self._state in (State.CLOSED, State.HALF_OPEN) and
                    len(self._failures) >= self.config.failure_threshold):
                self._state    = State.OPEN
                self._opened_at = now
                print(f"[CircuitBreaker] {self.name} TRIPPED — {len(self._failures)} failures")

    def call(self, fn, *args, **kwargs):
        """Wrap a provider call with circuit breaker logic."""
        if self.is_open():
            raise RuntimeError(f"CircuitBreaker OPEN for {self.name} — fast-failing to fallback")
        try:
            result = fn(*args, **kwargs)
            self.record_success()
            return result
        except Exception as exc:
            self.record_failure()
            raise

5. Load Balancing Across Providers

Strategies & Quota Management ▼

When you have multiple API keys for the same provider (e.g., 5 OpenAI org keys each with their own rate limit), or equivalent capacity across providers (e.g., OpenAI + Azure OpenAI), you need a load balancer inside your gateway.

Strategy How It Works Best For Downside
Round-Robin Cycle through keys/endpoints sequentially Homogeneous keys with equal limits Doesn't account for key exhaustion or variable latency
Weighted Round-Robin Each key gets a weight proportional to its quota Keys with unequal rate limits (e.g., one key at Tier 5, others at Tier 2) Weights must be kept current as quotas change
Least Connections Route to the key/endpoint with fewest in-flight requests Variable-length requests (mix of streaming and batch) More bookkeeping; race conditions in distributed gateways
Token-Bucket Aware Track remaining TPM for each key in real time; route to key with most remaining tokens High-throughput systems where TPM is the binding constraint Requires reliable tracking of consumed tokens across gateway replicas
Latency-Weighted Prefer endpoint with lowest current p95 latency (EMA-tracked) Multi-region deployments (us-east vs. eu-west) Slow to react to sudden latency spikes

Provider Health Checking

The gateway should run a background health-check loop separate from request-path circuit breakers:

  • Every 30 s: send a minimal probe request (e.g., 1-token completion) to each provider endpoint
  • Track TTFT and success rate; mark endpoint as degraded if probe p95 > 2× baseline
  • Push health state to an in-memory map consulted by the routing engine
  • Alert on PagerDuty / OpsGenie when primary provider health drops below 95% success rate

Quota Management Across Multiple Keys

"""
Token-bucket quota tracker for a pool of API keys.
Uses Redis for distributed state across gateway replicas.
"""
import time
import redis

class QuotaManager:
    def __init__(self, redis_client: redis.Redis, refill_interval_s: int = 60):
        self.redis = redis_client
        self.refill_interval = refill_interval_s

    def _key(self, api_key_id: str) -> str:
        bucket = int(time.time() / self.refill_interval)
        return f"quota:{api_key_id}:{bucket}"

    def consume(self, api_key_id: str, tokens: int, limit: int) -> bool:
        """Returns True if tokens could be consumed, False if quota exceeded."""
        k = self._key(api_key_id)
        pipe = self.redis.pipeline()
        pipe.incrby(k, tokens)
        pipe.expire(k, self.refill_interval * 2)
        results = pipe.execute()
        used = results[0]
        return used <= limit

    def remaining(self, api_key_id: str, limit: int) -> int:
        k = self._key(api_key_id)
        used = int(self.redis.get(k) or 0)
        return max(0, limit - used)

    def pick_key(self, key_pool: list[dict]) -> dict | None:
        """
        Pick the key with the most remaining quota.
        key_pool: [{"id": "sk-...", "limit_tpm": 80000}, ...]
        """
        candidates = [
            (k, self.remaining(k["id"], k["limit_tpm"]))
            for k in key_pool
        ]
        candidates.sort(key=lambda x: x[1], reverse=True)
        best_key, best_remaining = candidates[0]
        if best_remaining <= 0:
            return None  # all keys exhausted
        return best_key

Geographic Routing for Compliance

Data residency requirements (GDPR, HIPAA, SOC 2) can mandate that certain data never leaves a geographic boundary:

  • EU users: Route to Azure OpenAI EU West or Anthropic's planned EU endpoint; never to US-based endpoints
  • Healthcare data: Route to HIPAA-BAA-covered endpoints only (Azure OpenAI, AWS Bedrock, GCP Vertex — all have BAAs; direct OpenAI API does not)
  • Implement as a hard pre-filter before the routing engine: tag each request with its compliance zone, maintain a zone → allowed-endpoint mapping, reject any routing decision that violates the zone constraint

6. Tools & Platforms

LiteLLM, Portkey, Martian, OpenRouter — Compared ▼

LiteLLM

Open Source

Unified Python SDK + proxy server for 100+ LLM providers. Drop-in replacement for the OpenAI SDK. The de-facto standard for multi-provider support in Python.

  • OpenAI-compatible proxy (self-hosted)
  • Built-in fallbacks, retries, load balancing
  • Cost tracking via SQLite or Postgres
  • Teams / virtual keys for internal rate limiting
  • Streaming support across all providers

Best for: Teams that want full control, no SaaS dependency, and need to support many providers.

Portkey

SaaS + OSS SDK

Production AI gateway with a rich analytics dashboard, prompt versioning, and guardrails. SaaS gateway with an OSS SDK wrapper.

  • Detailed latency/cost dashboards out-of-the-box
  • Semantic caching (in-built)
  • Guardrails (PII masking, content filtering)
  • Prompt versioning and A/B testing
  • Virtual keys per team/feature

Best for: Teams that want analytics and guardrails without building them from scratch.

Martian

SaaS

Intelligent model router that uses ML to predict which model will give the best quality/cost ratio for a specific query. Learns from your traffic.

  • ML-powered routing (not just rules)
  • Learns from your labelled quality feedback
  • OpenAI-compatible proxy endpoint
  • Cost guarantees with quality floors

Best for: Teams willing to pay for smart routing without building a classifier.

OpenRouter

SaaS Marketplace

Multi-provider marketplace with a single API key giving access to 200+ models from 30+ providers. Pay-per-token, no subscription.

  • One API key for every major model
  • Automatic provider fallbacks for popular models
  • Best for: rapid prototyping, model evaluation
  • Higher per-token cost (margin over provider price)

Best for: Rapid prototyping or teams that want to test many models without managing provider accounts.

7. Building a Model Router (Hands-On)

Architecture & Full Python/FastAPI Implementation ▼

Architecture Walkthrough

1
Request ingress: FastAPI accepts an OpenAI-compatible POST /v1/chat/completions. Validates JWT / API key, extracts tenant metadata.
2
Semantic cache lookup: Hash the canonicalised messages array. Query Redis for an exact match. If hit, return instantly (p99 < 5 ms).
3
Complexity classification: Run the heuristic classifier (Section 3) to assign simple / medium / complex. Optionally escalate borderline cases to a fast LLM judge.
4
Model selection: Combine complexity tier, tenant cost budget, latency SLA, and compliance zone to select a model and API key via QuotaManager.
5
Provider call with circuit breaker: Wrap the LiteLLM call in a circuit breaker. On failure, advance the fallback chain.
6
Observability emit: Write a structured log event: model, provider, tenant, tokens_in, tokens_out, latency_ms, cost_usd, cache_hit.
7
Cache population: Write successful response to Redis with TTL proportional to query type (factual: 24 h; creative: no cache).

    "claude-sonnet-3-5":   0.003,
    "claude-haiku-3-5":    0.00025,
    "together_ai/meta-llama/Meta-Llama-3.1-8B-Instruct-Turbo": 0.0001,
}

CACHE_TTL = {
    "simple": 86400,   # 24 h — factual answers are stable
    "medium": 3600,    # 1 h
    "complex": 300,    # 5 min — complex answers vary with context
}

# ─── Pydantic models ──────────────────────────────────────────────────────────

class Message(BaseModel):
    role: str
    content: str

class ChatRequest(BaseModel):
    model: str = "auto"          # callers can pass "auto" to let router decide
    messages: list[Message]
    stream: bool = False
    max_tokens: int = 1024
    temperature: float = 0.7
    # Router hints (optional, passed in extra fields)
    latency_sla_ms: int  = 5000
    max_cost_usd:   float = 0.10
    task_type: str = "general"

# ─── Complexity classifier ────────────────────────────────────────────────────

def classify_complexity(messages: list[Message]) -> str:
    last_user = next(
        (m.content for m in reversed(messages) if m.role == "user"),
        ""
    )
    tokens = len(last_user.split())
    lowered = last_user.lower()

    complex_kws = {"step by step", "explain why", "debug", "refactor",
                   "compare", "analyse", "analyze", "tradeoff"}
    if any(kw in lowered for kw in complex_kws) or tokens > 600:
        return "complex"
    if tokens > 150:
        return "medium"
    return "simple"

# ─── Cache ────────────────────────────────────────────────────────────────────

def _cache_key(messages: list[Message]) -> str:
    payload = json.dumps([m.model_dump() for m in messages], sort_keys=True)
    return "cache:" + hashlib.sha256(payload.encode()).hexdigest()

async def cache_get(redis: aioredis.Redis, key: str) -> str | None:
    return await redis.get(key)

async def cache_set(redis: aioredis.Redis, key: str, value: str, ttl: int) -> None:
    await redis.setex(key, ttl, value)

# ─── Cost tracker ─────────────────────────────────────────────────────────────

async def record_cost(
    redis: aioredis.Redis,
    tenant_id: str,
    model: str,
    input_tokens: int,
    output_tokens: int,
) -> float:
    cost = (
        input_tokens  / 1000 * COST_PER_1K_INPUT.get(model, 0.005) +
        output_tokens / 1000 * COST_PER_1K_INPUT.get(model, 0.005) * 2
    )
    key = f"cost:{tenant_id}:{int(time.time() // 3600)}"  # hourly bucket
    await redis.incrbyfloat(key, cost)
    await redis.expire(key, 7200)
    return cost

# ─── Application ──────────────────────────────────────────────────────────────

app = FastAPI(title="Model Router", version="0.1.0")

@app.on_event("startup")
async def startup():
    app.state.redis = await aioredis.from_url("redis://localhost:6379")

@app.on_event("shutdown")
async def shutdown():
    await app.state.redis.aclose()

@app.post("/v1/chat/completions")
async def chat_completions(req: ChatRequest, request: Request):
    redis: aioredis.Redis = request.app.state.redis
    tenant_id = request.headers.get("x-tenant-id", "default")

    # 1. Cache lookup
    ck = _cache_key(req.messages)
    cached = await cache_get(redis, ck)
    if cached:
        logger.info(f"cache_hit tenant={tenant_id}")
        return json.loads(cached)

    # 2. Classify
    tier = classify_complexity(req.messages)

    # 3. Select model (respects max_cost hint)
    models = MODEL_TIERS[tier]

    # 4. Call with fallback chain
    last_exc: Exception | None = None
    for model in models:
        try:
            t0 = time.monotonic()
            response = await litellm.acompletion(
                model=model,
                messages=[m.model_dump() for m in req.messages],
                max_tokens=req.max_tokens,
                temperature=req.temperature,
                stream=False,
            )
            latency_ms = (time.monotonic() - t0) * 1000

            # 5. Cost tracking
            usage = response.usage
            cost = await record_cost(
                redis, tenant_id, model,
                usage.prompt_tokens, usage.completion_tokens
            )

            # 6. Log
            logger.info(
                f"model={model} tier={tier} tenant={tenant_id} "
                f"tokens_in={usage.prompt_tokens} tokens_out={usage.completion_tokens} "
                f"latency_ms={latency_ms:.0f} cost_usd={cost:.6f}"
            )

            # 7. Cache store
            response_dict = response.model_dump()
            await cache_set(redis, ck, json.dumps(response_dict), CACHE_TTL[tier])

            return response_dict

        except Exception as exc:
            logger.warning(f"model={model} failed: {exc} — trying next fallback")
            last_exc = exc
            continue

    raise HTTPException(status_code=503, detail=f"All models failed: {last_exc}")

"Your classifier needs labelled training data you may not have. Start with rules-based routing using heuristics; instrument quality feedback; use that to train a better ML classifier after 2-4 weeks of production traffic."

Distributed Gateway Consistency

"Quota tracking across N gateway replicas requires a shared store (Redis). Eventual consistency is acceptable for TPM tracking — a 1-2 second window of over-counting is tolerable and dramatically simpler than distributed transactions."

The Routing Quality Flywheel

The best staff-level insight: model routing and quality measurement form a virtuous cycle.

  1. Route requests → collect model, latency, tokens for each request
  2. Collect user quality signals (implicit: re-asks, explicit: thumbs, LLM-as-judge)
  3. Train/update classifier on (request features, model) → quality_score
  4. Better classifier → smarter routing → lower cost at same quality
  5. Use cost savings to run more quality evaluations → richer training data

This flywheel means the system gets cheaper and better simultaneously as it accumulates traffic — a classic compounding moat in AI product infrastructure.

9. Active Recall Questions

Test yourself before looking at the answers. Cover the answer section and write your own response first.

What are the three states of a circuit breaker, and when does it transition between them?

CLOSED (normal): requests pass through; failures are counted in a sliding window. Transitions to OPEN when the failure count exceeds a threshold (e.g., 5 failures in 60 s).

OPEN (tripped): all requests fast-fail immediately to the fallback chain; no traffic hits the degraded provider. Transitions to HALF-OPEN after a recovery timeout (e.g., 30 s).

HALF-OPEN (probing): a single probe request is allowed through. If it succeeds (and subsequent probes succeed up to a threshold), the circuit transitions back to CLOSED. If it fails, it returns to OPEN and resets the recovery timer.

A company wants to cut their LLM spend by 60% without degrading CSAT. What is your approach?
  1. Measure first: instrument all requests with model, tokens, cost. Build a cost attribution dashboard by feature/query-type.
  2. Classify queries: build a complexity classifier (start with heuristics). Identify what % of traffic is "simple" — often 60-70%.
  3. Semantic caching: enable exact-match prompt caching (free via Anthropic/OpenAI native). Often saves 10-20% immediately.
  4. Route simple queries to small models: Claude Haiku 3.5 costs ~6% of Claude Sonnet for equivalent quality on simple tasks.
  5. Measure quality per route: set up LLM-as-judge or human eval checkpoints; ensure quality floors are maintained before expanding routing.
  6. Prompt optimisation: remove redundant system prompt tokens; compress context with summarisation for long conversations.

A 60% cost reduction is very achievable: 70% of traffic on Haiku (6% cost) + 20% on GPT-4o-mini (1% cost) + 10% on GPT-4o (100% cost) = 0.70×6 + 0.20×1 + 0.10×100 = 4.2 + 0.2 + 10 = 14.4 relative cost vs. 100 baseline — an 86% reduction!

What is the difference between RPM and TPM rate limits, and how does your gateway handle each?

RPM (requests per minute): a limit on the number of API calls regardless of size. A 429 is returned immediately if exceeded. The gateway handles this via rate-limit-aware load balancing across multiple API keys; the Retry-After header is parsed and respected.

TPM (tokens per minute): a limit on total token throughput. A large 50K-token request consumes as much quota as 500 small 100-token requests. The gateway handles this by: (1) estimating input tokens before the call (tiktoken), (2) tracking consumed tokens per key in Redis per-minute buckets, (3) routing to keys with sufficient remaining TPM. Token estimation errors mean the gateway must also handle reactive 429s when actual usage exceeds estimates.

The key insight: both limits can bind simultaneously. A well-designed gateway tracks both and routes to the key with the most headroom on the binding constraint.

Why is streaming TTFT (time-to-first-token) more important than total latency for user-facing surfaces?

Users perceive latency primarily as the time before they see any response — not the time for the complete response. Research shows that TTFT <500 ms feels "instant"; TTFT >2 s feels "slow" even if the full generation completes in 5 s total.

Streaming starts displaying tokens as they arrive, so a 500 ms TTFT + 4.5 s full generation feels much faster than a 4 s non-streaming response even though the total latency is similar.

For the gateway, this means: (1) the timeout that triggers a fallback should fire on TTFT, not total latency; (2) model selection should optimise for p95 TTFT, not average total latency; (3) small models have lower TTFT even when total token generation time is comparable.

What data residency concerns affect model routing decisions, and how do you implement compliance-aware routing?

Key compliance zones:

  • GDPR: EU personal data must not be processed outside the EU/EEA without adequate safeguards. Direct OpenAI API data may be processed in US datacenters — use Azure OpenAI EU West or a compliant EU endpoint.
  • HIPAA: Protected health information (PHI) requires a Business Associate Agreement (BAA). Only Azure OpenAI, AWS Bedrock, and GCP Vertex AI offer BAAs. The direct OpenAI API does not qualify.
  • SOC 2 / ISO 27001: Enterprise customers require their data not be used for model training. Most API providers offer "zero data retention" tiers — confirm and route accordingly.

Implementation: tag each request with a compliance zone at the tenant level (stored in your tenant config). The routing engine applies a hard pre-filter: only endpoints in the allowed set for that zone are candidates. The routing optimizer then picks the best model among compliant options only.

How does semantic caching differ from exact-match caching, and when does each apply?

Exact-match caching: hash the full request payload (model + messages + parameters). Cache hit only if the payload is byte-for-byte identical. Very fast (O(1) Redis lookup), zero false positives. Providers like OpenAI and Anthropic do this natively (prompt caching) for repeated prefix tokens.

Semantic caching: embed the user query into a vector, do ANN (approximate nearest neighbour) search in a vector DB (Qdrant, Pinecone, pgvector). Return the cached response if a semantically similar prior query (cosine similarity > threshold, e.g., 0.95) exists.

When to use each:

  • Exact-match: always — zero cost, zero risk of incorrect cache hits
  • Semantic: for FAQ-style or high-repetition traffic (customer support, chatbots) where users phrase the same question differently. Threshold must be tuned carefully — too low and you'll return wrong answers for similar-but-different questions

Typical semantic cache hit rate on customer support traffic: 20-40%. At scale this is enormous — 30% of GPT-4o calls saved is a 30% cost reduction with zero quality trade-off.
