The AI Cost Problem

Traditional software vs. AI: a fundamentally different cost curve

In traditional software, once you've paid for servers the marginal cost of an extra request is near zero — a MySQL query costs fractions of a microsecond of CPU. AI inference is the opposite: every request consumes tokens, and tokens cost real money proportional to the content processed and generated. There is no "cached hot path" at the model level. A 10,000-token context window fed through GPT-4o costs roughly $0.10 for that single request.

Real-world cost horror stories — and how companies fixed them

These are real patterns from production teams (details anonymised or from public post-mortems):

1
The context-stuffing agent
A customer support automation team built an agent that prepended the entire conversation history (avg 8,000 tokens) to every tool call. With 5 tool calls per workflow, each user interaction consumed 40,000+ input tokens. At GPT-4o pricing (~$2.50/M input tokens) and 500K daily sessions, the monthly bill was $1.5M — just for input tokens. Fix: summarise history after each turn (sliding window), reducing context to 1,500 tokens. Cost dropped 80%.
2
The re-embedding pipeline
A startup re-embedded their entire 2M-document knowledge base nightly as a "safety" measure. At $0.13/M tokens (text-embedding-3-small) and 500 tokens/doc average, that's $130/night or ~$47K/year — for data that changes <0.1% per day. Fix: incremental embedding on document change events only. Cost: $40/month.
3
The fanout classifier
A search product used GPT-4 to classify every search query into 12 categories so it could route to specialised sub-systems. Average query: 15 tokens. GPT-4 input + output: ~25 tokens total per classification. At 20M queries/day and GPT-4 pricing ($30/M input), daily classification cost: $15,000. Fix: fine-tuned a DistilBERT classifier on labelled data from GPT-4 outputs. Inference cost: $2/day. Break-even: 2 days.
4
The LLM-as-formatter
A data pipeline team used Claude to format JSON outputs from a legacy system into a new schema. The task was deterministic — always the same transformation. Fix: a 50-line Python script. LLM cost saved: $8K/month.
Staff-level insight: The first question you should ask about any LLM usage is: "Does this task actually require a frontier model, or can it be solved with a smaller model, a rules engine, or a cached response?" Most production AI systems over-use frontier models in their early implementations.

Token Economics

How token pricing works

LLM providers charge per million tokens processed, split into input tokens (your prompt + context + history) and output tokens (the model's response). Output tokens cost 3–5x more than input tokens because they require sequential, non-parallelisable computation at inference time — each output token depends on the previous one.

Rule of thumb: 1 token ≈ 0.75 words in English. A 1,000-word document ≈ 1,333 tokens. A GPT-4-class model with a 128K context window can theoretically process ~96,000 words — but the cost of filling that window is $0.38 (input) + whatever output you generate.

Prompt Compression & Optimization

System prompt optimization

The system prompt is sent with every single request. A bloated system prompt of 3,000 tokens costs you 3,000 tokens × (requests/day) × ($/M tokens). At 1M requests/day and GPT-4o pricing that's $7,500/day just for the system prompt.

Techniques to compress system prompts

  • Remove redundancy: "You are a helpful, friendly, and knowledgeable AI assistant that always tries to help the user" → "Helpful AI assistant." Most LLMs are already trained to be helpful — stating it wastes tokens.
  • Use abbreviations and structured formats: JSON/YAML lists instead of prose paragraphs. A 200-token prose instruction often compresses to 80 tokens in structured form.
  • Reference over recitation: Instead of pasting a 500-token policy into every prompt, use a short pointer ("Follow company policy v2.3") if the model was fine-tuned on that policy.
  • Deduplication: Many teams copy-paste sections across system prompts. Audit and merge shared sections.
  • Anthropic prompt caching: For prompts over 1,024 tokens, Claude supports cache_control blocks. Cached tokens cost 10% of normal input price after the first call.
  • OpenAI prompt caching: Automatic for prompts >1,024 tokens with the same prefix; cached tokens cost 50% less. Design prompts so the static prefix is as long as possible.

Few-shot example pruning

Few-shot examples demonstrate format and style. The temptation is to add many examples ("the more, the better"), but research shows diminishing returns after 4–8 examples for most tasks, and negative returns (distraction) beyond 20. Each example costs tokens. A 5-example prompt with 200-token examples = 1,000 extra tokens per request.

Adaptive few-shot selection: Instead of a static example set, retrieve the 2–3 most similar examples to the current query from a vector store. This costs ~$0.0001 per lookup but reduces example tokens by 60–80% while improving example relevance.

Dynamic context window management

Long context windows are a trap. A 128K context window costs 128x more to fill than a 1K window, but you almost never need all of it. The "lost in the middle" phenomenon (Liu et al., 2023) shows model accuracy degrades for information placed in the middle of very long contexts — so you pay more for worse results.

Strategies

1
Sliding window with summarisation
Keep the last N turns verbatim (recency matters). Summarise older turns into a compact rolling summary. Typical: last 3 turns verbatim + 200-token rolling summary of the rest. Reduces multi-turn conversation cost by 70%.
2
Retrieval-augmented context
Instead of stuffing all documents into context, retrieve only the top-K relevant chunks. 3 chunks × 400 tokens = 1,200 tokens vs. 50 documents × 400 tokens = 20,000 tokens. 16x cost reduction with comparable answer quality.
3
Token budget enforcement
Truncate from the middle or beginning of long documents, not the end — the last 20% of a document often contains the conclusion, which is most relevant. Use a tokenizer library (tiktoken for OpenAI, tokenizers for Hugging Face) to measure before sending.
4
Structured extraction preprocessing
If you're sending a 5,000-token PDF to answer a specific question, consider running a fast cheap model first to extract just the relevant paragraphs, then sending only those to the expensive model. 2-step pipeline but 10x cheaper.

LLMLingua — learned prompt compression

Microsoft Research's LLMLingua (2023) and LLMLingua-2 (2024) use a small language model to score token importance in a prompt and drop low-importance tokens. Achieves 2–20x compression with <5% quality degradation on most tasks. It's a pre-processing step that runs a tiny model locally (Llama 7B or smaller) before calling the expensive API.

When it makes sense: LLMLingua adds ~50–100ms latency and the cost of running a small model. At high request volume and expensive models (GPT-4o), this is easily ROI-positive. At low volume or cheap models, the overhead isn't worth it.

Code: Token counter and prompt optimizer

"""
prompt_optimizer.py
Measures token count, applies LLMLingua compression, and reports savings.
Requires: pip install tiktoken llmlingua
"""
import tiktoken
from llmlingua import PromptCompressor

class PromptOptimizer:
    def __init__(self, model_name: str = "gpt-4o"):
        self.enc = tiktoken.encoding_for_model(model_name)
        self.compressor = None  # lazy-load

    def count_tokens(self, text: str) -> int:
        return len(self.enc.encode(text))

    def _get_compressor(self):
        if self.compressor is None:
            # Uses Llama-2-7B as the scoring model; runs locally
            self.compressor = PromptCompressor(
                model_name="NousResearch/Llama-2-7b-hf",
                use_llmlingua2=True,
                device_map="auto",
            )
        return self.compressor

    def compress(
        self,
        system: str,
        instruction: str,
        context: str,
        target_ratio: float = 0.5,  # keep 50% of tokens
    ) -> dict:
        original_tokens = (
            self.count_tokens(system)
            + self.count_tokens(instruction)
            + self.count_tokens(context)
        )

        result = self._get_compressor().compress_prompt(
            context,
            instruction=instruction,
            question="",
            ratio=target_ratio,
        )

        compressed_context = result["compressed_prompt"]
        new_tokens = (
            self.count_tokens(system)
            + self.count_tokens(instruction)
            + self.count_tokens(compressed_context)
        )

        return {
            "original_tokens": original_tokens,
            "compressed_tokens": new_tokens,
            "savings_pct": round((1 - new_tokens / original_tokens) * 100, 1),
            "compressed_context": compressed_context,
        }

    def estimate_cost(
        self, tokens: int, input_price_per_m: float = 2.50
    ) -> float:
        return tokens / 1_000_000 * input_price_per_m


# Usage
if __name__ == "__main__":
    optimizer = PromptOptimizer(model_name="gpt-4o")

    system = "You are a helpful assistant specialized in answering questions about company policies."
    instruction = "Answer the user's question based on the policy documents below."
    context = "... (5000 token policy document) ..."

    result = optimizer.compress(system, instruction, context, target_ratio=0.4)

    print(f"Original tokens:    {result['original_tokens']}")
    print(f"Compressed tokens:  {result['compressed_tokens']}")
    print(f"Savings:            {result['savings_pct']}%")

    daily_requests = 100_000
    original_cost = optimizer.estimate_cost(result["original_tokens"] * daily_requests)
    compressed_cost = optimizer.estimate_cost(result["compressed_tokens"] * daily_requests)
    print(f"Daily cost (original):    ${original_cost:,.2f}")
    print(f"Daily cost (compressed):  ${compressed_cost:,.2f}")
    print(f"Daily savings:            ${original_cost - compressed_cost:,.2f}")

Semantic Caching

Exact match vs. semantic similarity caching

Traditional HTTP caching uses exact-match cache keys (URL + headers). This works when the same request is repeated verbatim. For LLM workloads, semantically equivalent questions arrive in different phrasings: "What is your return policy?" and "How do I return a product?" are different strings but the same intent. Semantic caching uses embedding similarity to match "close enough" queries to cached responses.

How it works

1
Incoming query → embed using a fast embedding model (e.g., text-embedding-3-small, ~$0.02/M tokens).
2
ANN search in vector cache (Redis with RediSearch, Qdrant, Faiss in-memory) for nearest cached query embedding.
3
If cosine similarity > threshold (typically 0.92–0.97), return cached response. Otherwise, call LLM, cache result + embedding.
4
Cache TTL and invalidation: tie to document version/hash if context-dependent, or set TTL based on how quickly answers become stale.
Threshold calibration matters: Too low (0.85) → wrong cached answers served; too high (0.99) → near-zero cache hit rate. Start at 0.93 and A/B test against manual quality reviews. Use an LLM judge to automatically flag cases where cached answer quality dropped >10%.

Cache hit rate analysis

Cache hit rate depends heavily on query distribution. Customer support and FAQ-style applications have high repetition (40–70% hit rates achievable). Open-ended creative or analytical queries have low repetition (<10%). Match your caching strategy to your query distribution.

GPTCache and similar tools

Code: Redis-based semantic cache

"""
semantic_cache.py
Redis + RediSearch vector index for LLM response caching.
Requires: pip install redis openai numpy
"""
import hashlib
import json
import time
from dataclasses import dataclass
from typing import Optional

import numpy as np
import openai
import redis


@dataclass
class CacheEntry:
    query: str
    response: str
    embedding: list[float]
    created_at: float
    hit_count: int = 0


class SemanticCache:
    def __init__(
        self,
        redis_url: str = "redis://localhost:6379",
        similarity_threshold: float = 0.93,
        ttl_seconds: int = 3600,
        embed_model: str = "text-embedding-3-small",
    ):
        self.redis = redis.from_url(redis_url)
        self.threshold = similarity_threshold
        self.ttl = ttl_seconds
        self.embed_model = embed_model
        self.oai = openai.OpenAI()
        self._ensure_index()

    def _ensure_index(self):
        """Create RediSearch vector index if it doesn't exist."""
        try:
            self.redis.execute_command("FT.INFO", "llm_cache_idx")
        except redis.ResponseError:
            self.redis.execute_command(
                "FT.CREATE", "llm_cache_idx",
                "ON", "HASH",
                "PREFIX", "1", "llmcache:",
                "SCHEMA",
                "embedding", "VECTOR", "HNSW", "6",
                "TYPE", "FLOAT32",
                "DIM", "1536",
                "DISTANCE_METRIC", "COSINE",
                "query_text", "TEXT",
            )

    def _embed(self, text: str) -> list[float]:
        resp = self.oai.embeddings.create(input=text, model=self.embed_model)
        return resp.data[0].embedding

    def _cosine_sim(self, a: list[float], b: list[float]) -> float:
        va, vb = np.array(a), np.array(b)
        return float(np.dot(va, vb) / (np.linalg.norm(va) * np.linalg.norm(vb)))

    def get(self, query: str) -> Optional[str]:
        """Return cached response if a semantically similar query exists."""
        embedding = self._embed(query)
        embedding_bytes = np.array(embedding, dtype=np.float32).tobytes()

        # KNN search: top-1 nearest neighbour
        results = self.redis.execute_command(
            "FT.SEARCH", "llm_cache_idx",
            f"*=>[KNN 1 @embedding $vec AS score]",
            "PARAMS", "2", "vec", embedding_bytes,
            "RETURN", "3", "query_text", "response_json", "score",
            "SORTBY", "score",
            "DIALECT", "2",
        )

        if results[0] == 0:
            return None  # empty cache

        # results[1] is the key, results[2] is the field list
        fields = dict(zip(results[2][::2], results[2][1::2]))
        score = float(fields.get(b"score", 1.0))  # RediSearch returns distance

        # Redis COSINE distance = 1 - cosine_similarity
        similarity = 1.0 - score

        if similarity >= self.threshold:
            cache_key = results[1].decode()
            # Increment hit counter
            self.redis.hincrby(cache_key, "hit_count", 1)
            return json.loads(fields[b"response_json"])

        return None

    def set(self, query: str, response: str):
        """Store a new query-response pair in the cache."""
        embedding = self._embed(query)
        key = f"llmcache:{hashlib.sha256(query.encode()).hexdigest()[:16]}"
        self.redis.hset(key, mapping={
            "query_text": query,
            "response_json": json.dumps(response),
            "embedding": np.array(embedding, dtype=np.float32).tobytes(),
            "created_at": time.time(),
            "hit_count": 0,
        })
        self.redis.expire(key, self.ttl)

    def stats(self) -> dict:
        """Return cache statistics."""
        keys = self.redis.keys("llmcache:*")
        total_hits = sum(
            int(self.redis.hget(k, "hit_count") or 0) for k in keys
        )
        return {
            "cached_entries": len(keys),
            "total_cache_hits": total_hits,
        }


# Usage example
def cached_llm_call(cache: SemanticCache, query: str, system: str) -> str:
    cached = cache.get(query)
    if cached:
        print("[CACHE HIT]")
        return cached

    print("[CACHE MISS] Calling LLM...")
    oai = openai.OpenAI()
    resp = oai.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "system", "content": system},
                  {"role": "user", "content": query}],
    )
    answer = resp.choices[0].message.content
    cache.set(query, answer)
    return answer
Safety Risks of Semantic Caching
Eugene Yan calls semantic caching "a disaster waiting to happen" if implemented without safeguards. The core risk: semantically similar queries can have very different correct answers.

Failure Modes

Failure ModeExampleImpactMitigation
False positive match "What's Apple's stock price?" matches cached "What's Apple's revenue?" (cosine sim 0.94) User gets completely wrong answer with high confidence Higher threshold (0.95+), domain-specific embedding models, keyword overlap check as secondary filter
Stale context Cached response about product pricing is served after a price change Incorrect information, potential legal/financial liability TTL tied to data freshness, cache invalidation on upstream data changes, version hashing
User-specific leakage User A asks about their account, User B gets User A's cached response because query embeddings are similar Privacy violation, data leak between users Partition cache by user/tenant ID. Never share cache across security boundaries.
Adversarial cache poisoning Attacker crafts query that produces a harmful cached response, then similar queries from other users hit the poisoned cache entry Serving harmful content at scale Output guardrails on cache writes (not just reads), cache entry moderation, anomaly detection

Safe Semantic Caching Checklist

  • Partition by tenant: Never share cached responses across users or organizations
  • Set aggressive TTLs: Hours, not days. Stale cache is worse than no cache for factual queries.
  • Validate before serving: Run a lightweight check — does the cached response actually answer the new query? A small classifier or keyword overlap check catches the worst false positives.
  • Monitor cache quality: Sample 1-5% of cache hits, score with LLM-as-judge, alert if quality drops below threshold
  • Exclude sensitive query types: Don't cache account-specific, PII-containing, or time-sensitive queries
  • Log cache hit metadata: Track which cache entry served which query. Essential for debugging and auditing.

Staff-level insight: The decision to implement semantic caching should be driven by query distribution analysis. If >30% of queries are near-duplicates (support bots, FAQ systems), the ROI is clear. If queries are diverse and context-dependent (coding assistants, analytical tools), caching may cause more harm than good. Always measure false positive rate before enabling in production.

Tiered Model Selection & Routing

Complexity classification and cascading

Not all requests are equal. A user asking "What is 2+2?" and a user asking "Analyse the geopolitical implications of lithium supply chain concentration in Chile" both arrive as API requests, but they require vastly different model capabilities. Model routing classifies request complexity and routes to the cheapest model that can handle it adequately.

Complexity signals

  • Query length: Short queries (<50 tokens) are usually simpler
  • Query category: Factual lookup vs. reasoning vs. code generation vs. creative writing
  • Presence of multi-step words: "analyse", "compare", "explain why", "design a system" → escalate
  • User tier: Free users → cheap model; enterprise users → frontier model
  • Task type: Structured extraction, classification, simple Q&A → cheap; reasoning, long-form synthesis → expensive

Cascading pattern

Try the cheap model first. Use an LLM judge or rule-based check on the output quality. If quality is below threshold, retry with a more capable model. Works well for tasks where "good enough" is acceptable 70–80% of the time.

A/B testing model tiers

Before committing to a routing strategy, A/B test the model tiers against your specific task distribution. Shadow traffic: send 5% of production requests to the cheap model (without returning that response to users), evaluate quality, and measure the gap. If quality gap is <5% on your evaluation metrics, route 100% to the cheap model.

Fine-tuning vs. Prompting: Break-Even Analysis

When fine-tuning pays for itself

Fine-tuning embeds task knowledge into model weights, allowing you to use shorter prompts (no few-shot examples needed) and often a smaller model tier. The question is: how long until the inference savings recoup the training cost?

Break-even formula

break_even_requests = training_cost / (cost_per_request_before - cost_per_request_after)

Example: Training cost = $5,000. Before fine-tuning: $0.015/request (GPT-4o with 5,000-token prompt). After fine-tuning on GPT-4o mini with 500-token prompt: $0.0005/request. Savings: $0.0145/request. Break-even: 5000 / 0.0145 = 345K requests ≈ 3.5 days at 100K req/day.

Distillation: using GPT-4o to train a small model

Teacher-student distillation is one of the most cost-effective patterns in production AI:

  1. Generate 10K–100K high-quality labelled examples using GPT-4o (expensive, one-time cost)
  2. Fine-tune a small open-source model (Llama 8B, Mistral 7B) on those examples
  3. Deploy the fine-tuned small model for inference at near-zero marginal cost

Google reported doing this for their internal search quality ranking models. OpenAI's GPT-4 was reportedly used to generate training data for GPT-3.5-turbo instruction following. The pattern is ubiquitous at scale.

Code: Cost comparison calculator

"""
finetune_roi.py
Calculates break-even point and ROI for fine-tuning vs prompting.
"""
from dataclasses import dataclass


@dataclass
class ModelScenario:
    name: str
    input_price_per_m: float   # $ per million input tokens
    output_price_per_m: float  # $ per million output tokens
    avg_input_tokens: int       # tokens per request (prompt)
    avg_output_tokens: int      # tokens per request (response)
    one_time_cost: float = 0.0  # training / fine-tuning cost


def cost_per_request(scenario: ModelScenario) -> float:
    input_cost  = scenario.avg_input_tokens  / 1_000_000 * scenario.input_price_per_m
    output_cost = scenario.avg_output_tokens / 1_000_000 * scenario.output_price_per_m
    return input_cost + output_cost


def break_even_requests(baseline: ModelScenario, optimised: ModelScenario) -> int | None:
    base_cost = cost_per_request(baseline)
    opt_cost  = cost_per_request(optimised)
    savings_per_request = base_cost - opt_cost

    if savings_per_request <= 0:
        return None  # no break-even; optimised costs more per request

    total_investment = optimised.one_time_cost - baseline.one_time_cost
    if total_investment <= 0:
        return 0  # immediately profitable

    return int(total_investment / savings_per_request)


def print_analysis(
    baseline: ModelScenario,
    optimised: ModelScenario,
    daily_requests: int,
):
    base_cost = cost_per_request(baseline)
    opt_cost  = cost_per_request(optimised)
    beq       = break_even_requests(baseline, optimised)

    print(f"\n{'='*60}")
    print(f"BASELINE:  {baseline.name}")
    print(f"  Cost/request:  ${base_cost:.5f}")
    print(f"OPTIMISED: {optimised.name}")
    print(f"  Cost/request:  ${opt_cost:.5f}")

Queue-based batch processing — implementation sketch

"""
batch_processor.py
Collects requests into batches, submits to OpenAI Batch API,
polls for completion, distributes results.
"""
import json
import time
import uuid
from pathlib import Path
import openai


class OpenAIBatchProcessor:
    """
    Queues JSONL requests, submits to Batch API (50% cheaper),
    polls until done, returns results.
    """
    def __init__(self, client: openai.OpenAI):
        self.client = client

    def build_batch_file(
        self,
        requests: list[dict],   # each: {"custom_id": str, "messages": [...]}
        model: str = "gpt-4o-mini",
        output_path: str = "/tmp/batch_input.jsonl",
    ) -> str:
        with open(output_path, "w") as f:
            for req in requests:
                line = {
                    "custom_id": req.get("custom_id", str(uuid.uuid4())),
                    "method": "POST",
                    "url": "/v1/chat/completions",
                    "body": {
                        "model": model,
                        "messages": req["messages"],
                        "max_tokens": req.get("max_tokens", 1024),
                    },
                }
                f.write(json.dumps(line) + "\n")
        return output_path

    def submit(self, jsonl_path: str) -> str:
        with open(jsonl_path, "rb") as f:
            file_obj = self.client.files.create(file=f, purpose="batch")
        batch = self.client.batches.create(
            input_file_id=file_obj.id,
            endpoint="/v1/chat/completions",
            completion_window="24h",
        )
        print(f"Batch submitted: {batch.id} (status: {batch.status})")
        return batch.id

    def wait_for_completion(
        self, batch_id: str, poll_interval: int = 60
    ) -> dict:
        while True:
            batch = self.client.batches.retrieve(batch_id)
            print(f"  Status: {batch.status} | "
                  f"completed: {batch.request_counts.completed} / "
                  f"{batch.request_counts.total}")
            if batch.status in ("completed", "failed", "expired", "cancelled"):
                return batch
            time.sleep(poll_interval)

    def fetch_results(self, batch) -> list[dict]:
        if batch.status != "completed":
            raise RuntimeError(f"Batch {batch.id} status: {batch.status}")
        content = self.client.files.content(batch.output_file_id)
        results = []
        for line in content.text.strip().splitlines():
            results.append(json.loads(line))
        return results


# Usage
if __name__ == "__main__":
    client = openai.OpenAI()
    processor = OpenAIBatchProcessor(client)

    # Build 1000 requests
    requests = [
        {
            "custom_id": f"doc-{i}",
            "messages": [
                {"role": "system", "content": "Summarize in 2 sentences."},
                {"role": "user", "content": f"Document content {i}..."},
            ],
        }
        for i in range(1000)
    ]

    path   = processor.build_batch_file(requests, model="gpt-4o-mini")
    b_id   = processor.submit(path)
    batch  = processor.wait_for_completion(b_id)
    results = processor.fetch_results(batch)
    print(f"Got {len(results)} results.")

Budget Management & Guardrails

Per-user budgets, rate limiting by cost, and anomaly alerting

Traditional rate limiting counts requests per unit time (100 req/min). For AI systems, a single request can cost $0.001 or $10.00 depending on input/output volume. Rate limiting by request count is insufficient — you must rate limit by token spend.

Budget architecture

1
User-level budget: Each user has a daily/monthly token budget. Budget is stored in Redis with a TTL equal to the budget window. On each request, decrement by estimated cost (pre-request estimate using input tokens + expected output). If balance <= 0, reject with 429 + informative message.
2
Team/org-level budget: For internal AI platforms, each team has a monthly chargeback budget. Track spend in a relational DB (not just Redis) for billing and audit purposes.
3
Anomaly alerting: Alert when any entity (user, team, API key) spends more than 3x their 7-day rolling average in a single hour. This catches both runaway automation and credential theft.
4
Hard and soft limits: Soft limit = 80% of budget consumed → alert + reduce max_tokens. Hard limit = 100% → reject requests. Never silently degrade quality without notifying the user.

Chargeback models for internal AI platforms

When you operate an internal LLM gateway serving multiple teams, implement a chargeback system:

  • Metered billing: Each API call is tagged with team/project/environment. Monthly report shows cost by team. Teams become accountable for their spend.
  • Budget allocation: FinOps allocates AI budget to teams quarterly. Teams can request increases with business justification.
  • Wasteful pattern detection: Flag requests that use frontier models for tasks your routing classifier scores as "simple". Surface to team leads weekly.
  • Cost per product feature: Track cost per feature, not just per team. A single poorly-optimised feature can dominate costs and hide the signal.

Code: Budget tracking middleware (Python / FastAPI)

"""
budget_middleware.py
FastAPI middleware that enforces per-user token budgets using Redis.
Costs are estimated pre-request and reconciled post-response.
"""
import time
from dataclasses import dataclass
from typing import Callable

import redis.asyncio as aioredis
from fastapi import FastAPI, HTTPException, Request, Response
from fastapi.responses import JSONResponse


@dataclass
class BudgetConfig:
    daily_token_limit: int      = 500_000    # tokens / user / day
    monthly_token_limit: int    = 10_000_000 # tokens / user / month
    soft_limit_pct: float       = 0.80       # alert at 80%
    input_price_per_m: float    = 0.15       # GPT-4o mini pricing
    output_price_per_m: float   = 0.60


class BudgetMiddleware:
    def __init__(self, app: FastAPI, redis_url: str, config: BudgetConfig):
        self.app    = app
        self.redis  = aioredis.from_url(redis_url)
        self.config = config

    async def __call__(self, request: Request, call_next: Callable) -> Response:
        user_id = request.headers.get("X-User-ID", "anonymous")

        # Pre-flight: estimate input tokens from request body
        body = await request.body()
        estimated_input = self._estimate_input_tokens(body)

        # Check budget
        daily_key   = f"budget:daily:{user_id}:{self._today()}"
        daily_used  = int(await self.redis.get(daily_key) or 0)
        daily_limit = self.config.daily_token_limit

        if daily_used + estimated_input > daily_limit:
            return JSONResponse(
                status_code=429,
                content={
                    "error": "daily_budget_exceeded",
                    "used": daily_used,
                    "limit": daily_limit,
                    "message": f"You have used {daily_used:,} of {daily_limit:,} daily tokens.",
                },
            )

        # Soft limit check
        if daily_used > daily_limit * self.config.soft_limit_pct:
            request.state.soft_limit_reached = True

        # Process request and track time
        start = time.monotonic()
        response = await call_next(request)
        elapsed = time.monotonic() - start

        # Post-response: record actual token usage from response headers
        actual_input  = int(response.headers.get("X-Token-Input",  estimated_input))
        actual_output = int(response.headers.get("X-Token-Output", 0))
        total_tokens  = actual_input + actual_output

        # Increment counters (TTL = end of day + 1h buffer)
        await self.redis.incrby(daily_key, total_tokens)
        await self.redis.expire(daily_key, 90_000)  # 25h

        # Attach cost info to response
        cost = self._calc_cost(actual_input, actual_output)
        response.headers["X-Cost-USD"]          = f"{cost:.6f}"
        response.headers["X-Budget-Used-Today"] = str(daily_used + total_tokens)
        response.headers["X-Budget-Limit-Daily"]= str(daily_limit)

        # Anomaly check: if this single request used >10% of daily budget, log it
        if total_tokens > daily_limit * 0.10:
            await self._flag_anomaly(user_id, total_tokens, daily_limit)

        return response

    def _estimate_input_tokens(self, body: bytes) -> int:
        # Rough estimate: 1 token per 4 bytes
        return max(100, len(body) // 4)

    def _calc_cost(self, input_tokens: int, output_tokens: int) -> float:
        return (
            input_tokens  / 1_000_000 * self.config.input_price_per_m
            + output_tokens / 1_000_000 * self.config.output_price_per_m
        )

    def _today(self) -> str:
        return time.strftime("%Y-%m-%d")

    async def _flag_anomaly(self, user_id: str, tokens: int, limit: int):
        # In production: send to alerting system (PagerDuty, Slack, etc.)
        anomaly_key = f"anomaly:{user_id}:{self._today()}"
        await self.redis.lpush(anomaly_key, f"tokens={tokens},limit={limit},ts={time.time()}")
        await self.redis.expire(anomaly_key, 86_400)
        print(f"[BUDGET ANOMALY] User {user_id} used {tokens:,} tokens in one request "
              f"({tokens/limit*100:.1f}% of daily limit)")

Staff-Level Interview Angle

How staff engineers think about AI cost — systems framing

A senior engineer gives you a list of cost-cutting tips. A staff engineer gives you a framework for reasoning about cost as a first-class engineering concern, equivalent to reliability and latency.

The four levers

Every AI cost optimization maps to one of four levers:

Reduce
Tokens consumed per request (compression, caching, context mgmt)
Route
Use cheaper models for simpler requests (tiering, routing)
Reuse
Cache responses and avoid redundant inference (semantic cache)
Batch
Shift latency-tolerant workloads to batch APIs (50% discount)

Prioritization framework for interviews

When asked "How would you reduce AI costs by 60%?", walk through this decision tree:

  1. Measure first: You cannot optimize what you cannot observe. Instrument every LLM call with tokens in/out, model used, latency, user/feature tags. Build a cost dashboard before you optimize anything.
  2. Find the 80/20: In most systems, 20% of call sites consume 80% of token spend. Instrument and identify these. Optimise them first.
  3. Is it even necessary?: Is this task truly LLM-appropriate, or can it be done with a rules engine, regex, or a deterministic algorithm? This is zero-cost optimization.
  4. Semantic cache: If query distribution has any repetition, implement semantic caching before touching model selection. Can yield 40–60% cost reduction with one architectural change.
  5. Model routing: Classify requests and route cheap ones to cheap models. With a well-calibrated routing classifier, 60–70% of requests can go to a model 10x cheaper.
  6. Prompt compression: Reduce input tokens. Most early-stage systems have 2–4x token waste in their prompts.
  7. Fine-tune / distil: Only after validating at scale. The ROI is enormous at volume but the investment is not trivial.

The cost-quality-latency triangle

Every cost optimization has a quality and/or latency cost. The staff-level framing is: "What is the acceptable quality floor for this feature, and what is the latency SLA?" These constraints define the feasible space for cost reduction. Don't reduce cost below the quality floor — that turns a cost problem into a product problem.

Interview winning move: When given a cost optimization question, immediately frame your answer around measurement and instrumentation first, then prioritised optimisations by expected ROI. This signals you understand the engineering discipline, not just the techniques. Interviewers at staff level are evaluating whether you can lead a cost reduction initiative — measurement, hypothesis, experiment, ship.

Common interview follow-ups

  • "How do you ensure cost optimizations don't degrade user experience?" → Quality monitoring, shadow traffic, gradual rollout with quality gates.
  • "How would you build internal buy-in for the investment in a semantic cache?" → ROI calculation, A/B test to demonstrate cache hit rate, pilot on highest-cost feature.
  • "A fine-tune degraded over time. What happened and how do you fix it?" → Distribution shift. Monitor model performance metrics on live traffic; retrain periodically or on drift detection.
  • "How do you attribute AI costs to product decisions?" → Cost per feature tracking, FinOps-style chargeback, correlate cost metrics with product KPIs (engagement, revenue).

Active Recall Questions

Try to answer each question before expanding the answer.

Why are output tokens more expensive than input tokens, and what practical implication does this have for system design?
Output tokens require sequential autoregressive decoding — each token is generated one at a time and depends on all previous tokens. This cannot be parallelised across the sequence, unlike input processing which uses parallel attention. Input tokens are processed simultaneously in the attention layers (effectively O(n²) memory but parallelised on GPU).

Practical implication: Minimise output length wherever possible. Use structured output formats (JSON with short field names), request "answer only, no explanation" for classification tasks, and set max_tokens aggressively. For a model where output costs 4x input, cutting output tokens in half saves proportionally more than cutting input tokens by the same amount.
You have a customer support chatbot serving 500K queries/day. What is the first optimization you would implement, and why?
Semantic caching. Customer support has high query repetition ("What is your return policy?", "Where is my order?", "How do I cancel?"). A semantic cache with a 0.93 cosine similarity threshold can serve 40–60% of queries from cache with sub-2ms latency and zero LLM cost. This is the highest-ROI intervention with the lowest implementation risk.

Why not prompt compression first? Caching eliminates the entire LLM cost for cache hits. Compression only reduces it. Caching ROI = 100% cost savings on hits; compression ROI = 30–70% reduction on misses only.

After caching: Implement model routing — route simple queries (product lookups, status checks) to GPT-4o mini / Gemini Flash and only route complex escalations to frontier models. Combined with caching, you can reduce total LLM spend by 70–80%.
Explain the break-even calculation for fine-tuning. A team has 100K requests/day. GPT-4o with a 4,000-token prompt costs $0.015/request. A fine-tuned GPT-4o mini with a 200-token prompt costs $0.0008/request. Fine-tuning costs $8,000. When does fine-tuning break even?
Savings per request = $0.015 - $0.0008 = $0.0142/request
Break-even requests = $8,000 / $0.0142 = ~563,000 requests
At 100K requests/day: break-even in 5.6 days

Annual savings = $0.0142 × 100,000 × 365 = $518,300
1-year ROI: ($518,300 - $8,000) / $8,000 = 6,379%

This illustrates why fine-tuning is almost always worth it at significant scale for narrow, well-defined tasks. The ROI is extraordinary when the daily request volume is high.
What is the "lost in the middle" phenomenon and how does it inform context window management?
Liu et al. (2023) found that LLM performance on multi-document QA tasks degrades significantly for information placed in the middle of the context window, while information at the very beginning and end of the context is recalled with much higher accuracy. This is attributed to the attention mechanism — early and late positions receive disproportionate attention weight in practice.

Implications for system design:
  • Place the most critical information at the start (system prompt) or end (last user message) of the context.
  • When truncating long documents, truncate from the middle rather than the end — the conclusion is often most relevant and should be preserved.
  • This means you pay more and get worse results when filling large context windows with undiscriminating content. Selective retrieval (RAG) almost always beats long-context stuffing on both cost and quality.
  • For very long context workloads, consider hierarchical summarisation to compress the middle sections rather than passing them verbatim.
How does the OpenAI Batch API achieve 50% cost reduction, and what architectural pattern enables you to use it for non-interactive workloads?
The Batch API reduces cost because OpenAI can run batched requests at off-peak times and use spare GPU capacity rather than maintaining always-on low-latency infrastructure. Users accept up to 24-hour completion time in exchange for the discount. This is analagous to spot instances in cloud compute — you accept scheduling uncertainty for significantly lower cost.

Enabling architecture: The queue-based decoupling pattern:
  1. API gateway accepts requests synchronously, returns a job ID immediately.
  2. Requests are enqueued in SQS/Pub-Sub.
  3. A batch worker polls the queue, collects requests into JSONL files, submits to Batch API.
  4. A poller checks batch completion status every N minutes.
  5. Completed results are stored in object store (S3/GCS) or a results cache (Redis).
  6. Client is notified via webhook, WebSocket push, or polls the job endpoint.
This works for any workload where the user does not need to wait synchronously: background processing, report generation, content moderation, embedding generation, data annotation.
You are designing a rate limiting system for an internal AI platform. Why is request-count rate limiting insufficient, and how do you design a token-budget-based system?
Request-count rate limiting fails because requests have wildly variable cost. A 100-token request and a 50,000-token request are both "1 request" but differ in cost by 500x. A user making 10 large-context requests could consume the same budget as 5,000 small requests.

Token-budget-based system design:
  1. Per-user token counter in Redis with a TTL matching the budget window (daily or monthly). Use INCRBY for atomic increments.
  2. Pre-request check: estimate input tokens (from request body size or explicit token count). If remaining_budget - estimated_tokens < 0, reject with 429.
  3. Post-response reconciliation: read actual token usage from LLM response headers/body and write the true value. Pre-request estimate prevents overspend; post-response reconcile ensures accuracy.
  4. Soft and hard limits: at 80% of budget, reduce max_tokens to limit output. At 100%, reject all requests.
  5. Cost-weighted quotas by user tier: free tier gets 100K tokens/day; pro tier gets 2M tokens/day.
  6. Anomaly detection: alert when any entity exceeds 3x their 7-day rolling average spend in a single hour — catches both runaway automation and credential compromise.
