1. Why Evals Are the Foundation

Evals Are the Unit Tests of AI — But Harder

In traditional software, a function either returns the right value or it doesn't. In LLM systems, "correct" is often a spectrum. An answer can be factually accurate but poorly formatted, well-structured but hallucinated, or faithful to context but missing the point. This is why evals require purpose-built infrastructure.

The central thesis of LLM engineering is: "If you don't have evals, you are guessing." Every prompt change, model upgrade, or retrieval tweak either improves or regresses quality. Without automated measurement, engineers fly blind.

The Cost of Missing Evals

  • Random walks: Prompt engineering without evals means you can't tell if change A helped or hurt. Teams end up reverting changes because "it felt worse."
  • Silent regressions: A new model version silently degrades your use case. You find out from customer complaints three weeks later.
  • Unscalable code review: Human reviewing every LLM output doesn't scale past early prototypes.
  • No deployment confidence: You can't give stakeholders a signal that "this release is better than the last."

The Eval-Driven Development Loop

Industry Practice: Teams at Anthropic, OpenAI, and Google DeepMind maintain eval suites with hundreds to thousands of test cases per product feature. Prompt changes that don't improve any eval are generally not deployed, regardless of how good they seem subjectively.

2. Eval Taxonomy

Complete Classification of Evaluation Approaches

Offline vs Online Evals

Offline evals run on static datasets before deployment. They are fast, cheap, and reproducible. Think of them as integration tests that gate releases. Online evals run on live production traffic — either synchronously (adding latency) or asynchronously (sampled, post-response). Online evals catch distribution shift and real-user edge cases that offline datasets miss.

PropertyOffline EvalsOnline Evals
When to runPre-deployment, CI/CDProduction traffic
DatasetCurated, versioned golden setSampled live queries
SpeedBatch, parallelReal-time or async
Cost controlFull controlNeeds sampling strategy
CatchesKnown failure modesNovel edge cases, distribution drift
ToolsDeepEval, Promptfoo, pytestLangSmith, Braintrust, Langfuse

Deterministic vs Probabilistic Metrics

Deterministic metrics produce the same result on every run (exact match, BLEU, ROUGE, regex checks). They're fast and free but brittle — a correct paraphrase scores 0 on exact match. Probabilistic metrics use model inference (LLM-as-judge, embedding similarity) and have variance. Running the same eval twice may give slightly different scores.

Reference-Based vs Reference-Free

  • Reference-based: Compare model output against a known-good "gold" answer. Requires labeled data. Examples: BLEU, ROUGE, exact match, BERTScore.
  • Reference-free: Evaluate output quality without a gold standard. Examples: coherence scoring, factual consistency checking, toxicity classifiers. Essential when ground truth is unavailable or too expensive to produce.

Pointwise vs Pairwise vs Listwise

  • Pointwise: Score a single response on a scale (1–5). Simple and parallelizable. Suffers from scale calibration issues.
  • Pairwise: Compare two responses and pick the better one. More reliable signal; used by RLHF and LLM-as-judge benchmarks. Does not scale to large candidate sets.
  • Listwise: Rank a list of N responses. Used in NDCG for retrieval. Computationally expensive but provides a full ordering.

3. RAG Evaluation: The RAGAS Framework

Measuring RAG Quality Across All Dimensions

RAGAS (Retrieval-Augmented Generation Assessment) is the canonical framework for evaluating RAG pipelines end-to-end. It decomposes RAG quality into four orthogonal metrics that together cover both retrieval and generation failure modes.

Faithfulness

Faithfulness measures whether each claim in the generated answer is supported by the retrieved context. A faithfulness score of 1.0 means every statement in the answer can be traced back to the provided chunks. A low score is the primary indicator of hallucination.

How it's computed: The judge LLM extracts atomic claims from the answer, then checks each claim against the retrieved context. Score = (supported claims) / (total claims).

Common failure patterns: (1) LLM "fills in" plausible-sounding details not in context; (2) LLM conflates information from two different documents; (3) Retrieved context is technically relevant but lacks the specific fact needed, so the LLM invents it.

Answer Relevancy

Answer relevancy asks: does the generated answer address the original question? A high-faithfulness but low-relevancy answer might correctly quote from context but answer a different question than was asked. This catches prompt engineering failures where the model "responds to context" rather than "responds to the user."

How it's computed: The judge generates N reverse questions from the answer ("what question would this answer be a good response to?"), then computes embedding cosine similarity between those reverse questions and the original question. High similarity = high relevancy.

Context Precision

Context precision measures signal-to-noise in the retrieved chunks. If you retrieve 10 chunks but only 2 are relevant to answering the question, context precision is low. Low precision wastes context window space, increases cost, and can confuse the LLM with irrelevant information (the "lost in the middle" problem).

Formula: For each position k, compute precision@k × relevance(k), then average over all relevant chunks. This is essentially a mean average precision (MAP) adapted for RAG.

Context Recall

Context recall measures whether the retriever found all the chunks needed to answer the question. You need ground-truth annotations (which chunks are needed) or an LLM that judges whether the expected answer could be derived from the retrieved context.

How it's computed: Each sentence in the ground-truth answer is checked against the retrieved context. Score = (sentences attributable to context) / (total expected answer sentences).

RAGAS Evaluation Pipeline — Python Code

# pip install ragas langchain openai chromadb
from ragas import evaluate
from ragas.metrics import (
    faithfulness,
    answer_relevancy,
    context_precision,
    context_recall,
)
from datasets import Dataset
from langchain_openai import ChatOpenAI, OpenAIEmbeddings

# Step 1: Prepare your eval dataset
# Each record needs: question, answer (generated), contexts (retrieved), ground_truth
eval_data = {
    "question": [
        "What is the capital of France?",
        "How does RLHF work?",
        "What is RAG and when should I use it?",
    ],
    "answer": [
        # These come from your RAG pipeline during eval run
        "The capital of France is Paris.",
        "RLHF stands for Reinforcement Learning from Human Feedback. It involves collecting "
        "human preference data on model outputs, training a reward model on those preferences, "
        "then fine-tuning the LLM using RL to maximize the reward signal.",
        "RAG (Retrieval-Augmented Generation) combines a retrieval system with a language model. "
        "Use RAG when: your knowledge base changes frequently, you need citations, or the domain "
        "is too large to fine-tune on.",
    ],
    "contexts": [
        # Lists of retrieved text chunks
        ["France is a country in Western Europe. Its capital and largest city is Paris."],
        [
            "RLHF involves three phases: supervised fine-tuning, reward modeling from human "
            "preferences, and RL optimization (usually PPO) against the reward model.",
            "Human labelers rank pairs of model outputs; the reward model learns to predict "
            "these rankings.",
        ],
        [
            "RAG augments LLMs with external retrieval. It is most useful when knowledge "
            "currency, traceability, and domain breadth matter more than latency.",
            "Fine-tuning is better when style/format consistency is the goal; RAG is better "
            "for factual grounding.",
        ],
    ],
    "ground_truth": [
        "Paris is the capital of France.",
        "RLHF collects human preference labels, trains a reward model, then uses RL to optimize "
        "the LLM policy to maximize reward.",
        "RAG retrieves relevant documents at inference time to ground LLM outputs. Prefer RAG "
        "when the knowledge base is large, dynamic, or requires sourcing.",
    ],
}

dataset = Dataset.from_dict(eval_data)

# Step 2: Configure judge LLM and embeddings
judge_llm = ChatOpenAI(model="gpt-4o", temperature=0)
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

# Step 3: Run RAGAS evaluation
result = evaluate(
    dataset=dataset,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
    llm=judge_llm,
    embeddings=embeddings,
)

print(result)
# Output example:
# {'faithfulness': 0.9167, 'answer_relevancy': 0.8823,
#  'context_precision': 0.8333, 'context_recall': 0.8667}

# Step 4: Export to pandas for analysis
df = result.to_pandas()
# Drill into low-scoring cases
failures = df[df["faithfulness"] < 0.7]
print(f"Faithfulness failures: {len(failures)} / {len(df)}")
for _, row in failures.iterrows():
    print(f"  Q: {row['question']}")
    print(f"  A: {row['answer'][:100]}...")
    print(f"  Score: {row['faithfulness']:.2f}")

Interpreting RAGAS Scores

  • > 0.85: Good — monitor for drift but no immediate action needed
  • 0.70 – 0.85: Acceptable for early-stage; invest in improvement
  • 0.50 – 0.70: Problematic — users will notice quality issues
  • < 0.50: Broken — do not deploy; fix the identified dimension first
⚠️
RAGAS Limitation: RAGAS itself uses LLM calls to compute metrics, which means scores are only as reliable as your judge model. Always validate RAGAS scores against a human-annotated sample (50–100 examples) when first deploying. GPT-4o-based RAGAS scores typically correlate ~0.7–0.8 with expert human judgments.

DeepEval — pytest-Style LLM Evals

DeepEval maps LLM evaluation onto the familiar pytest pattern. Each test case defines input, actual output, retrieved context (for RAG), and expected output. Metrics are classes that implement a measure() method and return a score + reason. 

# pip install deepeval
import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase, LLMTestCaseParams
from deepeval.metrics import (
    FaithfulnessMetric,
    AnswerRelevancyMetric,
    ContextualRecallMetric,
    HallucinationMetric,
    ToxicityMetric,
    GEval,
)

# Define a custom G-Eval metric (rubric-based)
conciseness_metric = GEval(
    name="Conciseness",
    criteria="The response answers the question without unnecessary verbosity. "
             "It does not repeat the question back or pad with filler phrases.",
    evaluation_params=[LLMTestCaseParams.ACTUAL_OUTPUT, LLMTestCaseParams.INPUT],
    minimum_score=0.7,
)

@pytest.mark.parametrize("test_case", [
    LLMTestCase(
        input="What is RAG?",
        actual_output=my_rag_pipeline("What is RAG?"),
        expected_output="RAG combines retrieval with generation to ground LLM outputs.",
        retrieval_context=[
            "RAG (Retrieval-Augmented Generation) uses a retriever to fetch relevant "
            "documents and a generator to produce answers grounded in those documents."
        ],
    ),
    LLMTestCase(
        input="Explain the transformer architecture",
        actual_output=my_rag_pipeline("Explain the transformer architecture"),
        expected_output="Transformers use self-attention to process sequences in parallel.",
        retrieval_context=[
            "The transformer model introduced by Vaswani et al. (2017) uses multi-head "
            "self-attention and feed-forward layers to process input sequences in parallel."
        ],
    ),
])
def test_rag_quality(test_case: LLMTestCase):
    assert_test(test_case, [
        FaithfulnessMetric(threshold=0.8, model="gpt-4o-mini"),
        AnswerRelevancyMetric(threshold=0.75, model="gpt-4o-mini"),
        ContextualRecallMetric(threshold=0.7, model="gpt-4o-mini"),
        HallucinationMetric(threshold=0.2, model="gpt-4o-mini"),  # lower is better
        conciseness_metric,
    ])

# Run: deepeval test run test_rag.py
# Output includes per-metric scores, reasons, and pass/fail status

5. LLM-as-Judge

Using a Strong Model to Evaluate a Weaker Model

LLM-as-Judge is the technique of using a capable frontier model (e.g., GPT-4o, Claude 3.5 Sonnet) to evaluate the output of another model. It scales better than human annotation and handles open-ended text better than deterministic metrics. The key insight is that evaluating quality is easier than generating quality — a smaller model can produce mediocre answers, but GPT-4o can reliably identify that they're mediocre.

Judge Prompt Engineering: Rubrics, Scales, and Examples

The quality of your judge is only as good as your judge prompt. Vague instructions produce noisy scores. A production-grade judge prompt should include:

  • Clear task description: Precisely what the evaluated model was asked to do
  • Scoring rubric: Each score level defined with explicit, distinct criteria
  • Few-shot examples: 2–3 (question, answer, score, reasoning) examples per score level
  • Chain-of-thought: Ask the judge to reason before scoring ("Think step by step, then output your score")
  • Structured output: JSON with score and reasoning fields

Example LLM Judge Implementation

import json
from openai import OpenAI
from typing import Optional

client = OpenAI()

JUDGE_SYSTEM_PROMPT = """You are an expert evaluator for AI assistant responses.
Evaluate the given response on FAITHFULNESS to the provided context.

Faithfulness measures whether every factual claim in the response is supported
by the provided context. Do not penalize for what the context doesn't say —
only penalize for claims that contradict or go beyond the context.

Scoring Rubric:
  5 - All claims directly supported by context. No unsupported additions.
  4 - Nearly all claims supported; one minor inference not explicitly in context.
  3 - Most claims supported but 1-2 clear additions beyond context.
  2 - Several claims lack context support; significant extrapolation.
  1 - Response largely ignores or contradicts the context; severe hallucination.

Output ONLY valid JSON: {"score": <int 1-5>, "reasoning": "<brief explanation>", "violations": ["<specific unsupported claim>"]}
"""

def judge_faithfulness(
    question: str,
    context: str,
    response: str,
    model: str = "gpt-4o",
) -> dict:
    user_message = f"""QUESTION: {question}

CONTEXT:
{context}

RESPONSE TO EVALUATE:
{response}"""

    completion = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": JUDGE_SYSTEM_PROMPT},
            {"role": "user",   "content": user_message},
        ],
        temperature=0,           # Deterministic scores
        response_format={"type": "json_object"},
        seed=42,                 # Reproducibility
    )

    result = json.loads(completion.choices[0].message.content)
    result["normalized_score"] = (result["score"] - 1) / 4  # 0.0 - 1.0
    return result

# Usage
result = judge_faithfulness(
    question="What is the boiling point of water?",
    context="Water boils at 100°C (212°F) at sea level. At higher altitudes, the boiling point decreases.",
    response="Water boils at 100°C at sea level. At high altitude, it boils at a lower temperature, "
             "which is why cooking times increase. Additionally, adding salt raises the boiling point slightly.",
)
# result: {"score": 3, "normalized_score": 0.5,
#  "reasoning": "First two claims are supported. Salt claim not in context.",
#  "violations": ["adding salt raises the boiling point slightly"]}

Position Bias and Mitigation

LLM judges show position bias in pairwise evaluation: when comparing Response A vs B, the judge often favors whichever response appears first in the prompt. Studies (Wang et al., 2023; Zheng et al., 2023) found GPT-4 has a ~10–15% position bias toward the first response.

Mitigation strategies:

  • Swap and average: Run pairwise eval twice with order swapped (A vs B, then B vs A). Only declare a winner when both agree.
  • Balanced ordering: Across your eval dataset, randomize which model appears first.
  • Chain-of-thought before verdict: Force the judge to reason extensively before declaring a winner — this reduces snap position-based judgments.
  • Calibration examples: Include examples in the system prompt that demonstrate the judge should not favor based on order.

Multi-Judge Agreement (Inter-Rater Reliability)

When a single judge LLM is insufficient (high-stakes decisions, catching judge bias), run multiple independent judges and aggregate. Common patterns:

  • Majority vote: 3 judges, take the majority score. Works well for binary or coarse ratings.
  • Average: Average continuous scores from N judges. Use standard deviation as a confidence indicator.
  • Escalate disagreements: When judges disagree by more than 1 point, route to human review or a stronger judge model.
  • Cross-model validation: Use GPT-4o as one judge and Claude 3.5 Sonnet as another — reduces model-family-specific biases.

When LLM-as-Judge Fails

🚫
Do NOT rely solely on LLM-as-judge when: (1) Evaluating safety-critical outputs (medical, legal) where the judge itself can miss subtle errors; (2) Evaluating code correctness — execution-based evals are ground truth; (3) Evaluating highly technical domains where GPT-4o has known knowledge gaps; (4) The evaluated model is stronger than your judge model.
  • Sycophancy: The judge favors verbose, confident-sounding answers over correct but brief ones.
  • Self-preference bias: GPT-4o tends to rate GPT-4o outputs higher; use a different model family to cross-validate.
  • Verbosity bias: Longer responses tend to score higher regardless of quality. Normalize by asking "is this response appropriately concise?"
  • Recency bias: In long responses, the judge over-weights the final paragraphs.

6. Human Eval Workflows

When You Need Humans, How to Structure It

When Human Evaluation is Irreplaceable

  • Safety and policy evaluation: Determining if output violates guidelines requires nuanced human judgment that LLMs reliably get wrong in edge cases.
  • Subjective quality dimensions: "Does this feel natural?", "Would a real customer find this helpful?" — humans are the ground truth.
  • Calibrating automated evaluators: Before deploying LLM-as-judge, validate against 100+ human-annotated examples to measure agreement.
  • Novel task types: When you don't yet have a reliable automated evaluator for a new capability.
  • Legal/medical/financial outputs: High-stakes domains where automated eval errors have real consequences.

Annotation Guidelines and Rubrics

High-quality human evals require investment in annotation infrastructure. The leading cause of poor human eval data is ambiguous guidelines that different annotators interpret differently. A production annotation rubric should include:

  • Task-specific criteria — not generic "is this good?" but "does this answer the original question AND stay within the provided context?"
  • Clear scale anchors — written descriptions of what a 1, 3, and 5 mean for this specific task
  • Positive and negative examples — 3–5 examples per score level, annotated with reasoning
  • Edge case guidance — explicit rules for common ambiguous cases
  • Conflict resolution protocol — what happens when annotators disagree

Inter-Annotator Agreement (IAA)

IAA measures how consistently different annotators rate the same samples. Low IAA means your task is ambiguous, your rubric is unclear, or your annotators need more training. 

from sklearn.metrics import cohen_kappa_score
import numpy as np
# krippendorff available via pip install krippendorff
import krippendorff

# Annotator ratings for 20 examples (scale 1-5)
annotator_1 = [5, 4, 3, 5, 2, 4, 5, 3, 4, 5, 2, 3, 4, 5, 1, 4, 3, 5, 4, 3]
annotator_2 = [5, 4, 4, 5, 2, 3, 5, 3, 4, 4, 2, 3, 4, 5, 1, 4, 4, 5, 4, 3]
annotator_3 = [4, 3, 3, 5, 3, 4, 5, 2, 4, 5, 1, 3, 5, 5, 1, 3, 3, 4, 4, 2]

# Cohen's Kappa (pairwise; handles chance agreement)
kappa_1_2 = cohen_kappa_score(annotator_1, annotator_2, weights='quadratic')
kappa_1_3 = cohen_kappa_score(annotator_1, annotator_3, weights='quadratic')
print(f"Kappa(A1, A2): {kappa_1_2:.3f}")  # 0.6-0.8 is substantial agreement
print(f"Kappa(A1, A3): {kappa_1_3:.3f}")

# Krippendorff's Alpha (multi-annotator; handles ordinal scales)
# ratings_matrix: rows=annotators, cols=examples
ratings_matrix = np.array([annotator_1, annotator_2, annotator_3], dtype=float)
alpha = krippendorff.alpha(reliability_data=ratings_matrix, level_of_measurement='ordinal')
print(f"Krippendorff's Alpha: {alpha:.3f}")
# Alpha interpretation:
#   > 0.80: High reliability, annotation can proceed
#   0.67 - 0.80: Acceptable; review ambiguous cases
#   0.50 - 0.67: Low; revise guidelines before proceeding
#   < 0.50: Unreliable; guidelines need major overhaul

Hybrid Human-LLM Eval Pipelines

Most production systems use a tiered approach to balance cost and quality:

Step 1
Automated filters (free): Exact match, regex, length checks. Filter out obvious failures before spending on LLM eval.
Step 2
LLM-as-judge (cheap): Run all remaining examples through a fast judge model (GPT-4o-mini). Flag cases where score < 0.5 or score is in ambiguous range (e.g., 0.45–0.65).
Step 3
Strong model re-eval (moderate): Re-evaluate flagged cases with a stronger judge (GPT-4o, Claude 3.5 Sonnet). Often resolves ambiguity without needing humans.
Step 4
Human review (expensive, targeted): Route only high-stakes or still-ambiguous cases to human annotators. Typically <5% of total volume.
Step 5
Feedback loop: Human annotations become training data for improving the judge model or go into the golden dataset for future automated evals.

Eval Dataset as Versioned Artifacts

Your eval dataset is as important as your code. Treat it like a software artifact:

  • Version control: Store datasets in git (for small sets) or DVC/S3 with a manifest file in git (for large sets).
  • Immutable snapshots: Never mutate an existing eval version; create a new version. This preserves reproducibility of historical scores.
  • Diverse coverage: Ensure your golden set covers: common cases (60%), edge cases (25%), adversarial inputs (15%).
  • Drift monitoring: Periodically compare live traffic distribution against your eval dataset. If they diverge significantly, update the dataset.

Regression Detection: Comparing Against Baseline

import json
import sys
from typing import Any

def check_regressions(
    current_scores: dict[str, float],
    baseline_scores: dict[str, float],
    threshold: float = 0.05,  # 5% regression is a fail
    strict_metrics: list[str] | None = None,
) -> tuple[bool, list[str]]:
    """
    Returns (passed, list_of_failures).
    strict_metrics: metrics where ANY regression (even 1%) fails the gate.
    """
    if strict_metrics is None:
        strict_metrics = ["faithfulness"]  # Safety-critical metric

    failures = []
    for metric, current in current_scores.items():
        if metric not in baseline_scores:
            continue
        baseline = baseline_scores[metric]
        drop = baseline - current

        if metric in strict_metrics and drop > 0.01:
            failures.append(
                f"{metric}: STRICT FAIL — dropped {drop*100:.1f}% "
                f"({baseline*100:.1f}% -> {current*100:.1f}%)"
            )
        elif drop > threshold:
            failures.append(
                f"{metric}: FAIL — dropped {drop*100:.1f}% "
                f"({baseline*100:.1f}% -> {current*100:.1f}%) "
                f"[threshold: {threshold*100:.0f}%]"
            )

    return len(failures) == 0, failures

8. Regression Testing for Prompts

Prompt Versioning, Golden Datasets, A/B Testing

Prompt Versioning Strategies

Prompts are code. They need versioning, review, and testing. The naive approach (embed prompts as strings in application code) leads to untested changes and no auditability.

  • File-based versioning: Store prompts as .txt or .jinja2 files in a prompts/ directory, committed to git. Use semantic versioning in filenames: customer-support-v2.3.0.jinja2.
  • Prompt registries: Tools like Langfuse, LangSmith, and Promptlayer provide hosted prompt management with version history, A/B assignment, and analytics.
  • Environment-specific deployment: Tag prompts with environments (dev/staging/prod). Only promote a prompt version after it passes the full eval suite in each environment.

Golden Dataset Management

A golden dataset is a curated collection of (input, expected_output) pairs that represent the "north star" quality your system should achieve. Building and maintaining it is ongoing work.

  • Seed from failures: Every time a bug is found in production, add it to the golden set. This prevents regressions of bugs you've already fixed.
  • Coverage criteria: Ensure the dataset covers all major use cases proportionally. Avoid datasets that are 80% easy examples — they make every model look good.
  • Freshness: Update the golden set when your product changes, new features are added, or user distribution shifts significantly.
  • Metadata tagging: Tag each example with category, difficulty, and source (user-submitted, synthetic, adversarial). This enables targeted analysis.

def assign_prompt_version(
    user_id: str,
    experiment_name: str,
    treatment_fraction: float = 0.1,
) -> PromptVersion:
    """
    Deterministic assignment: same user always gets same variant.
    Uses hashing so assignment is consistent across requests.
    """
    key = f"{experiment_name}:{user_id}".encode()
    hash_val = int(hashlib.md5(key).hexdigest(), 16)
    bucket = hash_val % 100
    return "treatment" if bucket < (treatment_fraction * 100) else "control"

Statistical Significance for Eval Comparisons

With a 100-example eval set, a 2% improvement could be noise. Use statistical testing before declaring a winner: 

from scipy import stats
import numpy as np

def compare_prompt_versions(
    control_scores: list[float],
    treatment_scores: list[float],
    alpha: float = 0.05,
) -> dict:
    """
    Paired t-test for comparing two prompt versions on the same eval set.
    Use paired test because we're comparing same examples across versions.
    """
    t_stat, p_value = stats.ttest_rel(treatment_scores, control_scores)
    effect_size = (np.mean(treatment_scores) - np.mean(control_scores)) / np.std(control_scores)

    return {
        "control_mean":   np.mean(control_scores),
        "treatment_mean": np.mean(treatment_scores),
        "absolute_delta": np.mean(treatment_scores) - np.mean(control_scores),
        "relative_delta": (np.mean(treatment_scores) - np.mean(control_scores)) / np.mean(control_scores),
        "p_value":        p_value,
        "significant":    p_value < alpha,
        "cohens_d":       effect_size,
        "recommendation": (
            "Deploy treatment" if (p_value < alpha and np.mean(treatment_scores) > np.mean(control_scores))
            else "Keep control" if p_value < alpha
            else "Inconclusive — need more data"
        ),
    }

# Rule of thumb: need ~100 examples for 5% difference to be detectable at p<0.05

Dataset Creation and Curation

Building your initial golden dataset is the hardest part of setting up evals. Most teams underinvest here and end up with datasets that are too easy, too narrow, or not representative of real usage.

  1. Harvest from production logs (Week 1): Sample 500–1000 real user queries. Label the ones your current system handles well as "positive examples" and the ones it gets wrong as "known failures."
  2. Expert curation (Week 1-2): Have domain experts review samples and write gold-standard answers for 100–200 examples. These are your most valuable evaluation points.
  3. Synthetic expansion (Week 2-3): Use an LLM to generate additional examples based on your real examples. Critically review synthetic examples — they can be biased toward what the LLM finds "typical."
  4. Adversarial injection (Week 3-4): Use red-teaming tools (Promptfoo, Garak) to generate adversarial inputs: prompt injections, jailbreaks, edge cases, boundary violations.
  5. Ongoing maintenance: Set a standing process to add 5–10 new examples per week from production failures or newly discovered edge cases.

"""
eval/run_eval.py — Complete eval pipeline runner
Usage: python eval/run_eval.py --dataset golden-set-v3.json --output results.json
"""
import asyncio
import json
import time
import argparse
from pathlib import Path
from typing import Any
from dataclasses import dataclass, asdict

from openai import AsyncOpenAI
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall
from datasets import Dataset

@dataclass
class EvalResult:
    question: str
    generated_answer: str
    contexts: list[str]
    ground_truth: str
    faithfulness: float
    answer_relevancy: float
    context_precision: float
    context_recall: float
    latency_ms: float

async def run_pipeline(question: str, client: AsyncOpenAI) -> tuple[str, list[str], float]:
    """Your actual RAG pipeline. Returns (answer, contexts, latency_ms)."""
    start = time.monotonic()
    # --- Replace with your pipeline ---
    contexts = await retrieve_chunks(question)
    answer   = await generate_answer(question, contexts, client)
    # ----------------------------------
    latency_ms = (time.monotonic() - start) * 1000
    return answer, contexts, latency_ms

async def evaluate_dataset(
    dataset_path: str,
    output_path: str,
    max_concurrency: int = 5,
) -> dict[str, float]:

    client = AsyncOpenAI()
    examples = json.loads(Path(dataset_path).read_text())

    semaphore = asyncio.Semaphore(max_concurrency)
    raw_results = []

    async def process_one(example: dict) -> EvalResult | None:
        async with semaphore:
            try:
                answer, contexts, latency = await run_pipeline(
                    example["question"], client
                )
                return {
                    "question":  example["question"],
                    "answer":    answer,
                    "contexts":  contexts,
                    "ground_truth": example["ground_truth"],
                    "latency_ms":   latency,
                }
            except Exception as e:
                print(f"Pipeline error for '{example['question'][:50]}': {e}")
                return None

    tasks = [process_one(ex) for ex in examples]
    raw_results = [r for r in await asyncio.gather(*tasks) if r is not None]

    # Run RAGAS scoring
    ds = Dataset.from_list([{
        "question":     r["question"],
        "answer":       r["answer"],
        "contexts":     r["contexts"],
        "ground_truth": r["ground_truth"],
    } for r in raw_results])

    scores = evaluate(ds, metrics=[faithfulness, answer_relevancy, context_precision, context_recall])

    # Merge scores into results
    score_dict = scores.to_pandas().to_dict(orient="records")
    for i, row in enumerate(score_dict):
        raw_results[i].update(row)

    # Aggregate
    aggregate = {
        "faithfulness":       float(scores["faithfulness"]),
        "answer_relevancy":   float(scores["answer_relevancy"]),
        "context_precision":  float(scores["context_precision"]),
        "context_recall":     float(scores["context_recall"]),
        "avg_latency_ms":     sum(r["latency_ms"] for r in raw_results) / len(raw_results),
        "n_examples":         len(raw_results),
        "n_failed":           len(examples) - len(raw_results),
        "timestamp":          time.time(),
    }

    Path(output_path).write_text(json.dumps({
        "aggregate": aggregate,
        "per_example": raw_results,
    }, indent=2))

    return aggregate

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--dataset",  required=True)
    parser.add_argument("--output",   required=True)
    parser.add_argument("--baseline", default=None)
    parser.add_argument("--fail-threshold", type=float, default=0.05)
    args = parser.parse_args()

    scores = asyncio.run(evaluate_dataset(args.dataset, args.output))
    print(json.dumps(scores, indent=2))

                print(f"REGRESSION: {f}")

10. Staff-Level Interview Angle

How to Discuss Evals at the Staff Level

At the staff level, interviewers don't just want to know what RAGAS metrics mean — they want to see that you can design eval infrastructure for a system, reason about tradeoffs in eval strategy, and advocate for eval investment across an organization.

System Design Question: "How would you build evals for a new AI feature?"

A strong staff-level answer demonstrates a deliberate, phased approach rather than jumping to a specific framework. Structure your answer around:

  1. Define success criteria first: "Before choosing metrics, I'd work with product and users to define what 'good' means for this feature. For a support chatbot, that's answer correctness, tone, and task completion rate — not just ROUGE."
  2. Build a tiered eval stack: Deterministic checks → embedding similarity → LLM-as-judge → human spot checks. Each tier is a fallback for the ones above it.
  3. Start small, automate fast: "I'd start with 50 handcrafted golden examples and get automated evals running in CI within the first sprint. Growing the dataset is easier than building the pipeline."
  4. Treat eval data as a product artifact: "The golden dataset gets versioned, reviewed in PRs, and owned by the team — just like the model config."
  5. Connect evals to business metrics: "RAGAS faithfulness of 0.85 means nothing to a PM. I'd run calibration studies showing 'faithfulness below 0.7 correlates with 15% higher escalation rate.' That makes eval investment concrete."

Tradeoff Questions to Expect

  • "When would you choose LLM-as-judge over human evaluation?" For volume (>1000 examples), speed (CI pipelines), and low-stakes domains. For safety, medical, or when your judge is weaker than the evaluated model, prefer humans.
  • "How do you prevent your eval from overfitting to your golden dataset?" Separate development eval set (for iteration) from a hold-out test set (never used for prompt tuning). Periodically sample new examples from production to refresh both sets.
  • "Your eval suite runs for 45 minutes in CI. How do you fix this?" Tier the eval: a fast tier (deterministic, <30s) runs on every PR; the full LLM eval suite runs only on changes to prompt files or pipeline config. Cache LLM responses during development.
  • "What do you do when human evaluators and your LLM judge disagree?" Human judgment is ground truth. Investigate the systematic disagreements to understand the judge's failure modes. Update the judge prompt or calibrate the threshold. If disagreement is above 15%, the judge is unreliable for that dimension.

What Strong Candidates Demonstrate

  • They know that evals are infrastructure, not an afterthought
  • They quantify uncertainty — "this metric has X% agreement with human judgment on our dataset"
  • They tie technical metrics to user-observable or business outcomes
  • They have opinions on when NOT to use LLM-as-judge
  • They've thought about how to grow and maintain a golden dataset over time
  • They understand the difference between measuring improvement and proving statistical significance

11. Active Recall

Test your understanding. Click each question to reveal the answer.

What do the four RAGAS metrics each measure, and which failure mode does each one catch?
Faithfulness measures whether every claim in the answer is supported by retrieved context — it catches hallucination. Answer Relevancy checks if the answer actually addresses the question — it catches cases where the model "answers the context" rather than the user. Context Precision measures signal-to-noise in retrieved chunks — it catches a noisy retriever that returns many irrelevant chunks. Context Recall measures whether all needed information was retrieved — it catches a retriever that misses relevant documents. All four are needed because a RAG system can fail at each stage independently.
What is position bias in LLM-as-judge, and what are two concrete mitigation techniques?
Position bias is the tendency of an LLM judge to favor whichever response appears first in a pairwise comparison prompt, regardless of actual quality. Studies found GPT-4 has ~10–15% position bias toward Response A. Two mitigations: (1) Swap and average — run the eval twice with A/B order swapped; only declare a winner when both orderings agree. (2) Force chain-of-thought before verdict — require the judge to reason extensively about both responses before declaring a winner, which reduces snap position-based judgments. A third useful practice is randomizing which model appears first across the eval dataset.
When should you use offline evals vs online evals, and what does each catch that the other misses?
Offline evals run pre-deployment on curated static datasets. They catch known failure modes, prevent regressions, and block bad deploys. They miss: novel user behaviors, distribution drift, and real-world edge cases you didn't think to include in your golden set. Online evals run on live production traffic (sampled asynchronously). They catch distribution shift, real user edge cases, and failure modes that don't appear in your curated dataset. They miss: pre-deployment regressions (by definition, since the code is already live). Best practice: use offline evals as CI gates, online evals as continuous quality monitors with alerting.
Explain the difference between context precision and context recall in RAG evaluation. If context precision is low but context recall is high, what does that tell you about the retriever?
Context precision = of the chunks retrieved, how many are actually relevant to answering the question (precision / signal-to-noise). Context recall = of the chunks needed to answer the question, how many were actually retrieved (coverage). If context precision is low but context recall is high, the retriever is finding all the right chunks but also retrieving many irrelevant chunks alongside them. This pattern points to a re-ranking problem — the retriever is too broad, and you need a re-ranker (cross-encoder, Cohere Rerank, etc.) to filter the candidate set before passing it to the LLM. Low context recall with high context precision suggests a retrieval coverage problem — the retriever is precise but missing documents, often due to embedding model limitations or chunking strategy issues.
What is Krippendorff's Alpha and when would you use it over Cohen's Kappa?
Both are inter-annotator agreement statistics. Cohen's Kappa is pairwise (two annotators) and handles chance-corrected agreement; it's easy to compute but doesn't generalize to multiple annotators without averaging. Krippendorff's Alpha handles multiple annotators simultaneously, handles ordinal/interval/ratio scales appropriately, and handles missing data (not all annotators must rate every example). Use Krippendorff's Alpha when: you have 3+ annotators, your rating scale is ordinal (like 1–5 quality scores), or you have incomplete annotation data. Use Cohen's Kappa for quick pairwise reliability checks or when annotators annotate every example. Acceptable IAA thresholds: Alpha > 0.80 is high reliability; 0.67–0.80 is acceptable; below 0.67 suggests the rubric needs revision.
You're running a prompt A/B test with 80 examples. The treatment prompt scores 2% higher on faithfulness. Can you ship it?
No — not without statistical validation. A 2% improvement on 80 examples is very likely to be within normal statistical noise. You need to run a paired t-test (or Wilcoxon signed-rank test for non-normal distributions) to determine p-value. With n=80 and a 2% effect size (small Cohen's d ≈ 0.2), you likely won't achieve p < 0.05 — you'd typically need ~200+ examples to detect a 2% difference reliably. Options: (1) Collect more eval examples until you have sufficient power, (2) Ship as a cautious A/B in production with 10% traffic and monitor online metrics for a week, (3) Accept the change anyway if the improvement is consistent across ALL metrics and the absolute risk of regression is low. Never ship based on a single marginally-better metric without significance testing.

Create a 50-example golden dataset from production logs. Each record: question, retrieved contexts, ground truth answer, metadata (category, difficulty). Write a Python script that samples from real logs and exports to JSON. Target: at least 5 categories, 10 adversarial examples.
M2
RAGAS Baseline (Day 2–3)
Run RAGAS on your golden dataset against the current embedding model. Record baseline scores for all four metrics. Identify the bottom 10 examples by faithfulness — analyze what the common failure pattern is (hallucination type, missing context, etc.).
M3
LLM-as-Judge Integration (Day 3–4)
Implement a custom judge metric for "answer completeness" — does the answer address all parts of a multi-part question? Write a rubric, implement judge_completeness(), and validate it against 20 human-annotated examples (target: > 0.7 correlation with human scores).
M4
CI Gate (Day 4–5)
Implement a GitHub Actions workflow that: (1) runs the eval suite on any PR touching config/embedding_model.yaml, (2) compares against baseline, (3) fails the PR if faithfulness drops more than 3%, (4) posts a score summary comment on the PR.
M5
Reporting Dashboard (Day 5–7)
Build a simple HTML dashboard (or Braintrust project) showing: current vs baseline scores per metric, per-category breakdown, top-5 worst-performing examples with their scores and judge explanations, and a trend line over the last 10 eval runs.
BONUS
Online Eval Sampling
Add an async background task that samples 1% of production queries, runs faithfulness scoring via LLM-as-judge, and writes results to a time-series database (InfluxDB or CloudWatch). Alert when 7-day rolling faithfulness drops below 0.75.

Evaluation Criteria

  • Does your golden dataset have balanced coverage and adversarial examples?
  • Is the LLM judge validated against human annotations?
  • Does the CI gate correctly block regressions and pass improvements?
  • Can you explain any metric score in terms a non-engineer would understand?
  • Is the eval pipeline fast enough to run in < 10 minutes in CI?

13. Flashcard Suggestions

Export these to Anki, use them for spaced repetition, or quiz a colleague.

Q: What are the four RAGAS metrics and what does each measure?
Faithfulness (hallucination detection — are claims grounded in context?), Answer Relevancy (does the answer address the question?), Context Precision (signal-to-noise of retrieved chunks), Context Recall (did retrieval find all needed chunks?).
Q: What is position bias in LLM-as-judge and how do you mitigate it?
The judge systematically favors the response in the first position (~10–15% bias in GPT-4). Mitigate by: (1) swap-and-average — run twice with swapped order; (2) chain-of-thought before verdict; (3) randomize position assignment across dataset.
Q: What is Krippendorff's Alpha and when does it beat Cohen's Kappa?
A multi-annotator, scale-aware agreement statistic. Better than Cohen's Kappa when: 3+ annotators, ordinal scales (1–5), or missing annotations. Alpha > 0.80 = high reliability; below 0.67 = revise rubric.
Q: What is the difference between offline and online evals?
Offline: pre-deployment, curated static dataset, runs in CI, catches known failures and regressions. Online: live production traffic (sampled), async, catches distribution shift and novel edge cases. Both are needed; offline gates deploys, online monitors health.
Q: If RAGAS context precision is 0.45 but context recall is 0.90, what is the likely fix?
The retriever is finding all needed chunks (high recall) but also many irrelevant ones (low precision). The fix is a re-ranker (cross-encoder, Cohere Rerank) to filter the candidate set before passing to the LLM — not changing the embedding model.
Q: Name three ways LLM-as-judge can fail systematically.
(1) Sycophancy — favors verbose, confident-sounding answers; (2) Self-preference bias — GPT-4o rates GPT-4o outputs higher; (3) Verbosity bias — longer responses score higher regardless of quality; (4) Position bias in pairwise evals; (5) Domain blindness in highly technical/specialized areas.
Q: How do you determine statistical significance when comparing two prompt versions on an eval set?
Use a paired t-test (same examples run through both versions). Check p-value < 0.05 for significance. For n=100 examples, you can reliably detect ~5% differences. Use power analysis (statsmodels) to determine minimum sample size before running the experiment.
