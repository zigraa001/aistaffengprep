Design: AI Code Assistant (Copilot)

Examples: GitHub Copilot, Cursor, Codeium, Amazon CodeWhisperer

Difficulty: Hard | Time: 45-60 minutes

1. Requirements Clarification

Functional Requirements ▼
  • Inline code completion — predict next lines as user types (ghost text)
  • Chat-based code generation — explain, refactor, generate from natural language
  • Codebase-aware context — understand project structure, imports, types, related files
  • Multi-language support — Python, TypeScript, Java, Go, Rust, etc.
  • Streaming responses — token-by-token for real-time UX
  • Privacy controls — opt-out of telemetry, no training on private repos
Non-Functional Requirements ▼
  • Latency: First token < 200ms for inline completion (TTFT critical)
  • Throughput: Handle 1M+ developers, ~10 completions/minute each
  • Accuracy: Acceptance rate > 30% for inline suggestions
  • Availability: 99.9% — IDE can't hang waiting for completions
  • Cost efficiency: Sub-$0.01 per completion to be viable at $10-20/user/month pricing

2. Scale & Capacity Estimation

Back-of-Envelope Math ▼
User Scale:
- 1M active developers
- Average coding session: 4 hours/day
- ~10 completion triggers/minute while coding
- Many are debounced/cancelled (only ~30% reach backend)

Request Volume:
- Peak: 1M × 3 req/min = 3M req/min = 50K QPS
- Each request: ~2K tokens input context, ~100 tokens output
- 70% are inline completions (fast, small), 30% chat (slower, larger)

Inference Cost:
- Inline: use speculative decoding or smaller model (7B-13B)
- Chat: larger model (70B or GPT-4 class)
- Cost per inline completion: ~$0.001
- Cost per chat request: ~$0.01
- Monthly: ~$3-5M inference cost for 1M users

GPU Fleet:
- 50K QPS with ~50ms/completion = ~2,500 GPU-seconds/sec
- ~800-1,200 A100/H100 GPUs for inference

3. Context Engineering

Building the Perfect Context Window ▼

Context quality is the #1 driver of suggestion accuracy. The challenge: fit the most relevant code into a limited token budget.

Context Sources (Priority Order)

Source Tokens Why
Current file (cursor prefix/suffix) ~800 Immediate context, most relevant
Recently edited files ~400 Related work context
Imported modules/types ~300 Type signatures, API surface
Similar code (embedding search) ~300 Patterns from codebase
LSP diagnostics/errors ~100 Fix-aware suggestions

Fill-in-the-Middle (FIM) Format

Inline completion uses FIM, not standard left-to-right generation:

# FIM prompt format for inline completion
def build_fim_prompt(prefix: str, suffix: str,
                     context_snippets: list[str]) -> str:
    """Build Fill-in-the-Middle prompt for code completion.

    The model sees code BEFORE and AFTER the cursor,
    then generates what goes in between.
    """
    # Repo-level context (snippets from other files)
    repo_context = "\n".join(
        f"# File: {s['path']}\n{s['content']}"
        for s in context_snippets
    )

    return (
        f"<|repo_context|>\n{repo_context}\n"
        f"<|fim_prefix|>{prefix}"
        f"<|fim_suffix|>{suffix}"
        f"<|fim_middle|>"
    )


class ContextBuilder:
    """Assemble optimal context for code completion."""

    def __init__(self, index, lsp_client, max_tokens=2048):
        self.index = index       # Codebase embedding index
        self.lsp = lsp_client    # Language Server Protocol client
        self.max_tokens = max_tokens

    async def build(self, file_path: str, cursor_offset: int,
                    open_files: list[str]) -> dict:
        content = await self._read_file(file_path)
        prefix = content[:cursor_offset]
        suffix = content[cursor_offset:]

        budget = self.max_tokens
        snippets = []

        # 1. Current file prefix/suffix (highest priority)
        prefix_tokens = self._truncate_start(prefix, budget // 2)
        suffix_tokens = self._truncate_end(suffix, budget // 4)
        budget -= len(prefix_tokens) + len(suffix_tokens)

        # 2. Imported type signatures
        imports = await self.lsp.get_imports(file_path)
        for imp in imports[:5]:
            sig = await self.lsp.get_signature(imp)
            if sig and budget > 0:
                snippets.append({"path": imp, "content": sig})
                budget -= self._count_tokens(sig)

        # 3. Recently edited files (recency-weighted)
        for f in open_files[:3]:
            if f != file_path and budget > 100:
                excerpt = await self._get_relevant_excerpt(f, prefix)
                snippets.append({"path": f, "content": excerpt})
                budget -= self._count_tokens(excerpt)

        # 4. Similar code from codebase index
        if budget > 100:
            similar = await self.index.search(
                prefix[-500:], top_k=3, exclude=file_path
            )
            for s in similar:
                if budget > 0:
                    snippets.append(s)
                    budget -= self._count_tokens(s["content"])

        return {
            "prefix": prefix_tokens,
            "suffix": suffix_tokens,
            "snippets": snippets,
        }

4. Inference Architecture

Model Serving & Speculative Decoding ▼

Two-Tier Model Strategy

Tier Model Use Case Latency Cost
Fast (Draft) 7B code model (quantized) Inline completions TTFT < 100ms ~$0.001/req
Power 70B+ or GPT-4 class Chat, refactor, explain TTFT < 500ms ~$0.01/req

Speculative Decoding

Key optimization: small draft model generates N candidate tokens, large verifier model checks all N in one forward pass. 2-3x speedup.

class SpeculativeDecoder:
    """Speculative decoding: draft model proposes, target verifies."""

    def __init__(self, draft_model, target_model, n_speculative=5):
        self.draft = draft_model
        self.target = target_model
        self.n_spec = n_speculative

    async def generate(self, prompt: str, max_tokens: int) -> str:
        tokens = []
        while len(tokens) < max_tokens:
            # Draft model generates N candidate tokens autoregressively
            draft_tokens = []
            draft_probs = []
            ctx = prompt + self._decode(tokens)

            for _ in range(self.n_spec):
                logits = await self.draft.forward(ctx + self._decode(draft_tokens))
                prob = self._softmax(logits)
                token = self._sample(prob)
                draft_tokens.append(token)
                draft_probs.append(prob[token])

            # Target model verifies ALL draft tokens in single forward pass
            target_logits = await self.target.forward_batch(
                ctx, draft_tokens
            )

            # Accept tokens until first rejection
            for i, dt in enumerate(draft_tokens):
                target_prob = self._softmax(target_logits[i])
                # Rejection sampling
                if target_prob[dt] / draft_probs[i] >= self._random():
                    tokens.append(dt)
                else:
                    # Reject: sample from adjusted distribution
                    adjusted = self._adjust_distribution(
                        target_prob, self._softmax(target_logits[i])
                    )
                    tokens.append(self._sample(adjusted))
                    break

        return self._decode(tokens)

5. Streaming & Request Management

Debouncing, Cancellation & Caching ▼

Client-Side Debouncing

User types fast — don't send a request on every keystroke:

  • Debounce: Wait 150-300ms after last keystroke before sending
  • Cancel in-flight: If user keeps typing, abort previous request
  • Prefix matching: If new input is an extension of old prompt, reuse partial result

Server-Side Optimizations

  • KV Cache reuse: For prefix-sharing requests, reuse computed KV cache from previous request
  • Prompt caching: Hash the prompt — identical context = identical completion (high cache hit for boilerplate)
  • Continuous batching: vLLM/TensorRT-LLM batch incoming requests dynamically, maximizing GPU utilization
  • Early stopping: Stop generation when model outputs newline (single-line completion) or closing bracket

Latency Budget Breakdown

Target: First token < 200ms

Client debounce: 150ms (not counted, user is still typing)
Network RTT: ~30ms
Context assembly: ~20ms
Prompt encoding (prefill): ~50ms
First token decode: ~10ms
Network back: ~30ms
Total: ~140ms (within budget)

7. Quality & Evaluation

Metrics & Feedback Loops ▼

Key Metrics

Metric Target Why It Matters

Persistence Rate > 70% Accepted code not deleted within 30 seconds
TTFT (P50) < 200ms Must feel instant for inline

9. Staff-Level Discussion Points

Deep Tradeoffs ▼

Model Selection: Self-Hosted vs API

  • Self-hosted (StarCoder, CodeLlama): Full control, lower per-request cost at scale, data stays internal. But: GPU ops burden, slower iteration on model quality.
  • API (OpenAI, Anthropic): Best quality, zero ops. But: latency depends on provider, cost per token, data privacy concerns.
  • Hybrid: Self-hosted 7B for inline completions (latency-critical, high volume), API for chat (quality-critical, lower volume).

Codebase Indexing Strategy

  • On-device: Index on user's machine using local embedding model. Fast, private. Limited by client compute.
  • Server-side: Index per-repo in cloud. Shared across team. Higher quality embeddings. Privacy trade-off.
  • Hybrid: Local index for open files + server index for broader repo search.

Privacy vs Quality Tension

Better context = better suggestions, but enterprise customers won't send code to external APIs. Solutions:

  • On-prem deployment with customer-managed keys
  • Federated learning for model improvement without code access
  • Differential privacy for telemetry data

11. Active Recall Quiz

Test Your Understanding (6 Questions) ▼
Q1: Why use Fill-in-the-Middle (FIM) instead of standard left-to-right generation for inline code completion?
Show Answer▼

FIM sees code both BEFORE and AFTER the cursor. This allows the model to generate code that fits the surrounding context (e.g., matching variable names, return types). Standard L-to-R only sees the prefix and might generate code that conflicts with what comes next.

Q2: Explain speculative decoding and why it's critical for code completion.
Show Answer▼

A small draft model generates N candidate tokens fast. A larger verifier checks all N in one forward pass (parallelizable). Accepted tokens are kept, first rejected token is resampled. This gives 2-3x speedup with no quality loss — critical for the <200ms TTFT requirement.

Q3: Why is acceptance rate alone insufficient as a quality metric?
Show Answer▼

A model suggesting only trivial one-liners (closing brackets, obvious variable names) will have high acceptance but low value. Better metrics: accepted characters per session (volume × quality) and persistence rate (code not deleted within 30 seconds).

Q4: How would you handle a 100K-line monorepo for context? You can't fit it all in the prompt.
Show Answer▼

Prioritized context: (1) cursor prefix/suffix, (2) imported type signatures via LSP, (3) recently edited files, (4) similar code from embedding index. Use AST-aware chunking to index the repo. Budget ~2K tokens total with priority ordering.

Q5: Why use a two-tier model strategy (7B for inline, 70B+ for chat)?
Show Answer▼

Inline completions are 70% of requests, latency-critical (<200ms TTFT), and short output (~1-3 lines). A 7B model handles this fine at $0.001/req. Chat requests need deeper reasoning, can tolerate 500ms+ TTFT, and are 30% of volume. Different cost/latency/quality trade-offs per tier.

Q6: What are the key differences between client-side debouncing and server-side request cancellation?
Show Answer▼

Client debouncing (150ms delay) prevents sending requests while the user is actively typing — reduces request volume by ~70%. Server-side cancellation aborts in-flight GPU work when a new request arrives from the same user — frees GPU resources immediately rather than completing a stale completion no one will see.
