Design: RAG Over 10M Documents

Zero Hallucinations, Sub-2s Latency

Difficulty: Hard | Time: 45-60 minutes

1. Requirements Clarification

Functional Requirements ▼
  • Query 10M+ documents across PDF, HTML, Markdown, and code files
  • Natural language Q&A with cited, grounded answers
  • Zero hallucination guarantee — abstain rather than fabricate
  • Access control — users only see docs they're authorized for
  • Multi-format ingestion — PDF, HTML, DOCX, source code, Markdown
  • Incremental updates — new/modified docs reflected within minutes
Non-Functional Requirements ▼
  • Latency: P95 < 2 seconds end-to-end
  • Availability: 99.9% uptime
  • Scalability: Horizontal scaling for both ingestion and query paths
  • Audit trail: Every answer traceable to source chunks
  • Freshness: Index lag < 15 minutes for updated docs

2. Scale & Capacity Estimation

Back-of-Envelope Math ▼
Document Corpus:
- 10M documents, average 10 pages each
- Average 5 chunks per document (semantic chunking)
- Total chunks: 10M × 5 = 50M vectors

Embedding Storage:
- Embedding dimension: 1536 (OpenAI) or 1024 (Cohere v3)
- Bytes per vector: 1536 × 4 (float32) = 6,144 bytes
- Raw vector storage: 50M × 6 KB ≈ 300 GB
- With HNSW index overhead (~1.5x): ~450 GB

Chunk Text Storage:
- Average chunk: 512 tokens ≈ 2 KB text
- 50M × 2 KB = 100 GB raw text

Query Load:
- 1,000 queries/minute peak (enterprise)
- Each query: 1 embedding call + 1 vector search + 1 rerank + 1 LLM call
- LLM tokens per query: ~4K input + ~500 output = ~4.5K tokens

Cost Estimate (monthly):
- Embedding generation (one-time): 50M × $0.0001/1K tokens ≈ $2,500
- Query embeddings: 1M queries × $0.0001 ≈ $100
- LLM calls: 1M × 4.5K tokens × $3/1M ≈ $13,500
- Vector DB hosting (managed): ~$2,000-5,000/month
- Total: ~$18K-21K/month

3. Ingestion Pipeline

Document Parsing & Chunking ▼

Parsing Strategy by Format

Format Parser Challenges
PDF LlamaParse, Unstructured, PyMuPDF Tables, images, multi-column layouts
HTML BeautifulSoup + Trafilatura Boilerplate removal, navigation noise
Code Tree-sitter + custom splitter Preserving function boundaries
DOCX python-docx + Unstructured Embedded images, headers/footers

Chunking Strategies

  • Semantic Chunking: Split at topic boundaries using embedding similarity. Best for prose documents.
  • Recursive Character Splitting: Split by paragraph → sentence → word with overlap. Good baseline.
  • Parent-Document Chunking: Store small chunks for retrieval, but return parent (larger) chunk for context. Key for maintaining coherence.
  • Code-Aware Chunking: Use AST-based splitting to keep functions/classes intact.
Staff-Level Insight: Use parent-document retrieval at 10M scale. Small chunks (256 tokens) give better retrieval precision, but the LLM needs surrounding context (1024+ tokens) to generate coherent answers. Store both granularities.

Metadata Extraction

Each chunk carries metadata for filtering and attribution:

  • doc_id, chunk_index, parent_chunk_id
  • source_url, title, author
  • created_at, updated_at
  • access_groups[] — ACL tags for permission filtering
  • doc_type (pdf, html, code, etc.)

Code Sample: Chunking Pipeline

from dataclasses import dataclass, field
from typing import Optional
import hashlib

@dataclass
class Chunk:
    text: str
    doc_id: str
    chunk_index: int
    parent_chunk_id: Optional[str] = None
    metadata: dict = field(default_factory=dict)

    @property
    def chunk_id(self) -> str:
        return hashlib.sha256(
            f"{self.doc_id}:{self.chunk_index}".encode()
        ).hexdigest()[:16]

class SemanticChunker:
    """Split documents at topic boundaries using embedding similarity."""

    def __init__(self, embed_fn, similarity_threshold=0.75,
                 min_chunk_size=128, max_chunk_size=512):
        self.embed_fn = embed_fn
        self.threshold = similarity_threshold
        self.min_size = min_chunk_size
        self.max_size = max_chunk_size

    def chunk(self, text: str, doc_id: str) -> list[Chunk]:
        sentences = self._split_sentences(text)
        embeddings = self.embed_fn([s for s in sentences])

        chunks, current = [], []
        for i, sentence in enumerate(sentences):
            current.append(sentence)
            current_len = sum(len(s.split()) for s in current)

            # Check if next sentence is a topic shift
            if i < len(sentences) - 1 and current_len >= self.min_size:
                sim = self._cosine_sim(embeddings[i], embeddings[i + 1])
                if sim < self.threshold or current_len >= self.max_size:
                    chunks.append(Chunk(
                        text=" ".join(current),
                        doc_id=doc_id,
                        chunk_index=len(chunks),
                    ))
                    current = []

        if current:
            chunks.append(Chunk(
                text=" ".join(current),
                doc_id=doc_id,
                chunk_index=len(chunks),
            ))

        # Create parent chunks (groups of 3 child chunks)
        parent_chunks = []
        for i in range(0, len(chunks), 3):
            group = chunks[i:i+3]
            parent = Chunk(
                text=" ".join(c.text for c in group),
                doc_id=doc_id,
                chunk_index=i // 3,
                metadata={"is_parent": True},
            )
            parent_chunks.append(parent)
            for c in group:
                c.parent_chunk_id = parent.chunk_id

        return chunks + parent_chunks

    def _split_sentences(self, text):
        import re
        return [s.strip() for s in re.split(r'(?<=[.!?])\s+', text) if s.strip()]

    def _cosine_sim(self, a, b):
        import numpy as np
        return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

4. Retrieval Architecture

Hybrid Search: Dense + Sparse ▼

Neither dense (embedding) nor sparse (BM25) search alone is sufficient at 10M scale. Hybrid search combines both:

Method Strengths Weaknesses
Dense (Embedding) Semantic understanding, paraphrase matching Misses exact terms, acronyms, IDs
Sparse (BM25) Exact keyword match, rare terms No semantic understanding
Hybrid Best of both; Reciprocal Rank Fusion Slightly higher latency

Advanced Retrieval Techniques

  • Query Decomposition: Break complex questions into sub-queries, retrieve for each, merge results
  • HyDE (Hypothetical Document Embeddings): Generate a hypothetical answer, embed it, search for similar real chunks
  • Multi-hop Retrieval: First retrieval informs second query for questions requiring reasoning chains
  • Cross-encoder Re-ranking: After initial retrieval (top-100), re-rank with a cross-encoder model for precision (top-10)

Code Sample: Hybrid Retrieval + Rerank

from dataclasses import dataclass

@dataclass
class SearchResult:
    chunk_id: str
    text: str
    score: float
    metadata: dict

class HybridRetriever:
    def __init__(self, vector_db, bm25_index, reranker, embed_fn):
        self.vector_db = vector_db
        self.bm25 = bm25_index
        self.reranker = reranker
        self.embed_fn = embed_fn

    async def retrieve(self, query: str, user_groups: list[str],
                       top_k: int = 10) -> list[SearchResult]:
        # Step 1: Parallel dense + sparse search
        query_embedding = self.embed_fn(query)

        # Permission filter applied at vector DB level
        acl_filter = {"access_groups": {"$in": user_groups}}

        dense_results = await self.vector_db.query(
            vector=query_embedding,
            filter=acl_filter,
            top_k=100,
        )
        sparse_results = await self.bm25.search(
            query, filter_groups=user_groups, top_k=100
        )

        # Step 2: Reciprocal Rank Fusion
        fused = self._rrf_merge(dense_results, sparse_results, k=60)

        # Step 3: Cross-encoder rerank (top 50 -> top_k)
        candidates = fused[:50]
        reranked = await self.reranker.rerank(
            query=query,
            documents=[c.text for c in candidates],
            top_k=top_k,
        )

        return [candidates[i] for i in reranked.indices]

    def _rrf_merge(self, dense, sparse, k=60):
        """Reciprocal Rank Fusion: score = sum(1 / (k + rank))"""
        scores = {}
        for rank, r in enumerate(dense):
            scores[r.chunk_id] = scores.get(r.chunk_id, 0) + 1 / (k + rank)
        for rank, r in enumerate(sparse):
            scores[r.chunk_id] = scores.get(r.chunk_id, 0) + 1 / (k + rank)

        # Merge results, sort by fused score
        all_results = {r.chunk_id: r for r in dense + sparse}
        merged = sorted(
            all_results.values(),
            key=lambda r: scores.get(r.chunk_id, 0),
            reverse=True,
        )
        return merged

5. Zero Hallucination Strategy

Grounded Generation & Verification ▼

Zero hallucination is the hardest requirement. It requires a defense-in-depth approach across multiple layers:

Layer 1: Constrained Prompting

System Prompt Pattern:

You are a document Q&A assistant. Answer ONLY based on the provided context.
Rules:
1. Every claim must cite a source: [Source: doc_title, chunk_id]
2. If the context doesn't contain the answer, say "I don't have enough information to answer this."
3. Never speculate, infer, or use prior knowledge.
4. If partially answerable, answer what you can and explicitly state what's missing.

Layer 2: Faithfulness Scoring

After generation, score the answer against retrieved chunks using NLI (Natural Language Inference):

  • RAGAS Faithfulness: Decompose answer into claims, check each claim against context
  • NLI Model: Cross-encoder trained on NLI data (entailment/contradiction/neutral)
  • Threshold: Reject answers with faithfulness < 0.85

Layer 3: Abstention Mechanism

  • If retrieval confidence (max similarity score) < threshold → abstain
  • If LLM confidence (token probabilities) shows high entropy → abstain
  • If faithfulness score < 0.85 → return "Could not verify answer" with retrieved chunks

Layer 4: Fact-Verification Chain

Use a second LLM call as a verifier:

Code Sample: Hallucination Detector

from dataclasses import dataclass

@dataclass
class VerificationResult:
    is_faithful: bool
    score: float
    unfaithful_claims: list[str]
    verified_claims: list[str]

class HallucinationDetector:
    """Multi-layer hallucination detection pipeline."""

    def __init__(self, nli_model, llm_client, threshold=0.85):
        self.nli = nli_model
        self.llm = llm_client
        self.threshold = threshold

    async def verify(self, answer: str, context_chunks: list[str]) -> VerificationResult:
        # Step 1: Decompose answer into atomic claims
        claims = await self._extract_claims(answer)

        # Step 2: Check each claim against context via NLI
        context = "\n\n".join(context_chunks)
        verified, unfaithful = [], []

        for claim in claims:
            entailment_score = self.nli.predict(
                premise=context, hypothesis=claim
            )
            if entailment_score > self.threshold:
                verified.append(claim)
            else:
                unfaithful.append(claim)

        score = len(verified) / max(len(claims), 1)

        return VerificationResult(
            is_faithful=score >= self.threshold and len(unfaithful) == 0,
            score=score,
            unfaithful_claims=unfaithful,
            verified_claims=verified,
        )

    async def _extract_claims(self, answer: str) -> list[str]:
        """Use LLM to decompose answer into atomic, verifiable claims."""
        response = await self.llm.chat(
            messages=[{
                "role": "user",
                "content": (
                    f"Decompose this answer into atomic factual claims. "
                    f"Each claim should be a single verifiable statement.\n\n"
                    f"Answer: {answer}\n\n"
                    f"Return one claim per line, no numbering."
                ),
            }],
            temperature=0,
        )
        return [c.strip() for c in response.content.split("\n") if c.strip()]


class RAGPipeline:
    """End-to-end RAG with hallucination prevention."""

    def __init__(self, retriever, llm, detector):
        self.retriever = retriever
        self.llm = llm
        self.detector = detector

    async def query(self, question: str, user_groups: list[str]) -> dict:
        # Retrieve
        chunks = await self.retriever.retrieve(
            question, user_groups=user_groups, top_k=10
        )

        # Check retrieval confidence
        if not chunks or chunks[0].score < 0.3:
            return {
                "answer": "I don't have enough information to answer this question.",
                "sources": [],
                "confidence": 0.0,
            }

        # Generate
        context = "\n\n".join(
            f"[Source: {c.metadata.get('title', 'Unknown')}, {c.chunk_id}]\n{c.text}"
            for c in chunks
        )
        answer = await self.llm.chat(messages=[
            {"role": "system", "content": GROUNDED_SYSTEM_PROMPT},
            {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {question}"},
        ], temperature=0)

        # Verify
        verification = await self.detector.verify(
            answer.content, [c.text for c in chunks]
        )

        if not verification.is_faithful:
            return {
                "answer": (
                    "I found relevant documents but could not verify "
                    "a fully accurate answer. Here are the relevant sources:"
                ),
                "sources": [{"title": c.metadata.get("title"), "text": c.text[:200]} for c in chunks[:3]],
                "confidence": verification.score,
            }

        return {
            "answer": answer.content,
            "sources": [{"title": c.metadata.get("title"), "chunk_id": c.chunk_id} for c in chunks],
            "confidence": verification.score,
        }

6. Vector Database Design

Sharding, Indexing & Multi-Tenancy ▼

Index Algorithm: HNSW vs IVF

Aspect HNSW IVF-PQ
Query Latency <10ms (fast) 10-50ms
Memory High (graph in RAM) Low (compressed)
Insert Speed Slow (rebuild graph) Fast (append to cluster)
Recall@10 99%+ 90-95%
Best For Low-latency, high-recall (our case) Cost-sensitive, billions of vectors

Sharding Strategy

  • Namespace-based sharding: Each tenant/org gets a namespace (Pinecone) or collection (Qdrant)
  • Metadata filtering: Single index with access_groups filter — simpler ops, works to ~100M vectors
  • Horizontal partitioning: Shard by doc_type or department for query locality

Index Refresh Strategy

  • New documents: Insert immediately (HNSW supports online insertion)
  • Updated documents: Delete old chunks + insert new (transactional via doc_id filter)
  • Deleted documents: Soft delete with TTL, batch cleanup weekly
  • Embedding model change: Full re-index required. Run shadow index, atomic swap.

9. Staff-Level Discussion Points

Cost, Tradeoffs & Deep Decisions ▼

Embedding Model Selection

Model Dimensions MTEB Score Cost/1M tokens Tradeoff
OpenAI text-embedding-3-large 3072 (or 1536) 64.6 $0.13 High quality, vendor lock-in
Cohere embed-v3 1024 64.5 $0.10 Cheaper, built-in compression
BGE-large (self-hosted) 1024 63.9 GPU cost only No vendor lock-in, ops burden

When to Fine-Tune Retriever vs Generator

  • Fine-tune retriever when domain has specialized vocabulary (legal, medical, code) and general embeddings miss relevant chunks
  • Fine-tune generator when you need consistent output format, specific citation style, or domain-specific reasoning
  • Neither: Start with better chunking and prompting — 80% of RAG quality comes from retrieval quality, not model tuning

Cost Optimization at Scale

  • Semantic caching: Cache answers for similar queries (embedding similarity > 0.95)
  • Tiered retrieval: Fast BM25 first, upgrade to hybrid only if confidence low
  • Quantized vectors: int8 quantization reduces storage 4x with ~1% recall loss
  • Matryoshka embeddings: Use fewer dimensions for initial search, full dimensions for rerank

10. Interview Tips & Follow-ups

How to Ace This Problem ▼

What Interviewers Look For

  • Understanding that RAG quality is primarily a retrieval problem, not a generation problem
  • Concrete zero-hallucination strategy — not just "use a good prompt"
  • Scale awareness: chunking choices, vector DB selection, cost estimation
  • Security: ACL-aware retrieval, not just post-filtering

Common Follow-up Questions

  • "How do you handle a document update? Do you re-embed the whole doc?"
  • "What if the embedding model provider changes their model?"
  • "How do you evaluate your RAG system? What metrics?"
  • "Walk me through what happens when a query returns no good results."
  • "How would you handle multi-language documents?"

Red Flags to Avoid

  • Saying "just use GPT-4 with a big context window" instead of RAG
  • Ignoring chunking strategy or treating all docs the same
  • No verification layer — trusting LLM output blindly
  • Skipping access control in retrieval

11. Active Recall Quiz

Test Your Understanding (6 Questions) ▼
Q1: Why use hybrid search (dense + sparse) instead of just embedding search?
Show Answer▼

Dense embeddings miss exact keyword matches (acronyms, IDs, product codes). BM25 catches these. Hybrid with Reciprocal Rank Fusion combines semantic understanding with exact matching for best recall.

Q2: What is the parent-document retrieval pattern and why is it important at scale?
Show Answer▼

Store small chunks (~256 tokens) for precise retrieval, but fetch the parent chunk (~1024 tokens) for generation context. Small chunks match queries better, but the LLM needs surrounding context for coherent answers.

Q3: Describe three layers of defense against hallucination.
Show Answer▼

(1) Constrained prompting with citation requirements. (2) NLI-based faithfulness scoring that decomposes answer into claims and checks entailment. (3) Abstention mechanism when retrieval confidence or faithfulness score is below threshold.

Q4: HNSW vs IVF-PQ — which would you choose for 50M vectors with <2s latency requirement and why?
Show Answer▼

HNSW. At 50M vectors, HNSW gives <10ms query latency with 99%+ recall. The ~450GB memory requirement is manageable with modern servers. IVF-PQ saves memory but sacrifices recall (90-95%) which is unacceptable for a zero-hallucination system.

Q5: How do you handle embedding model migration without downtime?
Show Answer▼

Shadow re-indexing: build new index with new embeddings alongside existing one. Run queries against both, validate new index quality with eval set. Atomic swap once quality is confirmed. Roll back if metrics degrade.

Q6: Why should ACL filtering happen at the vector DB level, not as post-processing?
Show Answer▼

Post-filtering can return fewer than top-K results (or empty results) if many top matches are filtered out. DB-level filtering ensures you always get K results from the authorized set, maintaining result quality and avoiding information leakage through result count.
