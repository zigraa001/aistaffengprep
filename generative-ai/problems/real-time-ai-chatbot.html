Design: Real-Time AI Chatbot

ChatGPT / Claude-Scale Conversational AI

Difficulty: Hard | Time: 45-60 minutes

1. Requirements Clarification

Functional Requirements ▼
  • Real-time streaming chat — token-by-token response delivery
  • Multi-turn conversations with persistent history
  • File/image upload and multi-modal processing
  • Model selection — user picks GPT-4, Claude, open-source models
  • Conversation management — history, search, share, branch/regenerate
  • System prompt customization (custom instructions)
  • Code execution sandbox (like ChatGPT Code Interpreter)
Non-Functional Requirements ▼
  • TTFT (Time to First Token): P95 < 500ms
  • Concurrency: 1M concurrent conversations
  • Availability: 99.95% uptime
  • Graceful degradation under GPU pressure
  • Data privacy: Conversations encrypted, GDPR-compliant deletion

3. Streaming Architecture

SSE vs WebSocket & Token Streaming ▼

SSE vs WebSocket

Aspect Server-Sent Events (SSE) WebSocket
Direction Server → Client only Bidirectional
Protocol HTTP/2 (auto-reconnect) Custom protocol over TCP
Load Balancing Standard HTTP LB works Sticky sessions needed
Proxy Friendly Yes (standard HTTP) Requires upgrade support
Best For LLM token streaming (our case) Real-time collaborative features
Staff-Level Insight: ChatGPT and Claude both use SSE over HTTP, not WebSocket. SSE is simpler, works with standard HTTP infrastructure, auto-reconnects, and LLM streaming is server-to-client only. Use WebSocket only if you need client-to-server streaming (e.g., voice input).

Code Sample: SSE Streaming Endpoint

import asyncio
import json
import time
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app = FastAPI()

async def stream_llm_response(conversation_id: str, messages: list,
                                model: str, llm_client):
    """Stream LLM tokens as SSE events."""
    start = time.monotonic()
    first_token = True

    async for chunk in llm_client.stream(model=model, messages=messages):
        token = chunk.content
        if not token:
            continue

        if first_token:
            ttft = time.monotonic() - start
            metrics.record_ttft(conversation_id, ttft)
            first_token = False

        # SSE format: "data: {json}\n\n"
        event = {
            "type": "token",
            "content": token,
            "conversation_id": conversation_id,
        }
        yield f"data: {json.dumps(event)}\n\n"

    # Final event with metadata
    yield f"data: {json.dumps({'type': 'done', 'usage': chunk.usage.dict()})}\n\n"

Connection Lifecycle

  • Open: Client sends POST, server returns SSE stream
  • Streaming: Tokens arrive as data: events, client renders incrementally
  • Complete: Server sends done event with usage stats
  • Abort: Client closes connection → server cancels LLM inference (saves GPU)
  • Reconnect: Client resumes from last received token using Last-Event-ID

Code Sample: Model Gateway with Fallback

from dataclasses import dataclass
from typing import AsyncIterator
import asyncio

@dataclass
class ModelConfig:
    provider: str        # "openai", "anthropic", "self-hosted"
    model_id: str        # "gpt-4", "claude-sonnet-4-6", "llama-3-70b"
    max_tokens: int
    cost_per_1k_input: float
    cost_per_1k_output: float
    timeout_ms: int = 30000

class ModelGateway:
    """Multi-provider gateway with fallback and load balancing."""

    def __init__(self, providers: dict, fallback_chain: list[str]):
        self.providers = providers  # provider_name -> client
        self.chain = fallback_chain
        self.circuit_breakers = {p: CircuitBreaker() for p in providers}

    async def stream(self, model: str, messages: list,
                     **kwargs) -> AsyncIterator[str]:
        config = MODEL_REGISTRY[model]
        errors = []

        # Try primary, then fallbacks
        for provider_name in self._get_chain(config.provider):
            breaker = self.circuit_breakers[provider_name]

            if breaker.is_open:
                continue  # Skip providers with recent failures

            try:
                client = self.providers[provider_name]
                async for token in client.stream(
                    model=config.model_id,
                    messages=messages,
                    timeout=config.timeout_ms,
                    **kwargs,
                ):
                    yield token
                return  # Success — exit

            except (TimeoutError, ProviderError) as e:
                breaker.record_failure()
                errors.append(f"{provider_name}: {e}")
                continue

        raise AllProvidersFailedError(errors)

    def _get_chain(self, primary: str) -> list[str]:
        """Return fallback chain starting with primary provider."""
        chain = [primary]
        chain.extend(p for p in self.chain if p != primary)
        return chain


class CircuitBreaker:
    """Simple circuit breaker: open after 3 failures in 60s."""

    def __init__(self, threshold=3, window=60):
        self.threshold = threshold
        self.window = window
        self.failures: list[float] = []

    @property
    def is_open(self) -> bool:
        now = asyncio.get_event_loop().time()
        self.failures = [t for t in self.failures if now - t < self.window]
        return len(self.failures) >= self.threshold

    def record_failure(self):
        self.failures.append(asyncio.get_event_loop().time())

5. Conversation Management

Context Windows, Branching & Token Budgets ▼

Context Window Strategy

Long conversations exceed model context limits. Strategy:

  • Recent window: Keep last N messages verbatim
  • Summary compression: Summarize older messages into 200-300 tokens
  • Token budget: Reserve tokens for system prompt (500) + summary (300) + recent turns (variable) + generation (max_tokens)

Conversation Branching

"Edit & Regenerate" creates a tree, not a linear history:

from dataclasses import dataclass, field
from datetime import datetime
from typing import Optional
import uuid

@dataclass
class Message:
    id: str = field(default_factory=lambda: str(uuid.uuid4()))
    role: str = ""           # "user", "assistant", "system"
    content: str = ""
    parent_id: Optional[str] = None  # For branching
    model: Optional[str] = None
    tokens_used: int = 0
    created_at: datetime = field(default_factory=datetime.utcnow)

class ConversationManager:
    """Manages conversation tree with branching and context windows."""

    def __init__(self, db, summarizer, token_counter):
        self.db = db
        self.summarizer = summarizer
        self.count_tokens = token_counter

    async def get_context(self, conversation_id: str, leaf_msg_id: str,
                          max_tokens: int = 8000) -> list[dict]:
        """Build context by walking from leaf to root of message tree."""
        # Get the path from leaf to root
        path = await self._get_path_to_root(conversation_id, leaf_msg_id)
        path.reverse()  # Root to leaf order

        # Token budgeting
        system_budget = 500
        summary_budget = 300
        generation_budget = 2000
        available = max_tokens - system_budget - summary_budget - generation_budget

        # Take as many recent messages as fit
        recent, tokens_used = [], 0
        for msg in reversed(path):
            msg_tokens = self.count_tokens(msg.content)
            if tokens_used + msg_tokens > available:
                break
            recent.insert(0, msg)
            tokens_used += msg_tokens

        # Summarize older messages if any were cut
        context = []
        older = [m for m in path if m not in recent]
        if older:
            summary = await self.summarizer.summarize(older)
            context.append({
                "role": "system",
                "content": f"Earlier conversation summary: {summary}"
            })

        context.extend(
            {"role": m.role, "content": m.content} for m in recent
        )
        return context

    async def branch(self, conversation_id: str, parent_msg_id: str,
                     new_content: str) -> Message:
        """Create a new branch from an existing message."""
        msg = Message(
            role="user",
            content=new_content,
            parent_id=parent_msg_id,
        )
        await self.db.save_message(conversation_id, msg)
        return msg

    async def _get_path_to_root(self, conv_id, msg_id):
        """Walk parent pointers from leaf to root."""
        path, current_id = [], msg_id
        while current_id:
            msg = await self.db.get_message(conv_id, current_id)
            path.append(msg)
            current_id = msg.parent_id
        return path

9. Performance Optimization

KV Cache, Prefix Caching & Admission Control ▼

Key Optimizations

Optimization Speedup How It Works
KV Cache Reuse 2-5x TTFT Reuse previous turns' KV cache; only compute new message attention
Prefix Caching 3-10x for shared prompts Cache system prompt KV across users with same instructions
Continuous Batching 3-5x throughput New requests join batch as old ones finish (vLLM)
Speculative Decoding 2-3x tokens/sec Draft model proposes N tokens; large model verifies in one pass
Quantization (INT8/INT4) 2-4x memory savings Reduce model precision with minimal quality loss

Admission Control Under Load

  • Queue-based: When GPU utilization > 90%, queue new requests (show "Thinking..." with ETA)
  • Priority queue: Pro users skip ahead of free tier
  • Model downgrade: Under extreme load, auto-route free tier to smaller model
  • Request shedding: Return 503 with retry-after header as last resort

11. Staff-Level Discussion Points

Self-Hosted vs API, Cost, Multi-Region ▼

Self-Hosted vs API-Based

Aspect Self-Hosted (vLLM) API-Based (OpenAI/Anthropic)
Cost at Scale Cheaper above ~$50K/month Pay-per-token, no GPU management
Latency Control Full control over batching/caching Subject to provider's queue
Model Quality Open-source (Llama 3, Mistral) Best frontier models (GPT-4, Claude)
Ops Burden High (GPU cluster management) Minimal (REST API calls)
Staff-Level Take: Use API for frontier models (quality matters, GPT-4/Claude), self-host for free tier and high-volume use cases (cost matters). Hybrid approach: route premium users to API providers, free tier to self-hosted Llama 3. This optimizes cost while maintaining quality where it matters.

Cost Per Conversation

  • Average conversation: 8 turns × (500 input + 800 output) = ~10.4K tokens
  • GPT-4: $0.03/1K input + $0.06/1K output ≈ $0.50/conversation
  • Self-hosted Llama 3 70B: ~$0.002/1K tokens ≈ $0.02/conversation
  • At 8M conversations/month: $4M (GPT-4) vs $160K (self-hosted) = 25x cost difference

Multi-Region Deployment

  • GPU scarcity: Not all regions have A100/H100 availability
  • Latency: TTFT dominated by inference, not network. Region matters less than GPU availability.
  • Data residency: EU users' conversations stored in EU region (GDPR)
  • Strategy: GPU clusters in 2-3 regions, route by user location + GPU capacity

13. Active Recall Quiz

Test Your Understanding (6 Questions) ▼
Q1: Why is SSE preferred over WebSocket for LLM chat streaming?
Show Answer▼

LLM streaming is server-to-client only (unidirectional). SSE works over standard HTTP, supports auto-reconnect, works with normal load balancers and proxies, and doesn't need sticky sessions. WebSocket's bidirectionality is unnecessary overhead for this use case.

Q2: Explain KV cache reuse in multi-turn conversations and its impact on TTFT.
Show Answer▼

In multi-turn chat, previous turns' key-value attention states are cached. When a new message arrives, only the new tokens need attention computation (the "prefill" phase). This reduces TTFT from O(full_context) to O(new_message), typically 2-5x faster. vLLM and TensorRT-LLM both support automatic KV cache management.

Q3: How would you implement "edit and regenerate" (conversation branching)?
Show Answer▼

Model conversations as a tree, not a list. Each message has a parent_id pointer. "Edit and regenerate" creates a new branch from the edited message's parent. The UI shows siblings as alternatives. Context window is built by walking from current leaf to root.

Q4: What is continuous batching and why is it critical for chat workloads?
Show Answer▼

Traditional batching waits for all requests in a batch to complete before starting new ones. Continuous batching (iteration-level scheduling) allows new requests to join an in-progress batch as old requests finish generating. This is critical for chat because response lengths vary wildly — a "yes" answer shouldn't hold GPU capacity while a 2000-token answer completes.

Q5: How do you prevent a user from extracting the system prompt?
Show Answer▼

Multi-layer: (1) Prompt injection classifier on input to detect extraction attempts. (2) System prompt instructs model to never reveal instructions. (3) Output filter checks for system prompt substrings in response. (4) Use API-level system message separation (not concatenated with user text). None are foolproof — defense in depth.

Q6: At 1M DAU, when does self-hosting become cheaper than API-based inference?
Show Answer▼

Self-hosting breaks even around $50K/month in API costs. At 8M conversations/month, GPT-4 costs ~$4M/month vs ~$160K self-hosted Llama 3. But self-hosting needs GPU ops team (3-4 engineers), so factor in human cost. Strategy: API for frontier models (paid tier), self-hosted for free tier and high-volume.
