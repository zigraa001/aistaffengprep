Design: Multi-Agent Task Orchestrator

Examples: Claude Code, Devin, AutoGPT, CrewAI, LangGraph

Difficulty: Hard | Time: 45-60 minutes

1. Requirements Clarification

Functional Requirements ▼
  • Task decomposition — break complex user goals into sub-tasks
  • Multi-agent execution — specialized agents (researcher, coder, reviewer, executor) collaborate
  • Tool calling — agents invoke external tools (APIs, databases, file systems, browsers)
  • DAG execution — parallel where possible, sequential when dependent
  • State management — shared context, intermediate results, conversation memory
  • Error recovery — retry, fallback, human escalation on failure
  • Observability — trace every step, token usage, tool calls, decisions
Non-Functional Requirements ▼
  • Latency: Complex tasks complete in seconds-minutes, not hours
  • Cost control: Budget limits per task (max tokens, max tool calls)
  • Safety: Agents cannot take irreversible actions without human approval
  • Determinism: Same input should produce similar (if not identical) results
  • Extensibility: Easy to add new agents and tools without rewriting orchestrator

2. Agent Orchestration Patterns

Patterns: ReAct, DAG, Supervisor, Swarm ▼
Pattern How It Works Best For Weakness
ReAct Loop Think → Act → Observe → Repeat Single-agent tasks, exploration Gets stuck in loops, no parallelism
DAG Orchestration Plan as directed graph, execute in topological order Known workflows, parallelizable tasks Rigid, hard to adapt mid-execution
Supervisor Central LLM delegates to specialized agents Complex multi-step tasks Supervisor bottleneck, token expensive
Swarm / Handoff Agents pass control to each other based on context Conversational flows, customer support Hard to debug, no central view
Staff-Level Insight: In practice, combine patterns. Use a Supervisor for high-level planning, DAG for known sub-workflows, and ReAct for individual agent steps. The supervisor creates the plan, the orchestrator manages execution, and each agent runs its own tool-calling loop.

Code Sample: Orchestrator Core

from dataclasses import dataclass, field
from enum import Enum
from typing import Any, Optional
import asyncio

class TaskStatus(Enum):
    PENDING = "pending"
    RUNNING = "running"
    COMPLETED = "completed"
    FAILED = "failed"
    BLOCKED = "blocked"  # Waiting for dependency

@dataclass
class Task:
    id: str
    description: str
    agent_type: str           # "researcher", "coder", "reviewer"
    dependencies: list[str] = field(default_factory=list)
    status: TaskStatus = TaskStatus.PENDING
    result: Optional[Any] = None
    error: Optional[str] = None
    retries: int = 0
    max_retries: int = 2

@dataclass
class ExecutionPlan:
    tasks: dict[str, Task]
    goal: str

class Orchestrator:
    """DAG-based multi-agent task orchestrator."""

    def __init__(self, agents: dict, state_store, budget):
        self.agents = agents      # agent_type -> Agent instance
        self.state = state_store  # Shared state across agents
        self.budget = budget      # Token/cost budget

    async def execute(self, plan: ExecutionPlan) -> dict:
        """Execute task DAG with maximum parallelism."""
        while not self._all_done(plan):
            # Find tasks ready to run (deps satisfied)
            ready = [
                t for t in plan.tasks.values()
                if t.status == TaskStatus.PENDING
                and self._deps_satisfied(t, plan)
            ]

            if not ready and not self._any_running(plan):
                raise RuntimeError("Deadlock: no ready tasks, none running")

            # Execute ready tasks in parallel
            tasks_coros = []
            for task in ready:
                task.status = TaskStatus.RUNNING
                tasks_coros.append(self._run_task(task, plan))

            if tasks_coros:
                await asyncio.gather(*tasks_coros)

            # Check budget
            if self.budget.exceeded:
                raise BudgetExceededError(
                    f"Budget exceeded: {self.budget.used}/{self.budget.limit}"
                )

        return {
            t.id: t.result for t in plan.tasks.values()
            if t.status == TaskStatus.COMPLETED
        }

    async def _run_task(self, task: Task, plan: ExecutionPlan):
        """Execute a single task with the appropriate agent."""
        agent = self.agents[task.agent_type]

        # Gather dependency results as context
        dep_results = {
            dep_id: plan.tasks[dep_id].result
            for dep_id in task.dependencies
        }

        try:
            result = await agent.execute(
                task=task.description,
                context=dep_results,
                shared_state=self.state,
            )
            task.result = result
            task.status = TaskStatus.COMPLETED

            # Update shared state
            await self.state.set(f"task:{task.id}", result)

        except Exception as e:
            task.retries += 1
            if task.retries <= task.max_retries:
                task.status = TaskStatus.PENDING  # Retry
                task.error = str(e)
            else:
                task.status = TaskStatus.FAILED
                task.error = str(e)

    def _deps_satisfied(self, task, plan):
        return all(
            plan.tasks[d].status == TaskStatus.COMPLETED
            for d in task.dependencies
        )

    def _all_done(self, plan):
        return all(
            t.status in (TaskStatus.COMPLETED, TaskStatus.FAILED)
            for t in plan.tasks.values()
        )

    def _any_running(self, plan):
        return any(
            t.status == TaskStatus.RUNNING
            for t in plan.tasks.values()
        )

4. Tool Gateway & Sandboxing

Secure Tool Execution ▼

The Tool Gateway is the security boundary between AI decisions and real-world actions.

Gateway Responsibilities

  • Authentication: Each tool call carries agent identity; scoped permissions per agent type
  • Rate limiting: Per-agent, per-tool limits (prevent runaway loops)
  • Sandboxing: Code execution in isolated containers (Docker/Firecracker)
  • Approval gates: Destructive actions (delete, deploy, send email) require human confirmation
  • Audit logging: Every tool call logged with input, output, agent, timestamp

Permission Model

from dataclasses import dataclass

@dataclass
class ToolPermission:
    tool_name: str
    allowed_agents: list[str]
    requires_approval: bool = False
    max_calls_per_task: int = 50
    timeout_seconds: int = 30

# Example permission config
PERMISSIONS = [
    ToolPermission("web_search", ["researcher"], max_calls_per_task=20),
    ToolPermission("file_read", ["coder", "reviewer"], max_calls_per_task=100),
    ToolPermission("file_write", ["coder"], max_calls_per_task=50),
    ToolPermission("run_command", ["executor"], requires_approval=True, timeout_seconds=60),
    ToolPermission("git_push", ["executor"], requires_approval=True, max_calls_per_task=1),
    ToolPermission("send_email", ["communicator"], requires_approval=True, max_calls_per_task=5),
]

class ToolGateway:
    """Secure gateway for agent tool calls."""

    def __init__(self, permissions, sandbox, approval_queue):
        self.perms = {p.tool_name: p for p in permissions}
        self.sandbox = sandbox
        self.approval = approval_queue
        self.call_counts: dict[str, dict[str, int]] = {}  # task_id -> tool -> count

    async def execute(self, tool_name: str, args: dict,
                      agent_type: str, task_id: str) -> dict:
        perm = self.perms.get(tool_name)
        if not perm:
            raise PermissionError(f"Unknown tool: {tool_name}")

        # Check agent is allowed
        if agent_type not in perm.allowed_agents:
            raise PermissionError(
                f"Agent '{agent_type}' not allowed to use '{tool_name}'"
            )

        # Check rate limit
        counts = self.call_counts.setdefault(task_id, {})
        counts[tool_name] = counts.get(tool_name, 0) + 1
        if counts[tool_name] > perm.max_calls_per_task:
            raise RateLimitError(f"Tool '{tool_name}' limit exceeded")

        # Human approval if required
        if perm.requires_approval:
            approved = await self.approval.request(
                tool=tool_name, args=args, agent=agent_type
            )
            if not approved:
                return {"status": "denied", "reason": "Human denied action"}

        # Execute in sandbox with timeout
        result = await asyncio.wait_for(
            self.sandbox.run(tool_name, args),
            timeout=perm.timeout_seconds,
        )

        return result

5. Shared State & Memory

Context Sharing Between Agents ▼

State Layers

Layer Scope Contents Storage
Agent Context Single agent's conversation System prompt, messages, tool results In-memory (agent process)
Task State Current task execution Plan, sub-task results, intermediate artifacts Redis / in-memory store
Session State User session Conversation history, user preferences Database
Global Knowledge All users Learned patterns, tool docs, cached results Vector DB + PostgreSQL

Context Passing Problem

Each agent has limited context window. How to pass information between agents efficiently:

  • Summary injection: Summarize upstream agent's output before passing to next agent
  • Artifact store: Agents write artifacts (code files, research docs) to shared store; downstream agents read what they need
  • Structured handoff: Each agent outputs a structured JSON summary, not raw conversation history

6. Error Recovery & Self-Correction

Handling Failures Gracefully ▼

Error Taxonomy

Error Type Example Recovery Strategy
Tool failure API timeout, 500 error Retry with backoff (up to 3x)
Invalid tool call Wrong arguments, missing params Feed error back to agent, ask to fix
Agent stuck in loop Repeating same action Detect loop (N repeated actions), force re-plan
Sub-task failure Agent can't complete task Try different agent, decompose further, or escalate
Budget exceeded Too many tokens/tool calls Return partial results + explain what's left
Plan invalidated Early result changes requirements Re-plan from current state

Self-Correction Pattern

class SelfCorrectingAgent:
    """Agent that detects and recovers from its own mistakes."""

    def __init__(self, llm, tools, max_iterations=10):
        self.llm = llm
        self.tools = tools
        self.max_iter = max_iterations

    async def execute(self, task: str, context: dict,
                      shared_state) -> dict:
        messages = [
            {"role": "system", "content": self._build_system_prompt()},
            {"role": "user", "content": self._format_task(task, context)},
        ]

        action_history = []
        for i in range(self.max_iter):
            response = await self.llm.chat(
                messages=messages, tools=self.tools.schemas()
            )

            # Check for completion
            if response.stop_reason == "end_turn":
                return {"output": response.content, "steps": i + 1}

            # Execute tool call
            tool_call = response.tool_calls[0]

            # Loop detection
            action_key = f"{tool_call.name}:{hash(str(tool_call.args))}"
            if action_history.count(action_key) >= 3:
                messages.append({
                    "role": "user",
                    "content": (
                        "You are repeating the same action. "
                        "Try a completely different approach."
                    ),
                })
                action_history.clear()
                continue

            action_history.append(action_key)

            try:
                result = await self.tools.execute(
                    tool_call.name, tool_call.args
                )
                messages.append({
                    "role": "tool",
                    "content": str(result),
                    "tool_call_id": tool_call.id,
                })
            except Exception as e:
                # Feed error back for self-correction
                messages.append({
                    "role": "tool",
                    "content": f"ERROR: {e}. Please fix and try again.",
                    "tool_call_id": tool_call.id,
                })

        return {"output": "Max iterations reached", "steps": self.max_iter}

8. Failure Modes & Mitigations

What Can Go Wrong ▼
Failure Impact Mitigation
Infinite agent loop Token budget burned, no progress Max iterations + loop detection + forced re-plan
Agent takes destructive action Deletes files, sends wrong email Approval gates; sandbox execution; undo capability
Context overflow Agents forget earlier context Structured handoffs; artifact store; summary compression
Plan is wrong Agents execute bad plan perfectly Checkpoint after each phase; human review of plan; re-plan capability

9. Staff-Level Discussion Points

Deep Architecture Decisions ▼

Determinism vs Flexibility

  • More deterministic: Pre-defined DAG workflows, fixed agent roles, structured outputs. Predictable, testable, auditable.
  • More flexible: LLM decides the plan at runtime, agents can spawn sub-agents. Handles novel tasks, but harder to debug and predict cost.
  • Sweet spot: Deterministic skeleton (known workflow steps) with flexible agent behavior within each step.

Cost Control Strategies

  • Token budgets: Each agent gets a max token allocation; orchestrator tracks global spend
  • Model routing: Simple sub-tasks use cheaper models; complex reasoning uses expensive ones
  • Caching: Cache tool results and LLM responses for repeated patterns
  • Early termination: If first agent answers the question directly, skip remaining plan

When Multi-Agent vs Single Agent

  • Single agent wins when: Task is well-defined, single domain, fits in context window
  • Multi-agent wins when: Task requires multiple domains (code + research + review), needs parallelism, or exceeds single context window
  • Don't over-engineer: Start with single agent + tools. Add multi-agent only when you hit single-agent limitations.

10. Interview Tips & Follow-ups

  • Security mindset: sandboxing, approval gates, least-privilege tools
  • Error recovery: not just happy path, but loops, failures, budget limits

11. Active Recall Quiz

Test Your Understanding (6 Questions) ▼
Q1: Compare DAG orchestration vs Supervisor pattern. When would you choose each?
Show Answer▼

DAG: when you know the workflow upfront, want maximum parallelism, and need predictable execution. Supervisor: when the plan needs to adapt based on intermediate results, tasks are exploratory, or you need dynamic re-planning. In practice, combine both: Supervisor creates the plan, DAG executes it.

Q2: What is a Tool Gateway and why is it critical for multi-agent safety?
Show Answer▼

The Tool Gateway is the security boundary between AI decisions and real-world actions. It enforces: per-agent permissions (coder can't send emails), rate limits (prevent runaway loops), sandboxed execution (code runs in containers), approval gates (destructive actions need human OK), and audit logging. Without it, a misbehaving agent could delete databases or leak data.

Q3: How do you detect and break an agent stuck in an infinite loop?
Show Answer▼

Track action history (tool name + args hash). If the same action appears 3+ times, inject a message telling the agent to try a different approach. Also enforce max_iterations as a hard limit. If both fail, escalate to the supervisor/planner for re-planning or to a human.

Q4: How do agents share context without each one having the full conversation history?
Show Answer▼

Three strategies: (1) Structured handoffs — each agent outputs a JSON summary, downstream agents receive only relevant fields. (2) Artifact store — agents write files/docs to shared storage, others read what they need. (3) Summary injection — summarize upstream output before injecting into next agent's context. This keeps each agent's context window focused.

Q5: When should you use multi-agent vs a single agent with tools?
Show Answer▼

Single agent: task is well-defined, single domain, fits in one context window. Multi-agent: task spans multiple domains (research + code + review), benefits from parallelism, or exceeds single agent's context. Start simple — add multi-agent only when you hit single-agent limits. Over-engineering the orchestration wastes tokens and adds complexity.

Q6: How do you control costs in a multi-agent system where each agent makes LLM calls?
Show Answer▼

Per-agent token budgets tracked by orchestrator. Model routing: simple tasks use cheap models, complex reasoning uses expensive ones. Cache tool results and LLM responses. Early termination if first agent resolves the task. Max iterations per agent. Global task budget with hard stop.
