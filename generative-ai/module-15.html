1. Why Traditional APM Fails for AI Systems

The Observability Gap

Traditional Application Performance Monitoring (APM) tools like New Relic, Dynatrace, and basic Prometheus setups were designed for deterministic services. If your API returns HTTP 200 with a valid JSON body within 200 ms, the system is healthy. That mental model breaks catastrophically for AI systems.

Core Problem An LLM can return HTTP 200 OK, complete in 1.2 seconds, use 95% less CPU than a threshold, and still have completely failed by hallucinating facts, producing toxic output, leaking PII from training data, or answering a question the user did not ask.

What Traditional APM Measures vs. What It Misses

Traditional APM Signal What It Catches What It Misses for AI
HTTP status codes Network/server errors (4xx, 5xx) Hallucinated responses, refusals, off-topic output
Latency (p50, p95, p99) Slow endpoints Time-to-first-token, streaming stall mid-generation
CPU / Memory Infrastructure saturation Token budget exhaustion, context window overflow
Error rate Exceptions thrown Soft failures: incomplete answers, format violations
Throughput (req/s) Load level Token throughput, cost per request, quality degradation under load
Distributed traces Service dependency timing Prompt/completion content, retrieval quality, reranker score distribution

The New Failure Modes You Must Monitor

  • Hallucination creep: Model quietly starts fabricating facts — maybe after a provider model update you didn't control.
  • Latency tail blowout: p99 TTFT jumps from 800ms to 6s during peak hours because the provider rate-limits prompt-heavy requests.
  • Context window pressure: Long conversations start getting silently truncated mid-history, degrading coherence.
  • Prompt injection propagation: A malicious user payload alters downstream tool calls in an agent — invisible to HTTP-level monitoring.
  • Retrieval quality decay: The vector index grows stale; recall@5 drops from 0.92 to 0.61 over 3 weeks. No alarm fires.
  • Output format regression: Model stops returning valid JSON after a provider update. Parsing exceptions cascade.
  • Cost explosion: A single user sends 50,000-token system prompts in a loop. $0 per request becomes $0.80 per request at scale.

The implication is that observability for AI is not a monitoring bolted on after the fact — it is a first-class engineering discipline requiring custom instrumentation at every layer of the AI stack.

2.2 Metric Definitions and Why Each Matters

Time to First Token (TTFT)

TTFT is the wall-clock time from when the client sends the request until the first token streams back. This is the primary perceived latency signal for users using streaming interfaces (chat, copilots). A high TTFT feels like a "frozen" app even if the model is generating fast.

What drives TTFT: network RTT to provider, queue depth at the provider's inference cluster, KV cache miss rate (prompt prefill cost), and system prompt length. A 4,000-token system prompt can add 600ms of prefill time vs. a 100-token prompt.

SLO guidance: For chat interfaces, TTFT p95 under 1.5 seconds feels responsive. Above 3 seconds users perceive "lag." For batch workloads, TTFT matters less than throughput. 

# Measuring TTFT in Python with the OpenAI streaming API
import time
import openai

client = openai.OpenAI()

start = time.perf_counter()
first_token_time = None

stream = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Explain observability for LLMs."}],
    stream=True,
)

for chunk in stream:
    if first_token_time is None and chunk.choices[0].delta.content:
        first_token_time = time.perf_counter()
        ttft_ms = (first_token_time - start) * 1000
        print(f"TTFT: {ttft_ms:.1f} ms")

total_time_ms = (time.perf_counter() - start) * 1000
print(f"Total generation time: {total_time_ms:.1f} ms")
Inter-Token Latency (ITL) and Tokens per Second

ITL is the average time between successive tokens in the streaming response. Tokens per second is simply 1000 / ITL_ms. These metrics tell you about the decode throughput of the inference backend. A sudden drop from 60 tok/s to 10 tok/s indicates the backend is overloaded, running on reduced hardware, or hitting a memory bandwidth ceiling.

For streaming UIs, the readable word rate for humans is approximately 3-5 words per second (~4-7 tokens/s). So 20+ tok/s means output appears instantaneous to the user. Lower than 10 tok/s feels visibly slow. 

# Measuring ITL across a stream
import time

tokens_received = 0
token_times = []

for chunk in stream:
    content = chunk.choices[0].delta.content
    if content:
        token_times.append(time.perf_counter())
        tokens_received += 1

if len(token_times) > 1:
    intervals = [
        (token_times[i+1] - token_times[i]) * 1000
        for i in range(len(token_times) - 1)
    ]
    avg_itl_ms = sum(intervals) / len(intervals)
    tok_per_sec = 1000 / avg_itl_ms
    print(f"Avg ITL: {avg_itl_ms:.1f} ms | {tok_per_sec:.1f} tok/s")
Cost per Request and Token Utilization

Every LLM API call costs money proportional to tokens consumed. You must track input tokens, output tokens, and cached tokens separately because they have different per-token prices (e.g., OpenAI GPT-4o charges $2.50/M input tokens, $1.25/M for cached input tokens, and $10.00/M for output tokens as of mid-2025).

Token utilization rate = actual_tokens_used / context_window_size. If you consistently hit 95%+ utilization, you risk silent truncation. If you average 15%, you may be over-allocating context and paying for tokens that contribute no value. 

def calculate_request_cost(usage, model_pricing):
    """
    usage: openai UsageResponse object
    model_pricing: dict with keys input_per_mtok, output_per_mtok,
                   cached_input_per_mtok (optional)
    """
    input_cost = (usage.prompt_tokens / 1_000_000) * model_pricing["input_per_mtok"]
    output_cost = (usage.completion_tokens / 1_000_000) * model_pricing["output_per_mtok"]

    # Prompt caching discount (Anthropic / OpenAI)
    cached_tokens = getattr(usage, "prompt_tokens_details", None)
    cached_cost = 0.0
    if cached_tokens and hasattr(cached_tokens, "cached_tokens"):
        # Deduct the discount: we already counted these at full price above
        discount = (cached_tokens.cached_tokens / 1_000_000) * (
            model_pricing["input_per_mtok"] - model_pricing.get("cached_input_per_mtok", 0)
        )
        cached_cost = -discount

    total = input_cost + output_cost + cached_cost

    return {
        "input_tokens": usage.prompt_tokens,
        "output_tokens": usage.completion_tokens,
        "input_cost_usd": input_cost,
        "output_cost_usd": output_cost,
        "cache_discount_usd": cached_cost,
        "total_cost_usd": total,
    }

2.3 Quality Metrics (Online Evaluation)

Instrumenting latency and cost is table stakes. The frontier is online quality monitoring — continuously scoring production responses without blocking the critical path. Common approaches:

  • LLM-as-judge: Route a sampled 5-10% of responses to a fast, cheap judge model (e.g., GPT-4o-mini) that scores on rubrics: factual accuracy, relevance, completeness, tone. Fire-and-forget, async.
  • Heuristic signals: Response length distribution, refusal rate, format compliance (valid JSON, valid Markdown), citation presence for RAG.
  • User feedback: Thumbs up/down, copy actions, follow-up clarification rate as implicit quality signals.
  • Embedding similarity: Cosine similarity between query embedding and response embedding as a weak relevance proxy.

3. Tracing LLM Applications

Distributed Tracing for Multi-Step AI Systems

3.1 Why Traces Matter More Than Metrics for AI

Metrics tell you something is wrong. Traces tell you exactly where and why. For a simple REST API, logs are often enough. For a multi-step AI pipeline — RAG, tool-calling agents, multi-model chains — you need the full causal graph of what happened, in order, with timing and inputs at every step.

Consider a RAG pipeline where answer quality dropped overnight. Metrics show: p95 latency increased 40%, quality score fell 0.12. That could be caused by:

  • Retrieval returning irrelevant chunks (vector index drift)
  • Reranker model silently returning garbage scores
  • System prompt accidentally got double-escaped in a recent deploy
  • Provider model updated to a less capable version
  • Context window is overflowing and truncating relevant chunks

Without traces capturing the retrieved chunks, reranker scores, final prompt content, and token counts per request, you cannot distinguish these cases. With traces, you replay any failing request in seconds.

3.4 Instrumenting with OpenTelemetry (Code Example)

"""
Minimal OpenTelemetry instrumentation for a RAG pipeline.
Uses the OpenTelemetry Python SDK + OTLP exporter.
"""
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource, SERVICE_NAME
import time

# --- Bootstrap the tracer once at startup ---
resource = Resource(attributes={SERVICE_NAME: "rag-api"})
provider = TracerProvider(resource=resource)
otlp_exporter = OTLPSpanExporter(endpoint="http://otel-collector:4317")
provider.add_span_processor(BatchSpanProcessor(otlp_exporter))
trace.set_tracer_provider(provider)

tracer = trace.get_tracer("rag.pipeline", "1.0.0")


def rag_query(user_query: str) -> dict:
    with tracer.start_as_current_span("rag_request") as root_span:
        root_span.set_attribute("rag.query", user_query[:500])  # truncate for safety
        root_span.set_attribute("rag.user_id", get_current_user_id())

        # Step 1 - embed
        with tracer.start_as_current_span("embed_query") as span:
            query_embedding = embed_text(user_query)
            span.set_attribute("gen_ai.operation.name", "embed")
            span.set_attribute("gen_ai.request.model", "text-embedding-3-small")
            span.set_attribute("gen_ai.usage.input_tokens", count_tokens(user_query))

        # Step 2 - retrieve
        with tracer.start_as_current_span("retrieve_documents") as span:
            t0 = time.perf_counter()
            docs = vector_search(query_embedding, k=20)
            span.set_attribute("rag.retrieval.k", 20)
            span.set_attribute("rag.retrieval.results_returned", len(docs))
            span.set_attribute("rag.retrieval.latency_ms", (time.perf_counter()-t0)*1000)

        # Step 3 - rerank
        with tracer.start_as_current_span("rerank_documents") as span:
            reranked = rerank(user_query, docs, top_n=5)
            span.set_attribute("rag.rerank.model", "cohere/rerank-v3")
            span.set_attribute("rag.rerank.top_n", 5)
            span.set_attribute("rag.rerank.top_score", reranked[0].score)

        # Step 4 - generate
        with tracer.start_as_current_span("llm_generate") as span:
            t0 = time.perf_counter()
            response, usage = call_llm(user_query, reranked)
            ttft = get_ttft()  # measured during streaming

            # OpenTelemetry GenAI semantic conventions
            span.set_attribute("gen_ai.operation.name", "chat")
            span.set_attribute("gen_ai.system", "openai")
            span.set_attribute("gen_ai.request.model", "gpt-4o")
            span.set_attribute("gen_ai.response.model", response.model)
            span.set_attribute("gen_ai.usage.input_tokens", usage.prompt_tokens)
            span.set_attribute("gen_ai.usage.output_tokens", usage.completion_tokens)
            span.set_attribute("gen_ai.usage.cost_usd", calculate_cost(usage))
            span.set_attribute("gen_ai.performance.ttft_ms", ttft)
            span.set_attribute("gen_ai.performance.total_ms", (time.perf_counter()-t0)*1000)

        root_span.set_attribute("rag.total_input_tokens", usage.prompt_tokens)
        root_span.set_attribute("rag.total_output_tokens", usage.completion_tokens)
        return {"answer": response.content, "sources": reranked[:3]}

4. Prompt & Response Logging

Structured Logging for LLM Inputs and Outputs

4.1 Why You Must Log Prompts and Responses

Many teams ship LLM applications that log only latency and error codes, treating the actual prompt/response content as ephemeral. This is a serious operational mistake. Without prompt/response logs you cannot:

  • Reproduce a user-reported hallucination to diagnose root cause
  • Build a labeled dataset for offline evaluation from real traffic
  • Audit for compliance (many regulated industries require input/output retention)
  • Debug prompt injection attempts
  • Train or fine-tune on production data
  • Implement effective content moderation pipelines
PII and Privacy Warning Users will inevitably include PII in prompts (names, emails, credit card numbers, health information). You MUST implement PII detection and redaction before writing logs to persistent storage. Storing raw PII in logs likely violates GDPR, HIPAA, CCPA, and your organization's data retention policies.

4.2 PII Redaction Before Logging

"""
PII redaction middleware using presidio (Microsoft's open-source PII detection).
Run: pip install presidio-analyzer presidio-anonymizer
"""
from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine
from presidio_anonymizer.entities import OperatorConfig

analyzer = AnalyzerEngine()
anonymizer = AnonymizerEngine()

# Entities to detect and redact
PII_ENTITIES = [
    "PERSON", "EMAIL_ADDRESS", "PHONE_NUMBER",
    "CREDIT_CARD", "US_SSN", "IP_ADDRESS",
    "LOCATION", "DATE_TIME",
]

def redact_pii(text: str, language: str = "en") -> tuple[str, list]:
    """
    Returns (redacted_text, list_of_found_entities).
    The list of entities is logged separately for audit/alert purposes
    but NOT alongside the redacted content.
    """
    results = analyzer.analyze(text=text, language=language, entities=PII_ENTITIES)

    # Replace PII with labelled placeholders: <EMAIL_ADDRESS>, <PERSON>, etc.
    operators = {
        entity: OperatorConfig("replace", {"new_value": f"<{entity}>"})
        for entity in PII_ENTITIES
    }
    anonymized = anonymizer.anonymize(
        text=text, analyzer_results=results, operators=operators
    )

    found_types = list({r.entity_type for r in results})
    return anonymized.text, found_types


# Example
original = "Hi, I'm Alice Johnson and my email is alice@example.com"
redacted, pii_types = redact_pii(original)
# redacted: "Hi, I'm <PERSON> and my email is <EMAIL_ADDRESS>"
# pii_types: ["PERSON", "EMAIL_ADDRESS"]

4.4 Logging Middleware

"""
Async logging middleware that:
1. Intercepts every LLM call
2. Redacts PII from prompt and response
3. Computes cost
4. Writes structured log asynchronously (non-blocking)
"""
import asyncio
import json
import time
import uuid
from datetime import datetime, timezone
from functools import wraps

class LLMLoggingMiddleware:
    def __init__(self, logger, pii_redactor, cost_calculator, log_buffer_size=100):
        self.logger = logger
        self.pii_redactor = pii_redactor
        self.cost_calculator = cost_calculator
        self._queue = asyncio.Queue(maxsize=log_buffer_size)
        self._flush_task = None

    async def start(self):
        """Start background log flusher."""
        self._flush_task = asyncio.create_task(self._flush_loop())

    async def _flush_loop(self):
        while True:
            batch = []
            try:
                # Collect up to 20 logs or wait 2s
                deadline = time.monotonic() + 2.0
                while len(batch) < 20 and time.monotonic() < deadline:
                    try:
                        item = await asyncio.wait_for(
                            self._queue.get(),
                            timeout=max(0, deadline - time.monotonic())
                        )
                        batch.append(item)
                    except asyncio.TimeoutError:
                        break
                if batch:
                    await self._write_batch(batch)
            except Exception as e:
                self.logger.error(f"Log flush error: {e}")

    async def _write_batch(self, batch):
        # Write to your storage backend (BigQuery, ClickHouse, S3, etc.)
        for record in batch:
            self.logger.info(json.dumps(record))

    async def log_llm_call(
        self, messages, response, usage, model, ttft_ms, total_ms, metadata=None
    ):
        """Non-blocking enqueue of a log record."""
        try:
            # Redact each message
            redacted_messages = []
            for msg in messages:
                redacted_content, pii_types = self.pii_redactor.redact_pii(
                    msg.get("content", "")
                )
                redacted_messages.append({
                    "role": msg["role"],
                    "content_redacted": redacted_content,
                    "pii_detected": pii_types,
                })

            redacted_response, _ = self.pii_redactor.redact_pii(response.content)
            cost = self.cost_calculator(usage, model)

            record = {
                "schema_version": "1.2",
                "timestamp": datetime.now(timezone.utc).isoformat(),
                "request_id": str(uuid.uuid4()),
                "request": {
                    "model": model,
                    "messages": redacted_messages,
                    "input_tokens": usage.prompt_tokens,
                },
                "response": {
                    "content_redacted": redacted_response,
                    "finish_reason": response.finish_reason,
                    "output_tokens": usage.completion_tokens,
                },
                "performance": {
                    "ttft_ms": ttft_ms,
                    "total_ms": total_ms,
                },
                "cost": cost,
                **(metadata or {}),
            }

            # Non-blocking put; drop on overflow rather than block the request
            try:
                self._queue.put_nowait(record)
            except asyncio.QueueFull:
                self.logger.warning("LLM log queue full; dropping record")

        except Exception as e:
            self.logger.error(f"Failed to construct log record: {e}")

5. Drift Detection & Quality Monitoring

Detecting Silent Degradation in AI Systems

Drift is the most insidious failure mode in AI systems because it happens gradually, without exceptions, and is invisible to traditional monitoring. A model that was 90% accurate on Monday might be 72% accurate by Friday after a silent provider model update — and every HTTP response is still 200 OK.

5.1 Types of Drift

Input Drift: Changing User Query Patterns

Input drift occurs when the distribution of user queries changes. This matters because:

  • Your prompt templates may not handle new query types well
  • Retrieved documents may not cover new topic clusters
  • System prompts optimized for old query patterns fail on new ones

Detection approach: Embed all incoming queries with a consistent embedding model. Compute a sliding window centroid of query embeddings. Track the cosine distance between the current window centroid and the baseline centroid (from launch/last evaluation).

Query cluster: "pricing questions" (baseline: 12% → now: 28%)
Query cluster: "technical support" (baseline: 55% → now: 41%)
Query cluster: "refund/complaint" (baseline: 8% → now: 22%) — ALERT
import numpy as np
from scipy.spatial.distance import cosine

def detect_input_drift(
    baseline_embeddings: np.ndarray,
    current_window_embeddings: np.ndarray,
    threshold: float = 0.15
) -> dict:
    """
    Compare centroids of baseline vs. current query embedding windows.
    Returns drift score and whether alert threshold is exceeded.
    """
    baseline_centroid = baseline_embeddings.mean(axis=0)
    current_centroid = current_window_embeddings.mean(axis=0)

    drift_score = cosine(baseline_centroid, current_centroid)

    return {
        "drift_score": float(drift_score),
        "alert": drift_score > threshold,
        "baseline_n": len(baseline_embeddings),
        "current_n": len(current_window_embeddings),
    }
Output Drift: Model Behavior Changes

Output drift occurs when model responses change in distribution without corresponding input changes. Common causes:

  • Provider model swap: OpenAI silently updates "gpt-4o" to a new checkpoint. Response length, verbosity, or reasoning style changes.
  • RLHF policy changes: Provider tunes the model toward different safety thresholds; previously-answered queries start getting refused.
  • Prompt template regression: A deploy changes a system prompt; outputs shift dramatically.

Signals to monitor for output drift:

  • Response length distribution (histogram of output_tokens)
  • Refusal rate (regex or classifier detecting "I cannot", "I'm sorry, but")
  • Format compliance rate (% of responses that parse as valid JSON, Markdown, etc.)
  • LLM-as-judge quality score distribution over time
  • Response embedding centroid drift (same cosine approach as input drift)
from collections import deque
import re

class OutputDriftMonitor:
    """
    Monitors output characteristics over rolling windows.
    Window size of 1000 requests is typical for daily-scale apps.
    """
    def __init__(self, window_size: int = 1000):
        self.window_size = window_size
        self.output_lengths = deque(maxlen=window_size)
        self.refusal_flags = deque(maxlen=window_size)
        self.quality_scores = deque(maxlen=window_size)

        # Baselines set after first stable week in production
        self.baseline_avg_length = None
        self.baseline_refusal_rate = None

    REFUSAL_PATTERNS = re.compile(
        r"i('m| am) (sorry|unable)|i can'?t (help|assist)|"
        r"i (cannot|won'?t)|as an ai|i don'?t have (access|the ability)",
        re.IGNORECASE
    )

    def record(self, response_text: str, quality_score: float = None):
        length = len(response_text.split())
        is_refusal = bool(self.REFUSAL_PATTERNS.search(response_text))
        self.output_lengths.append(length)
        self.refusal_flags.append(int(is_refusal))
        if quality_score is not None:
            self.quality_scores.append(quality_score)

    def get_drift_report(self) -> dict:
        avg_length = sum(self.output_lengths) / len(self.output_lengths)
        refusal_rate = sum(self.refusal_flags) / len(self.refusal_flags)
        avg_quality = (
            sum(self.quality_scores) / len(self.quality_scores)
            if self.quality_scores else None
        )

        alerts = []
        if self.baseline_avg_length:
            length_change_pct = abs(avg_length - self.baseline_avg_length) / self.baseline_avg_length
            if length_change_pct > 0.20:
                alerts.append(f"Response length drift: {length_change_pct:.1%} change from baseline")
        if self.baseline_refusal_rate:
            if refusal_rate > self.baseline_refusal_rate * 2:
                alerts.append(f"Refusal rate doubled: {refusal_rate:.2%} vs baseline {self.baseline_refusal_rate:.2%}")

        return {
            "current_avg_length_words": avg_length,
            "current_refusal_rate": refusal_rate,
            "current_avg_quality": avg_quality,
            "alerts": alerts,
        }
Embedding Drift Detection (MMD / PSI)

For more rigorous drift detection, use statistical tests on embedding distributions rather than just centroid distance. Two common approaches:

Population Stability Index (PSI) — Originally from credit risk modeling, PSI measures how much a distribution has shifted between a baseline and current period. PSI < 0.1: stable, 0.1–0.25: moderate shift, > 0.25: major shift.

Maximum Mean Discrepancy (MMD) — A kernel-based two-sample test that measures distance between two distributions in a reproducing kernel Hilbert space. Works well in high dimensions (embedding spaces). More statistically principled than PSI but computationally heavier. 

import numpy as np

def compute_psi(baseline_dist: np.ndarray, current_dist: np.ndarray, bins: int = 10) -> float:
    """
    PSI for 1D distributions (use on PCA-reduced embeddings for efficiency).
    Returns PSI score.
    """
    # Compute histograms with shared bins
    min_val = min(baseline_dist.min(), current_dist.min())
    max_val = max(baseline_dist.max(), current_dist.max())
    bin_edges = np.linspace(min_val, max_val, bins + 1)

    baseline_counts, _ = np.histogram(baseline_dist, bins=bin_edges)
    current_counts, _  = np.histogram(current_dist,  bins=bin_edges)

    # Avoid log(0): clip to small value
    baseline_pct = np.clip(baseline_counts / baseline_counts.sum(), 1e-6, None)
    current_pct  = np.clip(current_counts  / current_counts.sum(),  1e-6, None)

    psi = np.sum((current_pct - baseline_pct) * np.log(current_pct / baseline_pct))
    return float(psi)


def compute_mmd_rbf(X: np.ndarray, Y: np.ndarray, gamma: float = 1.0) -> float:
    """
    Unbiased MMD^2 estimate using RBF kernel.
    X: baseline embeddings (n, d), Y: current embeddings (m, d)
    """
    def rbf_kernel(A, B):
        # ||A_i - B_j||^2
        diff = A[:, None, :] - B[None, :, :]  # (n, m, d)
        sq_dist = (diff ** 2).sum(-1)           # (n, m)
        return np.exp(-gamma * sq_dist)

    n, m = len(X), len(Y)
    K_XX = rbf_kernel(X, X)
    K_YY = rbf_kernel(Y, Y)
    K_XY = rbf_kernel(X, Y)

    mmd2 = (
        (K_XX.sum() - np.trace(K_XX)) / (n * (n - 1))
        + (K_YY.sum() - np.trace(K_YY)) / (m * (m - 1))
        - 2 * K_XY.mean()
    )
    return float(mmd2)

In practice, apply PCA to reduce 1536-dim embeddings to 32–64 dimensions before computing PSI/MMD. This makes computation fast enough to run on every 1,000-request batch.

7. Building an Observability Stack

Architecture: Collection to Visualization

7.1 Layered Architecture

Layer 1: Collection

OTel SDK in application code emits spans, metrics, and logs via OTLP. An OTel Collector receives, filters, enriches (adds environment, version tags), and batches signals. Collection should add less than 5ms of overhead.

Layer 2: Processing

The Collector's processors pipeline: batch processor for efficiency, span-to-metrics conversion (spanmetrics processor) to derive RED metrics from traces, tail sampling to keep 100% of error traces + 5% of success traces, and attribute filtering to strip high-cardinality or sensitive data.

Layer 3: Storage

Traces: Jaeger (self-hosted) or Tempo (Grafana stack) — stores full trace/span data, queryable by trace_id or attribute. Metrics: Prometheus (pull-based scraping, short retention) or VictoriaMetrics (long-term, scalable). Logs: Loki (Grafana stack) for structured log storage, ClickHouse for analytical log queries.

Layer 4: Visualization & Alerting

Grafana: unified dashboards pulling from Prometheus (metrics), Jaeger/Tempo (traces), Loki (logs). Alertmanager: routes alerts to PagerDuty, Slack, OpsGenie. AI-specific: Arize, LangSmith, or Braintrust for quality dashboards that Grafana cannot natively represent.

7.3 Cost of Observability at Scale

Observability itself has a cost. At 1 million LLM requests per day:

  • Trace storage: Average RAG trace ≈ 50 spans × ~500 bytes/span = ~25 KB/trace. 1M traces/day = 25 GB/day raw. With 5% sampling and compression: ~300 MB/day stored — negligible on Jaeger.
  • Metric cardinality: The combinatorial explosion of labels (model × provider × app × status) can create high cardinality. Design label sets carefully — 10 models × 5 providers × 20 apps = 1,000 series (fine). Adding user_id as a label = millions of series (will crash Prometheus).
  • Log storage: Full prompt/response logging at 1M req/day × 500 bytes average = 500 MB/day compressed = ~180 GB/year. At S3 rates: $4.10/year. Cheap enough to always do.
  • OTel Collector CPU: Typical Collector handles 10,000–50,000 spans/second on 1 CPU core. For 1M req/day (≈12 req/s × 8 spans each ≈ 100 spans/s), a single Collector instance is massively overprovisioned.

8. Staff-Level Interview Angle

What Interviewers Assess at the Staff Level

Staff-level observability questions test whether you think about monitoring as a system design problem, not a configuration task. Interviewers at this level are looking for:

What They're Really Asking

  • "How would you monitor this AI feature in production?"
    They want to hear: golden signals adapted for AI (TTFT, quality score, cost), tracing at every AI boundary, async quality evaluation, drift detection, and a rollback mechanism triggered by quality SLOs — not just "add Datadog."
  • "How do you know your RAG system is working?"
    Strong answer: online retrieval metrics (recall@k via LLM judge on sampled queries), embedding drift monitoring, chunk citation rate, user follow-up clarification rate as implicit signal.
  • "A model provider updates their model silently. How do you detect it?"
    Strong answer: Response embedding centroid drift alert (cosine distance from baseline), response length distribution shift, refusal rate change, scheduled regression against a golden dataset in CI, and canary deployment with quality gate comparison.

Design Principles to Demonstrate

  • Observability as a feature, not an afterthought: Build structured logging, span context, and quality sampling into the system from day one. Retrofitting is 5× the work.
  • Separate telemetry planes: Infrastructure metrics (Prometheus) and AI quality metrics (LangSmith/Arize) require different tools and query patterns. Don't force-fit quality into infra dashboards.
  • Asymmetric sampling: 100% of error/low-quality traces; 5% of normal-path traces. Cost-effective and ensures you always have context for incidents.
  • Feedback loops: Every quality score, user thumbs down, and eval failure should flow back into your dataset. Observability data powers your next fine-tune.
  • Defense in depth: No single metric catches all failures. Layer TTFT, refusal rate, output length, quality score, and embedding drift — different failures manifest in different signals.

Red Flags to Avoid

  • Only proposing HTTP-level metrics (status codes, latency) without AI-specific signals
  • Suggesting logging full raw prompts to a high-cardinality trace attribute (will kill your trace backend)
  • No mention of PII redaction in logging design
  • Treating online eval as blocking (synchronous) on the critical path
  • No drift detection strategy — only monitoring "is the system up?"
  • Proposing a single quality metric (e.g., just thumbs up/down) without complementary signals

Example Strong Answer Structure (STAR)

Situation: "We have a RAG-based support chatbot processing 200K daily conversations and I need to ensure quality doesn't degrade silently after model or data updates."

Task: "Design observability covering: latency (TTFT, ITL, total), cost (per-request, per-model), quality (online eval, user signals), and drift (input patterns, output distribution, retrieval quality)."

Action: "I would instrument every LLM call with OTel spans using gen_ai.* attributes, run async LLM-as-judge on 10% of responses, track embedding centroid drift weekly, alert on response distribution shifts, and store structured logs (PII-redacted) in ClickHouse for fast debugging and dataset construction."

Result: "This provides sub-1-hour detection of quality regressions, full request replay capability for any incident, and a continuous data flywheel for eval set expansion."

9. Active Recall Questions

Test your understanding. Think through each answer before revealing it.

Why does HTTP 200 tell you almost nothing about LLM response quality?
HTTP 200 only tells you the server received your request and returned a response without a transport or application-level error. LLMs can and frequently do return 200 OK with responses that: hallucinate facts, refuse to answer, go off-topic, include toxic content, violate the expected output format, or truncate context mid-sentence. The semantic correctness of a generated text response is entirely invisible to HTTP-level monitoring. You need AI-specific signals: quality scores, refusal detection, format validation, and embedding similarity to determine whether a 200 OK was actually useful.
Explain the difference between TTFT and ITL and why a user-facing chat application cares about both.
Time to First Token (TTFT) is the delay between sending the request and receiving the first token. This governs the "blank screen" experience — how long the UI looks frozen before anything appears. High TTFT feels like lag and drives user abandonment.

Inter-Token Latency (ITL) is the average time between consecutive tokens once streaming starts. This governs the "reading speed" of the output. If ITL is 100ms per token (10 tok/s), the text feels like it's being typed slowly. At 50 tok/s (20ms/token), it feels instant.

For a chat interface: TTFT should be under 1.5s p95 (responsiveness), and ITL should yield at least 20 tok/s (readable streaming speed). You can have great TTFT and terrible ITL (backend drops connection mid-generation) or great ITL and terrible TTFT (long prefill queue). Total generation time conflates both and is a poorer diagnostic signal.
You notice quality scores dropped 0.12 overnight. Walk through how you would diagnose the root cause using observability data.
1. Check the timeline: When exactly did the drop start? Correlate with deploys, config changes, or provider status pages.

2. Check output distribution: Did response length change? Did refusal rate spike? These point to a provider RLHF update or prompt regression.

3. Check input drift: Did query embedding centroid shift? New query patterns the system isn't equipped for. Compare query cluster distribution before/after.

4. Inspect traces of low-quality requests: In LangSmith/Arize, filter to quality_score < 0.5. Look at: what was retrieved (chunk scores), what was in the prompt (token count, system prompt version), what model version was returned in gen_ai.response.model.

5. Check retrieval metrics: Did retrieval latency spike? Were fewer relevant chunks returned (top_chunk_score distribution changed)? Vector index staleness?

6. Compare model versions: If gen_ai.response.model changed (e.g., "gpt-4o-2024-05-13" → "gpt-4o-2024-08-06"), run your golden eval set against both versions to confirm behavioral difference.

A well-instrumented system should pinpoint the layer within 30 minutes.
What is Population Stability Index (PSI) and how do you apply it to detect LLM input drift?
PSI is a statistical measure of how much a distribution has shifted between a baseline period and a current period. It is calculated as: PSI = Σ (current_% - baseline_%) × ln(current_% / baseline_%) across histogram bins.

Interpretation: PSI < 0.1 = stable, 0.1–0.25 = moderate shift (investigate), > 0.25 = major shift (alert).

For LLM input drift: Embed all incoming user queries with a consistent embedding model (the same one used at baseline). Apply PCA to reduce from 1536 to ~32 dimensions. Compute PSI on each principal component between the baseline window (e.g., first 10,000 queries after launch) and the current rolling window. A PSI > 0.25 on any of the top-3 components indicates the query distribution has shifted significantly enough to warrant re-evaluation of prompt coverage, retrieval index freshness, and system prompt alignment.
Why is high cardinality a critical concern when designing Prometheus labels for LLM metrics?
Prometheus stores a separate time series for every unique combination of label values. High cardinality means an exponential explosion of time series, which increases memory usage, query latency, and can crash Prometheus or cause OOM kills on the metrics backend.

In LLM systems, the dangerous labels are: user_id (millions of unique users), request_id (billions of unique values), prompt_hash (unbounded). These should NEVER be label values — only stored in traces and logs.

Safe high-level labels: model (5-20 values), provider (3-10 values), application (5-30 values), status (success/error/timeout), finish_reason (stop/length/content_filter). Even 20 models × 10 providers × 30 apps × 3 statuses = 18,000 series — well within Prometheus limits (10M series is the practical ceiling on medium hardware, but keeping to thousands is better practice).

Rule of thumb: if a label value can come from user input or per-request identity, it must not be a metric label.
Describe a production-safe architecture for logging full prompt and response content at scale.
Key constraints: PII must be redacted before persistence; logging must be non-blocking (async queue); storage must be cost-efficient and queryable.

Architecture:
1. PII redaction middleware (Presidio or equivalent) runs synchronously before enqueuing — adds ~5ms but protects against accidental PII storage.
2. In-process async queue (asyncio.Queue, bounded to 1,000 items): the request handler enqueues the log record and returns immediately. A background coroutine drains the queue in batches of 20 every 2 seconds.
3. Batch writer sends compressed NDJSON to S3 (archive, low cost, long retention) AND ClickHouse (fast analytical queries for debugging).
4. Retention policies: ClickHouse hot storage: 30 days; S3 cold storage: 2 years (compliance). Encrypt at rest; access-controlled.
5. Prompt/response content is NOT in OTel spans (too large, high-cardinality, inappropriate for trace backends). Traces carry the request_id for cross-referencing to the log store.
6. Sampling: For cost at massive scale (100M+ req/day), log 100% of error/low-quality requests and 20% of normal requests for the analytical backend while always archiving to S3.

11. Flashcard Suggestions

Export these to Anki or your preferred spaced-repetition system for long-term retention.

Q
What is TTFT and what user experience does it affect?
Time to First Token: time from request to the first streaming token. Governs the "blank screen" latency — how long the UI appears frozen. Target: p95 under 1.5 seconds for chat interfaces.
Q
Why can't you use error rate alone to detect LLM failures?
LLMs return HTTP 200 even for hallucinated, toxic, refused, or off-topic responses. Error rate captures infrastructure failures but is blind to semantic quality failures — the most common AI failure mode.
Q
What are the gen_ai.* OTel semantic conventions and why do they matter?
Standardized OpenTelemetry span attribute names for AI: gen_ai.system, gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.response.finish_reasons, etc. Enables observability tools to parse, aggregate, and visualize LLM telemetry consistently without custom parsing.
Q
What PSI threshold indicates major distribution drift and what action should trigger?
PSI > 0.25 = major shift (alert + investigate). PSI 0.10–0.25 = moderate shift (monitor closely). PSI < 0.10 = stable. On major drift: run offline eval against golden dataset; validate prompt coverage for new query patterns.
Q
Why is user_id a dangerous Prometheus label? What should you do instead?
user_id creates millions of unique label combinations = millions of time series = Prometheus OOM. Instead: use user_id only in traces and logs (queryable by request_id). Use low-cardinality aggregates (user_tier: free/pro/enterprise) in metrics if user-level attribution is needed.
Q
What is the recommended sampling strategy for LLM traces in production?
Asymmetric tail sampling: 100% of error traces and low-quality traces (quality_score < threshold), 5–10% of normal-path traces. This ensures full diagnostic context for all incidents while controlling storage costs at high volume.
Q
Name three signals that indicate a provider has silently updated their model.
1. gen_ai.response.model value changes in spans. 2. Response length distribution shifts >20% from baseline. 3. Refusal rate changes significantly (RLHF policy difference). Also: cosine drift in response embedding centroids and quality score drop on golden eval set.
Q
Why must PII redaction happen before logging, not after?
Once PII is written to a log store, it is extremely difficult to retroactively remove (distributed copies, backups, WAL). Redaction must happen in the application process before the data leaves the trust boundary, to comply with GDPR right-to-erasure, HIPAA minimum necessary use, and organizational data retention policies.
