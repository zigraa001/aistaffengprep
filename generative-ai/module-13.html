1. Why Inference Matters

The Economics of Training vs. Inference ▼

Training is a one-time event. Inference is forever.

Training GPT-4 cost an estimated $50M–$100M in compute. That sounds large — but at scale, inference dwarfs training cost within months of launch. OpenAI's inference bill is estimated to be several hundred million dollars per month as of 2024. Training is capex (a bet you make once). Inference is opex (the tax you pay every single day).

This asymmetry means that a 2x improvement in inference efficiency compounds continuously. A 2x better inference stack halves your monthly burn rate every single month. At $100M/month, that's $600M saved per year.

The Staff Engineer's Frame

At staff level, you're not just picking a server. You're designing a token economy: every architectural decision — batch size, quantization level, hardware tier, autoscaling policy — has a direct dollar cost and a direct latency SLA. The best inference engineers can reason about all three simultaneously: cost, latency, and throughput.

  • Cost = GPU-hours consumed per million tokens
  • Latency = Time to First Token (TTFT) and Inter-Token Latency (ITL)
  • Throughput = Tokens per second across all concurrent requests

These three form an iron triangle. Optimizing one without thinking about the others is a common junior mistake. Staff-level decisions explicitly state which vertex they're sacrificing.

2. GPU Serving Fundamentals

GPU Architecture for Inference ▼

Inference on large language models is memory-bandwidth-bound, not compute-bound. Understanding why requires looking at how a GPU actually works.

The Three Bottlenecks in GPU Inference

Resource A100 (80GB SXM) H100 (80GB SXM) Role in Inference
VRAM Capacity 80 GB HBM2e 80 GB HBM3 Holds model weights + KV cache
Memory Bandwidth 2.0 TB/s 3.35 TB/s Rate of loading weights per token decode
FP16 TFLOPS 312 TFLOPS 989 TFLOPS Prefill phase (compute-bound with large batches)
NVLink bandwidth 600 GB/s 900 GB/s Tensor parallelism across GPUs
Streaming Multiprocessors 108 SMs 132 SMs Parallel execution units
Why memory bandwidth is the bottleneck during decode: For each token generated, the GPU must read all model weights from VRAM once. A 70B parameter model in FP16 = 140 GB of weights. Even on an H100, loading 140 GB at 3.35 TB/s takes ~42 ms per decode step per batch element — if your batch is small. The GPU's 989 TFLOPS of compute sits idle most of that time. This is why techniques like quantization (reducing bytes per weight) and batching (amortizing the memory load across many requests) are so impactful.

Streaming Multiprocessors (SMs): The Execution Unit

Each SM on an H100 contains 128 CUDA cores and can run thousands of threads simultaneously via warp scheduling. For inference, what matters is how well the kernel fills these SMs:

  • Prefill (prompt processing): Matrix multiplications over long sequences saturate SMs well. This is compute-bound. Large batches help.
  • Decode (token generation): Each step is a matrix-vector multiply (single token against weight matrices). This uses SMs inefficiently unless you run many requests in parallel.

This asymmetry between prefill and decode is the fundamental reason inference is hard to optimize: they have opposite bottlenecks.

KV Cache: The Silent VRAM Killer ▼

The KV cache stores the attention key and value tensors for every token in every layer, so they don't have to be recomputed on each decode step. It's what makes autoregressive generation tractable — but it consumes enormous VRAM.

KV Cache Size Formula

"""
KV Cache memory formula:

  kv_bytes = 2               # keys + values
           * num_layers
           * num_kv_heads
           * head_dim
           * seq_len
           * batch_size
           * bytes_per_element

For LLaMA 3 70B (FP16):
  - num_layers    = 80
  - num_kv_heads  = 8   (GQA: grouped query attention)
  - head_dim      = 128
  - seq_len       = 8192
  - batch_size    = 32
  - bytes         = 2 (FP16)

kv_bytes = 2 * 80 * 8 * 128 * 8192 * 32 * 2
         = 2 * 80 * 8 * 128 * 8192 * 32 * 2
         = 85,899,345,920 bytes
         ~ 80 GB

That's the ENTIRE A100 just for KV cache at batch=32, seq=8192!
This is why vLLM's PagedAttention was a breakthrough:
it avoids pre-allocating contiguous memory per sequence.
"""

def kv_cache_gb(num_layers, num_kv_heads, head_dim,
                seq_len, batch_size, dtype_bytes=2):
    total = (2 * num_layers * num_kv_heads * head_dim
             * seq_len * batch_size * dtype_bytes)
    return total / (1024**3)

# LLaMA 3 70B with GQA, FP16
print(kv_cache_gb(80, 8, 128, 4096, 16))   # ~20 GB
print(kv_cache_gb(80, 8, 128, 8192, 32))   # ~80 GB

# Mistral 7B (32 layers, 8 kv_heads, head_dim=128)
print(kv_cache_gb(32, 8, 128, 4096, 32))   # ~4 GB

3. Inference Servers Deep Dive

The Major Inference Runtimes ▼

vLLM Throughput Champion Open Source

Core innovation: PagedAttention. Before vLLM (2023, UC Berkeley), every inference server pre-allocated a contiguous block of VRAM for each request's KV cache — based on the maximum possible sequence length. This wasted 60-80% of KV cache memory due to internal fragmentation. PagedAttention borrows the paging concept from OS virtual memory: the KV cache is divided into fixed-size pages (blocks), allocated on demand, and can be non-contiguous in physical VRAM.

  • PagedAttention: Non-contiguous KV cache blocks, near-zero memory waste
  • Continuous batching: Iteration-level scheduling (explained in Section 4)
  • Prefix caching: Reuse KV cache for shared prompt prefixes (e.g., system prompts)
  • Chunked prefill: Break long prefills into chunks to reduce TTFT variance
  • Speculative decoding: Use a small draft model to propose multiple tokens
  • Multi-LoRA serving: Serve many LoRA adapters on one base model

Best for: High-throughput production serving, when you need to squeeze maximum tokens/second per GPU dollar.

Weakness: Not always the fastest at single-request low-latency scenarios. TensorRT-LLM can beat it on raw TTFT for well-optimized models.

TensorRT-LLM NVIDIA Official Highest Raw Perf

NVIDIA's hand-optimized inference runtime. TensorRT-LLM compiles your model into a TensorRT engine with fused CUDA kernels, INT8/FP8/INT4 quantization via AMMO, and hardware-specific optimizations. It requires a compilation step per GPU architecture (Ampere vs. Hopper) and model configuration, but the resulting throughput is the highest available on NVIDIA hardware.

  • Fused kernels: FlashAttention, RMSNorm + Linear fused, custom GEMM kernels
  • INT4/INT8 via AMMO: Activation-aware quantization, W4A8 (weights INT4, activations INT8)
  • In-flight batching: TRT-LLM's version of continuous batching (called "inflight batching")
  • Triton backend: Deploys via NVIDIA Triton Inference Server
  • FP8 on Hopper (H100): H100 has dedicated FP8 Tensor Cores — 2x speedup over FP16

Best for: Maximum throughput and minimum latency on NVIDIA hardware, when you're willing to pay the compilation overhead and tight NVIDIA dependency.

Weakness: Complex build process, NVIDIA-only, less flexible for rapid experimentation.

Text Generation Inference (TGI) Hugging Face Easy Deploy

Hugging Face's production inference server. TGI is written in Rust (server) + Python (model execution) and is the default way to deploy Hugging Face models. It pioneered continuous batching in the open-source space and supports flash attention, Paged Attention (via a vLLM integration), and streaming via Server-Sent Events.

  • Token streaming: SSE-based streaming for real-time token delivery to clients
  • FlashAttention 2: Memory-efficient attention computation built-in
  • GPTQ / AWQ quantization: Load pre-quantized models directly
  • Watermarking: Optional LLM watermarking (Kirchenbauer et al.)
  • OpenAI-compatible API: Drop-in replacement for OpenAI chat completions endpoint

Best for: Teams already in the Hugging Face ecosystem, rapid deployment, when ease-of-use matters more than squeezing the last 20% of throughput.

Triton Inference Server NVIDIA Multi-model

NVIDIA's production-grade, multi-model, multi-framework serving platform. Triton is not an LLM-specific server — it supports TensorFlow, PyTorch, ONNX, TensorRT, and custom Python/C++ backends. For LLMs, it acts as the orchestration layer on top of TensorRT-LLM. At companies running many model types simultaneously (CV models, embedding models, LLMs), Triton provides a unified serving plane.

  • Model ensemble: Chain multiple models (e.g., tokenizer → LLM → detokenizer) as a pipeline
  • Dynamic batching: Automatic batching for non-LLM models
  • Multi-GPU / multi-node: Tensor and pipeline parallelism via MPI
  • GRPC + HTTP: KServe v2 protocol support
  • Metrics: Prometheus-compatible metrics out of the box

Best for: Enterprises with heterogeneous model fleets, when you want a single serving platform for all ML workloads.

Ollama / llama.cpp Local / Edge CPU Support

Local inference for consumer hardware. llama.cpp is a pure C++ inference engine that runs quantized models on CPU, Apple Silicon (Metal), and consumer NVIDIA/AMD GPUs. It pioneered the GGUF model format (successor to GGML) for quantized weights. Ollama wraps llama.cpp with a developer-friendly CLI and API server.

  • GGUF format: Quantized model weights (Q4_K_M, Q5_K_M, Q8_0 etc.) fitting in consumer RAM/VRAM
  • CPU inference: Can run 7B models on a MacBook Pro (slowly) — unique among these options
  • Apple Metal: GPU acceleration on M-series chips with full unified memory
  • Low concurrency: Not designed for multi-user serving at scale
  • Developer-first: Ollama's CLI is the fastest way to experiment locally

Best for: Local development, privacy-sensitive local deployments, edge inference, developer tooling. Not for high-throughput production serving.

Code: Deploy a Model with vLLM ▼

Production vLLM Deployment (Python)

# Install: pip install vllm

# --- Option 1: OpenAI-compatible API server (most common) ---
# Run from shell:
#   python -m vllm.entrypoints.openai.api_server \
#     --model meta-llama/Meta-Llama-3-70B-Instruct \
#     --tensor-parallel-size 2 \
#     --max-model-len 8192 \
#     --gpu-memory-utilization 0.90 \
#     --max-num-batched-tokens 32768 \
#     --enable-prefix-caching \
#     --port 8000

# --- Option 2: Python API (for embedding in your service) ---
from vllm import LLM, SamplingParams
from vllm.engine.arg_utils import AsyncEngineArgs
from vllm.engine.async_llm_engine import AsyncLLMEngine
import asyncio, uuid

# Synchronous (dev/testing)
llm = LLM(
    model="meta-llama/Meta-Llama-3-8B-Instruct",
    tensor_parallel_size=1,       # GPUs to use
    gpu_memory_utilization=0.85,  # Leave 15% for KV cache headroom
    max_model_len=4096,
    enable_prefix_caching=True,   # Cache shared system prompts
    quantization="awq",           # Load pre-quantized AWQ model
)

sampling = SamplingParams(
    temperature=0.7,
    top_p=0.95,
    max_tokens=512,
    stop=["<|eot_id|>"],
)

prompts = [
    "Explain the CAP theorem in two sentences.",
    "What is the difference between TCP and UDP?",
]

outputs = llm.generate(prompts, sampling)
for output in outputs:
    print(output.outputs[0].text)

# --- Option 3: Async engine for production FastAPI ---
async def serve_vllm():
    engine_args = AsyncEngineArgs(
        model="meta-llama/Meta-Llama-3-8B-Instruct",
        tensor_parallel_size=1,
        gpu_memory_utilization=0.85,
        max_model_len=4096,
        enable_prefix_caching=True,
    )
    engine = AsyncLLMEngine.from_engine_args(engine_args)

    request_id = str(uuid.uuid4())
    sampling_params = SamplingParams(temperature=0.7, max_tokens=256)

    # Streaming generation
    async for output in engine.generate(
        "Tell me about inference optimization.",
        sampling_params,
        request_id=request_id,
    ):
        if output.outputs:
            token = output.outputs[0].text
            # yield token to streaming response
            print(token, end="", flush=True)

# --- Key tuning parameters ---
# gpu_memory_utilization: Higher = more KV cache pages = more concurrent requests
#   but leaves less room for activations. 0.85-0.90 is typical.
# max_num_batched_tokens: Limits tokens across ALL requests in one forward pass.
#   Higher = better GPU utilization, higher memory pressure.
# enable_prefix_caching: Reuse KV cache for identical prompt prefixes.
#   ~50-70% latency reduction for system-prompt-heavy applications.

4. Continuous Batching & Scheduling

Static vs. Dynamic vs. Continuous Batching ▼

Static Batching: The Naive Approach

In static batching, the server waits to collect a fixed number of requests (e.g., 32), runs them all through the model together, and releases the GPU only when all requests in the batch are complete. The problem:

  • Requests finish at different times (different output lengths)
  • Short requests (say, 20 tokens) block the GPU slot until the longest request (say, 500 tokens) finishes
  • GPU utilization drops sharply as requests complete; you're paying for idle compute
  • Real-world GPU utilization: 20-40% under typical load distributions

Continuous Batching: Iteration-Level Scheduling

Pioneered in the "Orca" paper (OSDI 2022) and popularized by vLLM, continuous batching treats each decode iteration (one token generation step) as the scheduling unit rather than the entire request. After every decode step:

  1. Check if any request finished (emitted EOS token)
  2. If yes, immediately evict that request from the batch
  3. Fill the freed slot with the next waiting request (run its prefill)
  4. Continue decode for all remaining requests

This keeps GPU utilization near 80-95% because there's almost always a new request ready to fill a freed slot. Throughput improvement over static batching: 10-23x in real benchmarks (from the vLLM paper).

Preemption Strategies & Memory Pressure ▼

When a new high-priority request arrives but there are no free KV cache blocks (all VRAM is occupied by in-progress requests), the scheduler must choose a preemption strategy:

Preemption Options

Strategy Mechanism Pros Cons
Swap to CPU Move KV cache blocks of a low-priority request from GPU VRAM to CPU RAM Can resume the preempted request later without recomputation PCIe bandwidth bottleneck (~64 GB/s) adds latency; CPU RAM limited
Recompute Discard the KV cache; rerun prefill when the request gets GPU time again No extra memory needed; simpler implementation Wastes compute re-running prefill; increases latency for preempted requests
Chunked prefill Don't admit the full new request at once; interleave prefill chunks with decode steps Reduces memory pressure spikes; more predictable latency More complex scheduling; prefill takes longer to complete

vLLM uses swap-to-CPU by default and falls back to recompute. The right choice depends on your SLA: if all requests are interactive, recompute is simpler; if some are background batch jobs, swap is preferable.

TTFT (Time to First Token) = network latency + queuing time + prefill time
ITL (Inter-Token Latency) = time per decode step = f(batch_size, model_size, memory_bandwidth)
E2E Latency = TTFT + (output_tokens × ITL)

Why These Phase Are Fundamentally Different

Prefill processes all N prompt tokens in a single forward pass using matrix multiplications (QKV projection, attention over all pairs, FFN). With N=4096 tokens and a large batch, this is massively parallel and saturates the GPU's compute units. An A100 can prefill 4096 tokens in ~50ms for a 7B model.

Decode generates exactly one new token per forward pass, using the KV cache to avoid recomputing attention over previous tokens. Each decode step requires reading all model weights from VRAM — 16 GB for 8B FP16, 140 GB for 70B FP16. At 3.35 TB/s bandwidth (H100), a 70B model decode step takes at minimum 42ms, regardless of how fast the compute cores are.

The practical implication: To reduce ITL for large models, you must either (a) reduce weight size via quantization, (b) increase memory bandwidth via better hardware, or (c) amortize the memory load across more requests by increasing batch size. Options (a) and (c) are in your control today.
Speculative Decoding ▼

Speculative decoding exploits the fact that prefill is much faster than decode, and that a smaller "draft" model can usually predict the next few tokens correctly. It produces a speedup by letting the small model propose tokens cheaply, then verifying them all at once with the large model.

Algorithm Walkthrough

1
Draft phase: Run a small model (e.g., 3B draft for a 70B target) autoregressively to generate k candidate tokens (typically k=4-8). Cost: cheap, memory-bandwidth of the 3B model.
2
Verify phase: Feed the original prompt + all k draft tokens to the large target model in a single prefill-style forward pass. This processes all k+1 positions in parallel. Cost: one forward pass of the 70B model (the same cost as 1 decode step).
3
Accept/reject: Compare the target model's logits at each position against the draft model's choices using rejection sampling. Accept tokens where the draft was likely correct; reject at the first mismatch and resample.
4
Result: If the draft accepts on average a tokens per round (acceptance rate), you effectively generate a+1 tokens per large model forward pass instead of 1. For good draft models on repetitive tasks, a can be 3-5, giving 2-4x speedup.
Critical property: Speculative decoding is lossless — the output distribution is provably identical to running the target model alone. You trade compute (running the draft model) for reduced wall-clock latency. It works best when outputs are predictable (code completion, templated text), and worst when outputs are highly creative/random.

Variants

  • Medusa: Adds multiple prediction heads on top of the main model instead of a separate draft model. Simpler, no separate draft model weights, but heads must be trained on your specific base model.
  • Eagle: Learns a lightweight draft model by distilling from the target's hidden states. 3-4x speedup, widely used in production.
  • Self-speculative decoding: Skip early layers for draft generation — no separate model at all. Lower overhead but lower acceptance rates.
  • Prompt lookup decoding: For RAG/document QA, use copy-paste from the prompt as draft tokens. Near-zero cost, works well when output copies input text.
Tensor Parallelism vs. Pipeline Parallelism for Inference ▼

When Your Model Doesn't Fit on One GPU

Strategy How it Works Latency Impact Throughput Impact Best For
Tensor Parallelism (TP) Split each weight matrix across GPUs (column/row sharding). Each GPU computes a partial result; they all-reduce at the end of each layer. Adds all-reduce latency per layer (~1ms on NVLink). Reduces per-GPU memory pressure → smaller KV cache. Can decrease throughput if NVLink bandwidth is the bottleneck. Low-latency serving; tight NVLink interconnect (e.g., DGX node)
Pipeline Parallelism (PP) Assign consecutive transformer layers to different GPUs. GPU 1 processes layers 1-20, GPU 2 processes 21-40, etc. Adds pipeline bubble overhead; increased TTFT for single requests. Can achieve high throughput with large enough batch across pipeline stages. Batch/offline inference; when GPUs are connected via PCIe (not NVLink)
Expert Parallelism (EP) For MoE models (Mixtral, DeepSeek): route different experts to different GPUs. Communication per token goes to different GPU based on routing. Near-linear scaling for MoE models with good load balance. MoE model serving specifically
Sequence Parallelism Distribute the sequence dimension across GPUs (for long-context inference). High communication overhead per step. Enables very long contexts (1M+ tokens) that wouldn't fit on one GPU. Extreme long-context scenarios
Rule of thumb: Use TP=N where N is the number of GPUs on a single NVLink node (e.g., 4 or 8). Use PP only when you need to span multiple nodes over Infiniband. Mixing TP and PP (e.g., TP=4 across a node, PP=2 across two nodes) is common for 70B+ models in production.

6. Autoscaling Strategies

Scaling Metrics and Kubernetes GPU Scheduling ▼

What to Scale On

Unlike CPU services where requests-per-second is the obvious scaling metric, LLM services have several competing signals. Choosing the wrong one leads to over- or under-provisioning.

Metric Meaning Problem Verdict
GPU Utilization % How busy is the GPU compute Memory-bound decode keeps GPU at 30-50% even when overloaded Poor signal for LLMs
Requests per second Number of completed requests/sec A request generating 10 tokens is very different from one generating 1000 Misleading without token normalization
Queue depth Pending requests in the scheduler queue Good leading indicator; react before latency degrades Good
P95 TTFT 95th percentile time to first token Lagging indicator — you're already degraded by the time this fires Use as SLA alarm, not primary scaler
KV cache utilization % Fraction of allocated KV cache blocks in use When >85%, new requests queue up. Leading indicator before latency degrades. Best primary signal
Active batch size Number of requests currently in continuous batch Directly tied to decode latency; linear relationship to ITL Excellent
Recommended autoscaling stack: Scale up when kv_cache_utilization > 85% OR queue_depth > N. Scale down when both drop below 30% for 5 minutes. Set your HPA custom metrics via KEDA (Kubernetes Event-Driven Autoscaler) consuming Prometheus metrics exported by vLLM.

Multi-Instance GPU (MIG): Sharing a GPU

NVIDIA's A100 and H100 support MIG, which partitions a single GPU into up to 7 isolated instances, each with dedicated VRAM and compute. This is powerful for right-sizing:

  • 1x A100 80GB MIG 7g.80gb: Full GPU — use for 70B models
  • 2x A100 MIG 3g.40gb: Two 40GB partitions — run two 7B FP16 models simultaneously
  • 7x A100 MIG 1g.10gb: Seven 10GB partitions — run seven small models or seven copies of a quantized 7B model

MIG is static at runtime — you must configure partitions before starting workloads and cannot change them without draining the GPU. For dynamic workloads, time-sharing (CUDA MPS) is more flexible but less isolated.

Cold Start Problem & Solutions ▼

The cold start problem for GPU inference is severe: loading a 70B FP16 model from S3 to VRAM takes 3-10 minutes. This makes serverless GPU inference challenging — a user waiting for a cold start is already gone.

Cold Start Mitigation Techniques

1
Pre-warming / minimum replicas: Keep at least 1 replica always running. Cost: 1 idle GPU. Acceptable for revenue-critical paths. Most services use minReplicas=1 in K8s HPA.
2
Model weight caching on node-local NVMe: Pre-pull model weights to the node's local SSD. Loading from NVMe (6 GB/s) is 10x faster than S3 (600 MB/s effective). Kubernetes node selectors + DaemonSets can pre-pull weights to designated nodes.
3
Predictive pre-warming: Analyze traffic patterns and pre-scale 5 minutes before expected peak. Works well for predictable diurnal traffic. Use time-series forecasting (Prophet, ARIMA) on historical QPS data.
4
Checkpointing / CUDA graph capture: Serialize CUDA graphs (vLLM supports this) after first warmup. On restart, replay the captured graph instead of re-tracing. Reduces restart time from minutes to seconds for the compilation step.
5
Spot instance management: For batch inference, use AWS EC2 Spot / GCP Preemptible GPUs with checkpointing. For interactive inference, use on-demand instances. Route batch traffic to spot nodes with a priority queue.

Together AI / Fireworks AI: Inference Specialist Approach

Groq: Language Processing Unit (LPU) Architecture

Groq builds custom silicon (LPU) specifically designed for sequential matrix-vector multiply — exactly the decode bottleneck. By eliminating the DRAM entirely (on-chip SRAM only), Groq achieves memory bandwidth of 80 TB/s vs. 3.35 TB/s for H100 — a 24x bandwidth advantage. This translates to sub-millisecond ITL for most models. The tradeoff: LPUs have less total memory than HBM, limiting max model size and batch size.

8. Staff-Level Interview Angle

What Interviewers Are Looking For ▼

The Core Signal Interviewers Test

At the staff level, interview questions on inference platforms are rarely about memorizing which server is fastest. They test whether you can reason through the system design tradeoffs from first principles and communicate decisions in terms of business outcomes. The key question interviewers have in their heads is: "Can this engineer lead a team through the decision of how to serve our models at scale, with real cost and latency constraints?"

Common Interview Questions & Strong Answer Frameworks

Q
"We're launching a chat product. Walk me through how you'd design the inference stack."

Strong answer hits: latency SLA (interactive → <200ms TTFT), token budget per request, expected QPS, model choice, hardware selection, server choice (vLLM for throughput), autoscaling policy (KV cache utilization as primary signal), streaming via SSE, and monitoring (TTFT P50/P95, ITL, queue depth, cost per token). Weak answer: just says "use vLLM on A100s" without connecting decisions to requirements.

Q
"Our inference cost is 3x over budget. How do you diagnose and fix it?"

Strong answer: structured diagnosis — first check GPU utilization and batch size (are we underutilizing?), then KV cache hit rates (are we wasting memory on repeated prefixes?), then output token length distribution (are users generating longer outputs than expected?), then quantization state (are we running FP16 when INT8 is acceptable?). Each diagnosis maps to a specific fix: quantization, prefix caching, max_tokens limits, better routing, or model downgrade for simpler queries.

Q
"Explain how continuous batching works and why it matters."

Strong answer: start with the problem (static batching wastes GPU time when requests finish at different times), explain the iteration-level scheduling insight (evict finished requests immediately, admit new ones), quantify the benefit (10-23x throughput improvement from vLLM paper), and discuss the tradeoff (adds complexity to scheduler, requires careful memory management via PagedAttention). Bonus: mention the interaction with speculative decoding and why they compose well.

Q
"We need to serve a 70B model with 100ms TTFT SLA at 10,000 tokens/second throughput. Design the system."

Strong answer: 100ms TTFT for 70B is aggressive — requires H100s (not A100s), TensorRT-LLM with FP8, TP=4 per instance. At 4,000 tok/s per 4xH100 instance, you need ~3 instances. Add 50% headroom → 5 instances (20x H100 total). Cost: ~$200/hour at CoreWeave. Autoscale with KEDA on KV cache utilization. Put a load balancer with sticky sessions for prefix caching. Monitor P99 TTFT, queue depth, GPU memory utilization. This answer demonstrates you can make concrete hardware choices and justify them with math.

Red Flags to Avoid

  • Recommending fine-tuning to improve inference speed (conflates training with inference optimization)
  • Saying "just scale horizontally" without accounting for GPU cold start costs and provisioning time (minutes, not seconds)
  • Treating all requests as equal without mentioning that token length distribution shapes everything
  • Ignoring the KV cache when discussing memory requirements — model weights are just half the story
  • Recommending serverless for all inference workloads without noting the cold start and cost tradeoffs
  • Conflating GPU utilization (compute) with memory bandwidth utilization — for LLMs, the latter is almost always the bottleneck during decode
  • Not mentioning streaming/SSE for interactive applications — first-byte latency is what users feel

9. Active Recall Questions

Try to answer each question before expanding the answer.

Q1: Why is LLM decode memory-bandwidth-bound rather than compute-bound, and what does this imply for optimization?

During decode, the GPU generates exactly one token per forward pass. Each step requires reading all model weights from VRAM once (e.g., 140 GB for LLaMA 3 70B FP16). Even on an H100 with 3.35 TB/s bandwidth, this takes ~42ms. Meanwhile, the actual computation (one matrix-vector multiply per layer) uses only a tiny fraction of the GPU's 989 TFLOPS. The arithmetic intensity (FLOPs / bytes) is too low to saturate the compute units.

Implication: The primary optimization levers during decode are: (1) quantization — fewer bytes per weight means less bandwidth consumed per step; (2) batching — amortize the same memory load across N requests, getting N tokens per bandwidth pass; (3) better hardware — LPU-style chips with on-chip SRAM (like Groq) eliminate the DRAM bottleneck entirely.

Q2: What problem does PagedAttention solve, and how does it differ from standard KV cache allocation?

Standard KV cache allocation pre-allocates a contiguous VRAM block for each request sized at the maximum possible sequence length. Since actual output lengths are much shorter on average, 60-80% of this allocated memory sits unused — internal fragmentation. When VRAM is "full" of fragmented allocations, new requests queue up even though plenty of bytes are technically free.

PagedAttention (from the vLLM paper) borrows OS virtual memory paging: the KV cache is divided into fixed-size blocks (pages, typically 16 tokens × hidden_size per page). These blocks can be non-contiguous in physical VRAM. Each request gets a logical page table mapping its sequence positions to physical blocks. Blocks are allocated on demand and freed when a request completes. This reduces waste to near zero, enabling 2-4x more concurrent requests in the same VRAM footprint.

Q3: Explain speculative decoding. What is the acceptance rate, and when does speculative decoding NOT help?

In speculative decoding, a small "draft" model generates k candidate tokens (e.g., k=5) autoregressively. Then the large "target" model processes all k tokens in a single parallel forward pass (like a prefill step), checking whether it agrees with the draft's choices via rejection sampling. Accepted tokens are kept; the first rejected token is resampled from the target's distribution. On average, α (the acceptance rate) tokens are accepted per round, producing α+1 tokens per target model pass instead of 1.

The acceptance rate α depends on how well the draft model matches the target's distribution for the specific task. For predictable text (code completion, structured output, repetitive templates), α can reach 0.8-0.9, giving near 5x speedup. For creative or highly sampled text (temperature=1.0, random fiction), α may fall to 0.3-0.4, yielding minimal speedup — you pay the draft model cost but get little benefit. Speculative decoding also increases memory requirements (must hold both models in VRAM simultaneously) and is less effective for very short outputs.

Q4: What is the best autoscaling signal for an LLM inference service, and why are GPU utilization % and RPS poor choices?

GPU utilization % is misleading because LLM decode is memory-bandwidth-bound. During decode, compute units sit at 20-40% utilization even when the service is fully loaded and adding more requests would increase queue depth. Autoscaling on GPU utilization would chronically under-scale.

Requests per second (RPS) is poor because it ignores token length. A request generating 10 tokens takes 1/50th the GPU time of a request generating 500 tokens. Two workloads with identical RPS can have 50x different GPU utilization.

Best signals: (1) KV cache utilization % — when >85% of allocated KV cache blocks are in use, new requests will start queuing imminently. This is a leading indicator that reacts before latency degrades. (2) Request queue depth — when the scheduler queue exceeds N waiting requests, scale out. Combine both: scale up when either crosses threshold, scale down only when both drop below 30% for 5+ minutes.

Q5: What is chunked prefill, and what problem does it solve in continuous batching?

In standard continuous batching, when a request with a very long prompt arrives (e.g., 16K tokens of RAG context), the scheduler runs its entire prefill in one step before resuming decode for other requests. This "prefill monopoly" can cause all other requests in the batch to stall for hundreds of milliseconds — spiking their Inter-Token Latency and causing P99 TTFT to blow out.

Chunked prefill breaks the long prefill into small chunks (e.g., 512 tokens each) and interleaves them with decode steps for other requests. Instead of one 16K-token prefill step blocking everything for 200ms, the scheduler alternates: 512-token prefill chunk, decode step for existing requests, 512-token prefill chunk, decode step, etc. This smooths out ITL for concurrent requests at the cost of slightly longer completion time for the chunked request's prefill phase. Anyscale contributed chunked prefill to vLLM and showed 2-3x improvement in P99 decode latency for mixed-length workloads.

Q6: Calculate: How many H100 GPUs do you need to serve LLaMA 3 70B at 5,000 output tokens/second with 99th percentile TTFT < 150ms?

Step 1: Model size. LLaMA 3 70B in FP8 on H100 = 70GB (1 byte/param). With TP=4 across 4xH100, each GPU holds 17.5GB of weights, leaving ~62.5GB for KV cache per GPU.

Step 2: Throughput per instance. From benchmarks: 4xH100 with TRT-LLM FP8 achieves ~4,000 output tokens/sec at batch=32 with P50 TTFT ~100ms. To meet P99 TTFT <150ms, we must not overload the scheduler — practical throughput per instance is ~3,000-3,500 tokens/sec with headroom.

Step 3: Number of instances. 5,000 tok/s ÷ 3,000 tok/s per instance = 1.67 instances. Round up to 2 instances = 8 H100s. Add 50% headroom for burst and rolling updates → 3 instances = 12 H100s minimum. In practice, run 4 instances (16 H100s) to handle a single instance failure without SLA breach.

Cost: 16 H100s at CoreWeave reserved pricing ~$4/hr each = $64/hr = ~$1,536/day = ~$46,000/month. At 5,000 tok/s × 86,400s/day = 432M tokens/day → ~$0.11/M tokens fully loaded.

Step 2: Prefix-Aware Load Balancer (Python)

"""
Prefix-aware router: routes requests with the same system prompt
to the same vLLM instance to maximize prefix cache hit rates.
"""

import hashlib
import httpx
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
import asyncio

app = FastAPI()

BACKENDS = [
    "http://vllm-0:8000",
    "http://vllm-1:8000",
    "http://vllm-2:8000",
]

def get_prefix_hash(messages: list) -> str:
    """
    Hash the system prompt + first user message to create
    a stable routing key. Requests sharing these will hit
    the same backend and benefit from prefix caching.
    """
    prefix_parts = []
    for msg in messages:
        if msg["role"] in ("system", "user"):
            prefix_parts.append(msg["content"][:500])  # first 500 chars
            break
        prefix_parts.append(msg["content"][:500])

    prefix_str = "|".join(prefix_parts)
    return hashlib.md5(prefix_str.encode()).hexdigest()

def route_to_backend(prefix_hash: str) -> str:
    """Consistent hash routing for prefix locality."""
    idx = int(prefix_hash, 16) % len(BACKENDS)
    return BACKENDS[idx]

@app.post("/v1/chat/completions")
async def proxy_chat(request: Request):
    body = await request.json()
    messages = body.get("messages", [])
    prefix_hash = get_prefix_hash(messages)
    backend = route_to_backend(prefix_hash)

    # Forward request to selected backend
    headers = dict(request.headers)
    headers.pop("host", None)

    async def stream_response():
        async with httpx.AsyncClient(timeout=120) as client:
            async with client.stream(
                "POST",
                f"{backend}/v1/chat/completions",
                json=body,
                headers=headers,
            ) as resp:
                async for chunk in resp.aiter_bytes():
                    yield chunk

    if body.get("stream", False):
        return StreamingResponse(
            stream_response(),
            media_type="text/event-stream"
        )
    else:
        async with httpx.AsyncClient(timeout=120) as client:
            resp = await client.post(
                f"{backend}/v1/chat/completions",
                json=body,
                headers=headers,
            )
            return resp.json()

Step 3: Health Check & Circuit Breaker

"""
Health-aware routing: avoid sending requests to overloaded backends.
Check /metrics and skip backends with high queue depth.
"""

import asyncio
import httpx
from dataclasses import dataclass
from typing import Optional

@dataclass
class BackendHealth:
    url: str
    queue_depth: float = 0
    kv_cache_usage: float = 0
    healthy: bool = True

backend_health: dict[str, BackendHealth] = {
    url: BackendHealth(url=url) for url in BACKENDS
}

async def refresh_backend_health():
    """Background task: poll /metrics every 5 seconds."""
    while True:
        for url, health in backend_health.items():
            try:
                async with httpx.AsyncClient(timeout=3) as client:
                    resp = await client.get(f"{url}/metrics")
                    text = resp.text

                    # Parse Prometheus text format
                    for line in text.split("\n"):
                        if line.startswith("vllm:num_requests_waiting"):
                            parts = line.split()
                            if len(parts) >= 2:
                                health.queue_depth = float(parts[-1])
                        if line.startswith("vllm:gpu_cache_usage_perc"):
                            parts = line.split()
                            if len(parts) >= 2:
                                health.kv_cache_usage = float(parts[-1])

                    health.healthy = (
                        health.queue_depth < 20 and
                        health.kv_cache_usage < 0.95
                    )
            except Exception:
                health.healthy = False
        await asyncio.sleep(5)

def pick_best_backend(prefix_hash: str) -> str:
    """
    Prefer prefix-consistent backend if healthy,
    fall back to least-loaded healthy backend.
    """
    preferred_idx = int(prefix_hash, 16) % len(BACKENDS)
    preferred_url = BACKENDS[preferred_idx]

    if backend_health[preferred_url].healthy:
        return preferred_url

    # Fall back: find healthy backend with lowest queue depth
    healthy = [
        h for h in backend_health.values()
        if h.healthy
    ]
    if not healthy:
        # Circuit open: return preferred anyway (best effort)
        return preferred_url

    return min(healthy, key=lambda h: h.queue_depth).url

"""
Load test: verify prefix caching is working by measuring
latency for requests with shared vs. unique system prompts.
"""

import asyncio
import httpx
import time
import statistics

ROUTER_URL = "http://localhost:9000/v1/chat/completions"
SYSTEM_PROMPT = "You are a helpful assistant specialized in Python coding."

async def make_request(session: httpx.AsyncClient,
                       user_msg: str,
                       stream: bool = False) -> float:
    start = time.perf_counter()
    first_token_time = None

    payload = {
        "model": "meta-llama/Meta-Llama-3-8B-Instruct",
        "messages": [
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": user_msg},
        ],
        "max_tokens": 100,
        "stream": stream,
    }

    if stream:
        async with session.stream("POST", ROUTER_URL, json=payload) as resp:
            async for chunk in resp.aiter_text():
                if first_token_time is None and "data:" in chunk:
                    first_token_time = time.perf_counter() - start

        return first_token_time or (time.perf_counter() - start)
    else:
        await session.post(ROUTER_URL, json=payload)
        return time.perf_counter() - start

11. Parallel Tool-Calls Under SLO

Why This Matters for Agent Performance

AI agents that call tools sequentially are bottlenecked by the sum of all tool latencies. An agent that queries Splunk (2s), Grafana (1.5s), and PagerDuty (0.5s) sequentially takes 4s. In parallel: 2s. Under strict SLOs (e.g., "triage within 30s"), parallel execution is mandatory.

Parallel Tool Execution Patterns ▼

Pattern 1: Independent Parallel Calls

When tool calls have no dependencies, fire them all at once:

import asyncio
from typing import Any


class ParallelToolExecutor:
    """Execute multiple tool calls in parallel with SLO enforcement."""

    def __init__(self, slo_timeout_sec: float = 10.0):
        self.slo_timeout = slo_timeout_sec

    async def execute_parallel(self, tool_calls: list[dict]) -> dict:
        """Run independent tool calls in parallel, respecting SLO."""

        async def run_tool(call: dict) -> tuple[str, Any]:
            tool_fn = call["function"]
            args = call.get("args", {})
            try:
                result = await asyncio.wait_for(
                    tool_fn(**args),
                    timeout=self.slo_timeout * 0.8,  # 80% of SLO per tool
                )
                return call["name"], {"status": "success", "result": result}
            except asyncio.TimeoutError:
                return call["name"], {"status": "timeout", "result": None}
            except Exception as e:
                return call["name"], {"status": "error", "result": str(e)}

        tasks = [asyncio.create_task(run_tool(c)) for c in tool_calls]
        done, pending = await asyncio.wait(tasks, timeout=self.slo_timeout)

        results = {}
        for task in done:
            name, result = task.result()
            results[name] = result
        for task in pending:
            task.cancel()
            results[f"cancelled_{id(task)}"] = {"status": "slo_exceeded"}

        return results


# Usage: Agent needs logs, metrics, and topology simultaneously
executor = ParallelToolExecutor(slo_timeout_sec=5.0)
results = await executor.execute_parallel([
    {"name": "splunk_logs", "function": query_splunk, "args": {"query": "error", "last": "5m"}},
    {"name": "grafana_metrics", "function": query_grafana, "args": {"dashboard": "api-latency"}},
    {"name": "cmdb_topology", "function": query_cmdb, "args": {"service": "auth-service"}},
])
