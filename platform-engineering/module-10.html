Common Bugs to Spot

Q: How do you spot N+1 query problems in code review?

A: The N+1 problem occurs when code fetches a list of items and then makes a separate query for each item's related data.

# BAD: N+1 queries (1 query for orders + N queries for users)
orders = db.query("SELECT * FROM orders WHERE status = 'pending'")
for order in orders:
    user = db.query("SELECT * FROM users WHERE id = %s", order.user_id)  # N queries!
    order.user_name = user.name

# GOOD: Single query with JOIN
orders = db.query("""
    SELECT o.*, u.name as user_name
    FROM orders o
    JOIN users u ON o.user_id = u.id
    WHERE o.status = 'pending'
""")

# GOOD: Batch fetch
orders = db.query("SELECT * FROM orders WHERE status = 'pending'")
user_ids = [o.user_id for o in orders]
users = db.query("SELECT * FROM users WHERE id = ANY(%s)", user_ids)
user_map = {u.id: u for u in users}

Red flags in review:

  • Database calls inside a for/while loop
  • ORM lazy loading in a loop (e.g., order.user.name in Python/Django)
  • Missing .prefetch_related() or .select_related() in Django
  • Missing @EntityGraph or JOIN FETCH in JPA/Hibernate
Q: How do you spot race conditions during code review?
# BUG: Race condition - check-then-act without atomicity
def transfer_funds(from_account, to_account, amount):
    balance = db.get_balance(from_account)
    if balance >= amount:          # Thread A checks: balance=100, amount=80
        # Thread B also checks: balance=100, amount=80 (BOTH pass!)
        db.deduct(from_account, amount)  # Thread A deducts 80 (balance=20)
        db.add(to_account, amount)       # Thread B deducts 80 (balance=-60!) BUG!

# FIX: Use database-level atomicity
def transfer_funds(from_account, to_account, amount):
    rows_updated = db.execute("""
        UPDATE accounts SET balance = balance - %s
        WHERE id = %s AND balance >= %s
    """, amount, from_account, amount)  # Atomic check-and-deduct

    if rows_updated == 0:
        raise InsufficientFundsError()
    db.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s",
               amount, to_account)

Red flags in review:

  • Read-then-write patterns without locking or atomic operations
  • Shared mutable state without synchronization
  • if not exists then create patterns (TOCTOU)
  • Incrementing counters with count = get(); set(count + 1) instead of atomic increment

Spot the Bug Exercises

Spot the Bug #1: User registration endpoint
@app.post("/register")
async def register(request: RegisterRequest):
    # Check if email exists
    existing = await db.fetch_one(
        "SELECT id FROM users WHERE email = $1", request.email
    )
    if existing:
        raise HTTPException(409, "Email already exists")

    # Hash password
    hashed = hashlib.md5(request.password.encode()).hexdigest()

    # Create user
    user = await db.execute(
        "INSERT INTO users (email, password, role) VALUES ($1, $2, $3)",
        request.email, hashed, request.role
    )
    return {"id": user.id, "email": request.email}

Bugs found:

  1. MD5 for passwords — MD5 is cryptographically broken. Use bcrypt or argon2.
  2. Race condition — Two concurrent registrations with the same email can both pass the check. Add a UNIQUE constraint on the email column and handle the DB constraint violation.
  3. User-controlled role — request.role lets users set their own role (e.g., "admin"). Role should be set server-side.
  4. No input validation — No email format validation, no password strength check.
Spot the Bug #2: Pagination endpoint
@app.get("/orders")
async def list_orders(page: int = 1, per_page: int = 100):
    offset = (page - 1) * per_page
    orders = await db.fetch_all(
        f"SELECT * FROM orders ORDER BY created_at DESC OFFSET {offset} LIMIT {per_page}"
    )
    total = await db.fetch_val("SELECT COUNT(*) FROM orders")
    return {"orders": orders, "total": total, "page": page}

Bugs found:

  1. SQL injection — f-string with user input (offset, per_page). Use parameterized queries.
  2. No upper bound on per_page — User can request per_page=1000000 and OOM the server. Cap at a reasonable max (e.g., 100).
  3. No lower bound on page — page=0 or negative values produce invalid offsets.
  4. SELECT * — Returns all columns including potentially sensitive data.
  5. COUNT(*) on every request — Expensive on large tables. Consider caching or removing total count.
  6. Offset pagination — Slow on large datasets. Consider cursor-based pagination.
Spot the Bug #3: Cache invalidation
async def get_user_profile(user_id: str):
    # Check cache
    cached = await redis.get(f"user:{user_id}")
    if cached:
        return json.loads(cached)

    # Fetch from DB
    user = await db.fetch_one("SELECT * FROM users WHERE id = $1", user_id)
    if user:
        await redis.set(f"user:{user_id}", json.dumps(user))
    return user

async def update_user_profile(user_id: str, data: dict):
    await db.execute("UPDATE users SET name = $1 WHERE id = $2", data["name"], user_id)
    await redis.delete(f"user:{user_id}")

Bugs found:

  1. No TTL on cache — If update_user_profile fails to delete cache (Redis down), stale data persists forever. Always set a TTL.
  2. Race condition on update — Between DB update and cache delete, another request can read stale DB data and re-cache it. Use cache-aside with TTL, or write-through cache.
  3. No error handling on cache operations — If Redis is down, get_user_profile throws instead of falling back to DB.
  4. Cache stampede — If cache expires and 1000 requests hit simultaneously, all 1000 query the DB. Use a lock or probabilistic early expiration.
Spot the Bug #4: Concurrent counter update
public class ViewCounter {
    private Map<String, Integer> counts = new HashMap<>();

    public void incrementView(String pageId) {
        int current = counts.getOrDefault(pageId, 0);
        counts.put(pageId, current + 1);
    }

    public int getViews(String pageId) {
        return counts.getOrDefault(pageId, 0);
    }
}

Bugs found:

  1. Not thread-safe — HashMap is not concurrent. Multiple threads calling incrementView simultaneously can corrupt the map or lose increments. Use ConcurrentHashMap with compute() or AtomicInteger.
  2. Lost updates — Read-then-write is not atomic even with ConcurrentHashMap's get/put. Use counts.merge(pageId, 1, Integer::sum).
Spot the Bug #5: API retry logic
def call_payment_api(order_id, amount):
    for attempt in range(5):
        try:
            response = requests.post(
                "https://api.payment.com/charges",
                json={"order_id": order_id, "amount": amount},
                timeout=30
            )
            if response.status_code == 200:
                return response.json()
            elif response.status_code == 400:
                return response.json()  # Client error, retry won't help
        except requests.Timeout:
            time.sleep(1)
    raise PaymentError("Payment failed after 5 attempts")

Bugs found:

  1. Retrying 400 errors — The code continues looping on 400 (client error). These are not retryable. It should return/raise on 400.
  2. No idempotency key — Retrying a payment POST without an idempotency key can charge the customer multiple times.
  3. Fixed sleep (no backoff) — All retries are 1 second apart. Use exponential backoff with jitter.
  4. No circuit breaker — If the payment API is down, every order attempt waits 5 × 30s = 2.5 minutes.
  5. Swallowing non-timeout exceptions — Connection errors are not caught.

Review Culture

Q: How do you give constructive feedback in code reviews?

A:

Instead ofSay
"This is wrong""This could cause X when Y happens. What if we..."
"Why did you do it this way?""I'm curious about the thinking behind this approach. I was considering X because..."
"This is bad code""nit: this could be simplified to..." or "suggestion: consider X for readability"
Blocking for style"nit (non-blocking): prefer X style" and approve anyway

Comment prefixes:

  • nit: — Style/naming suggestion, non-blocking
  • suggestion: — Consider this alternative, non-blocking
  • question: — I don't understand this, help me understand
  • issue: — This is a bug or security issue, must fix before merge
  • praise: — This is well done! (Don't forget positive feedback)
Q: What should staff engineers prioritize when reviewing code?

A: Staff engineers should focus on what automated tools can't catch:

  • Architectural fit — Does this change align with the system's architecture? Does it introduce unnecessary coupling?
  • Failure modes — What happens when this code fails? Are error paths tested?
  • Scalability implications — Will this work at 10x current load?
  • API contract changes — Is this backward compatible? Will it break consumers?
  • Operational impact — Can this be deployed safely? Is it observable? Can it be rolled back?
  • Missing context — Is the PR description sufficient? Will the next person understand why this change was made?

What to delegate to automation: Style, formatting, import ordering, unused variables, simple type errors. Configure linters and formatters in CI so humans don't waste time on these.

Exception Handling Patterns

Q: Why are swallowed exceptions dangerous, and what patterns should you use instead?

A: A swallowed exception (empty catch block) silently discards errors, leading to data loss, corrupted state, or silent failures that are extremely hard to debug in production.

// BAD: Swallowed exception - payment failure is silently ignored!
public BookingResponse createBooking(BookingRequest request) {
    Booking booking = bookingRepo.save(request.toEntity());
    try {
        paymentService.charge(booking.getId(), request.getAmount());
    } catch (Exception e) {
        // Nothing here! If payment fails, booking is created but unpaid.
        // Customer thinks they booked, hotel thinks they didn't pay.
    }
    return BookingResponse.from(booking);
}

// GOOD: Handle, log, and propagate appropriately
public BookingResponse createBooking(BookingRequest request) {
    Booking booking = bookingRepo.save(request.toEntity());
    try {
        paymentService.charge(booking.getId(), request.getAmount());
    } catch (PaymentDeclinedException e) {
        // Client error - card declined. Rollback booking, return 422.
        bookingRepo.cancel(booking.getId());
        throw new BookingPaymentFailedException("Payment declined", e);
    } catch (PaymentTimeoutException e) {
        // Transient error - mark booking as PENDING_PAYMENT for retry
        booking.setStatus(BookingStatus.PENDING_PAYMENT);
        bookingRepo.save(booking);
        log.warn("Payment timeout for booking={}, will retry", booking.getId(), e);
        retryQueue.enqueue(booking.getId());
        return BookingResponse.pending(booking);
    } catch (Exception e) {
        // Unexpected error - log full context, return 500
        log.error("Unexpected payment error for booking={}", booking.getId(), e);
        bookingRepo.cancel(booking.getId());
        throw new InternalServerException("Booking failed due to payment error", e);
    }
    return BookingResponse.from(booking);
}

Exception handling rules:

  1. Never use empty catch blocks. At minimum, log the exception.
  2. Catch specific exceptions — handle each failure mode differently.
  3. Re-throw or wrap when you can't fully handle it. Don't swallow and return a success response.
  4. Preserve the original exception as the cause when wrapping (new CustomException("msg", e)).
  5. Log at the right level: Business errors (declined payment) = WARN. Unexpected errors = ERROR. Never log and re-throw the same exception at multiple layers (log once at the boundary).
Q: How should exceptions map to HTTP status codes (4xx vs 5xx)?

A: The distinction between 4xx and 5xx is critical: 4xx means the client did something wrong (and should change the request), 5xx means the server failed (and retrying might work).

Spot the Bug #6: Booking API with swallowed payment exception
@PostMapping("/bookings")
public ResponseEntity<BookingDTO> createBooking(@RequestBody BookingRequest req) {
    // Validate dates
    if (req.getCheckIn().isAfter(req.getCheckOut())) {
        return ResponseEntity.status(500).body(null);  // Bug #1
    }

    Booking booking = new Booking(req);
    bookingRepository.save(booking);

    try {
        PaymentResult result = paymentClient.charge(req.getPaymentInfo(), booking.getTotal());
        booking.setPaymentId(result.getId());
    } catch (Exception e) {
        // "We'll handle this later"  // Bug #2
    }

    try {
        emailService.sendConfirmation(booking);
    } catch (Exception e) {
        log.error("Email failed");  // Bug #3
    }

    bookingRepository.save(booking);
    return ResponseEntity.ok(booking.toDTO());
}

Bugs found:

  1. Wrong status code for validation: 500 for a client error (check-in after check-out). Should be 400 or 422. Also returns null body with no error message.
  2. Swallowed payment exception: If payment fails, the booking is saved as confirmed but unpaid. Customer thinks they booked; hotel has no payment. This is a silent data corruption bug. Fix: rollback booking or mark as PENDING_PAYMENT.
  3. Missing exception context: log.error("Email failed") doesn't include the exception object (e) or the booking ID. When this fails in production, you have no stack trace and no way to identify which booking's email failed. Fix: log.error("Email failed for booking={}", booking.getId(), e)
  4. No transaction boundary: Two save() calls without a transaction. If the second save fails, you have a partially saved booking.
  5. Email in request path: Email sending is synchronous in the booking request. If the email service is slow, the API response is slow. Move to async (message queue).

Concurrency Control & Locking

Q: How does optimistic locking work, and when should you use it?

A: Optimistic locking assumes conflicts are rare. Instead of locking the row, you check at write time whether anyone else modified it since you read it, using a version column.

-- Schema: room_inventory table with version column
CREATE TABLE room_inventory (
    room_id     BIGINT PRIMARY KEY,
    hotel_id    BIGINT NOT NULL,
    available   INT NOT NULL,
    version     INT NOT NULL DEFAULT 0,
    updated_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Optimistic lock: update only if version matches what we read
UPDATE room_inventory
SET available = available - 1,
    version = version + 1,
    updated_at = NOW()
WHERE room_id = 42
  AND version = 5          -- version we read earlier
  AND available > 0;       -- business rule: can't go negative

-- If rows_affected = 0, someone else modified it first → retry or fail
// Java/JPA implementation
@Entity
public class RoomInventory {
    @Id
    private Long roomId;
    private int available;

    @Version  // JPA handles optimistic locking automatically
    private int version;
}

// Service layer
@Transactional
public BookingResult bookRoom(Long roomId) {
    RoomInventory room = roomRepo.findById(roomId)
        .orElseThrow(() -> new RoomNotFoundException(roomId));

    if (room.getAvailable() <= 0) {
        throw new NoAvailabilityException(roomId);
    }

    room.setAvailable(room.getAvailable() - 1);
    try {
        roomRepo.save(room);  // JPA checks version on flush
    } catch (OptimisticLockingFailureException e) {
        // Another transaction modified this room - retry
        throw new ConcurrentBookingException("Room was modified, please retry", e);
    }
    return BookingResult.success();
}

When to use optimistic locking:

  • Conflicts are rare (most updates succeed without contention)
  • You can afford to retry on conflict
  • Read-heavy workloads where pessimistic locks would cause unnecessary blocking

When NOT to use: High-contention scenarios (e.g., last room available, flash sales). Optimistic locking will cause many retries, wasting resources. Use pessimistic locking instead.

Q: When is pessimistic locking necessary, and how do you avoid deadlocks?

A: Pessimistic locking acquires a database lock on the row before reading, preventing other transactions from modifying it until the lock is released.

-- Pessimistic lock: SELECT FOR UPDATE
BEGIN;
SELECT * FROM room_inventory
WHERE room_id = 42
FOR UPDATE;  -- Acquires row-level lock, other txns wait

-- Now we have exclusive access to this row
UPDATE room_inventory
SET available = available - 1
WHERE room_id = 42 AND available > 0;

COMMIT;  -- Lock released

When to use pessimistic locking:

  • High contention: Multiple concurrent transactions frequently update the same row (last room, popular hotel)
  • Must-succeed operations: When retry is expensive or not feasible (payment processing)
  • Multi-row updates: When you need to lock multiple related rows atomically

Deadlock prevention:

  1. Always lock in consistent order: If you need to lock rooms 42 and 57, always lock the lower ID first.
  2. Keep transactions short: Lock → update → commit. Never do HTTP calls or slow operations while holding a lock.
  3. Set lock timeout: SET lock_timeout = '5s'; so transactions don't wait forever.
  4. Use NOWAIT or SKIP LOCKED:
-- NOWAIT: Fail immediately if row is locked (don't wait)
SELECT * FROM room_inventory WHERE room_id = 42 FOR UPDATE NOWAIT;
-- Throws error immediately if locked - good for user-facing APIs

-- SKIP LOCKED: Skip locked rows, process unlocked ones (queue pattern)
SELECT * FROM booking_queue
WHERE status = 'pending'
ORDER BY created_at
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- Multiple workers can process different rows concurrently

Optimistic vs Pessimistic — decision guide:

ScenarioRecommendedWhy
General room booking (low contention)OptimisticMost bookings are for different rooms
Last room available (high contention)PessimisticMany users competing for same row
Flash sale / limited inventoryPessimistic + SKIP LOCKEDQueue-style processing of high-demand items
Updating user profileOptimisticOne user rarely has concurrent updates
Q: What is the reservation pattern (hold → confirm → expire)?

A: The reservation pattern is a two-phase approach for booking systems where you temporarily hold a resource before confirming. This is the standard pattern at Agoda, Booking.com, and airline reservation systems.

stateDiagram-v2 [*] --> Available Available --> Held : User selects room Held --> Confirmed : Payment succeeds Held --> Available : Hold expires (TTL) or user cancels Confirmed --> Cancelled : User cancels within policy Cancelled --> Available : Room released 
class ReservationService:
    HOLD_TTL_SECONDS = 900  # 15-minute hold

    async def hold_room(self, room_id: str, user_id: str) -> Reservation:
        """Phase 1: Temporarily hold the room."""
        # Atomic check-and-hold using optimistic locking
        result = await db.execute("""
            UPDATE room_inventory
            SET status = 'held',
                held_by = $1,
                held_until = NOW() + INTERVAL '15 minutes',
                version = version + 1
            WHERE room_id = $2
              AND status = 'available'
              AND version = $3
            RETURNING *
        """, user_id, room_id, expected_version)

        if not result:
            raise RoomUnavailableException(room_id)

        # Schedule expiry cleanup
        await redis.setex(f"hold:{room_id}", self.HOLD_TTL_SECONDS, user_id)
        return Reservation(room_id=room_id, status="held", expires_at=result.held_until)

    async def confirm_reservation(self, room_id: str, user_id: str, payment_id: str):
        """Phase 2: Confirm after payment succeeds."""
        result = await db.execute("""
            UPDATE room_inventory
            SET status = 'confirmed',
                payment_id = $1,
                confirmed_at = NOW()
            WHERE room_id = $2
              AND held_by = $3
              AND status = 'held'
              AND held_until > NOW()
        """, payment_id, room_id, user_id)

        if not result:
            raise HoldExpiredException("Hold expired, please try again")

    async def expire_holds(self):
        """Background job: release expired holds."""
        await db.execute("""
            UPDATE room_inventory
            SET status = 'available', held_by = NULL, held_until = NULL
            WHERE status = 'held' AND held_until < NOW()
        """)

Why this pattern works for bookings:

  • Prevents double-booking: Room is marked 'held' atomically, so only one user can hold it
  • No abandoned locks: TTL ensures rooms are released if user abandons the flow
  • Payment safety: Payment is charged only after the hold is confirmed, not before
  • User experience: Users see "held for 15 minutes" countdown, creating urgency

Double-booking prevention combo: Use UNIQUE constraint on (room_id, date, status='confirmed') + optimistic locking on the inventory table. The unique constraint is the last line of defense if the application-level check has a race condition.

Spot the Bug #7: Concurrent room booking with race condition
async def book_room(room_id: str, user_id: str, dates: DateRange):
    # Check availability
    room = await db.fetch_one(
        "SELECT * FROM rooms WHERE id = $1", room_id
    )
    if room["status"] != "available":
        raise RoomUnavailableError()

    # Check no overlapping bookings
    existing = await db.fetch_one("""
        SELECT id FROM bookings
        WHERE room_id = $1 AND check_in < $3 AND check_out > $2
    """, room_id, dates.check_in, dates.check_out)

    if existing:
        raise RoomUnavailableError()

    # Create booking
    booking = await db.execute("""
        INSERT INTO bookings (room_id, user_id, check_in, check_out, status)
        VALUES ($1, $2, $3, $4, 'confirmed')
    """, room_id, user_id, dates.check_in, dates.check_out)

    # Update room status
    await db.execute(
        "UPDATE rooms SET status = 'booked' WHERE id = $1", room_id
    )

    return booking

Bugs found:

  1. Classic TOCTOU race condition: Between checking availability (SELECT) and creating the booking (INSERT), another concurrent request can also pass the check and create a booking. Two users book the same room. Fix: wrap in a transaction with SELECT FOR UPDATE, or use optimistic locking.
  2. No transaction: The INSERT and UPDATE are separate operations. If the UPDATE fails, you have a booking with no room status change. Wrap in a single transaction.
  3. No database constraint: There's no unique constraint preventing overlapping bookings at the DB level. The application check is necessary but not sufficient. Add an exclusion constraint: EXCLUDE USING gist (room_id WITH =, daterange(check_in, check_out) WITH &&).
  4. Room status is redundant and inconsistent: Maintaining a status column on the rooms table AND checking the bookings table creates two sources of truth. If they diverge (which they will, given bug #2), you'll have phantom availability or phantom bookings.

Connection Pooling & Database Scaling

Q: How do you size a connection pool, and what happens when it's exhausted?

A: Connection pool sizing is critical for database performance. Too few connections = requests waiting; too many = database overwhelmed.

HikariCP formula (industry standard starting point):

pool_size = (core_count * 2) + effective_spindle_count

Example: 4-core server with SSD (no spindles):
  pool_size = (4 * 2) + 1 = 9 connections

For a typical web app on an 8-core server:
  pool_size = (8 * 2) + 1 = 17 connections

Why fewer connections is often better: PostgreSQL performance degrades with too many connections due to lock contention and context switching. A pool of 20 connections handling 10,000 req/s will outperform 200 connections because:

  • Each connection has overhead (~10MB RAM in PostgreSQL)
  • Connection acquisition/release is fast, but transactions should be short
  • CPU context switching between 200 active queries is expensive

Pool exhaustion symptoms:

SymptomDiagnosisFix
Requests timing out with "Connection pool exhausted"All connections in use, wait queue fullFind slow queries holding connections; increase pool only if queries are fast
Latency spikes in p99 but p50 normalSome requests waiting for pool connectionsCheck for long-running transactions, missing indexes
Connection count at max but DB CPU is lowConnections held by slow application code (not DB)Ensure connections are returned immediately after query, not held during HTTP calls
 
# HikariCP configuration (Spring Boot)
spring:
  datasource:
    hikari:
      maximum-pool-size: 17        # Based on formula
      minimum-idle: 5              # Keep 5 warm connections
      connection-timeout: 3000     # 3s max wait for connection
      idle-timeout: 600000         # 10 min idle before release
      max-lifetime: 1800000        # 30 min max connection lifetime
      leak-detection-threshold: 30000  # Warn if connection held >30s

Common mistake: Setting pool size to 100+ "just in case." This actually harms performance because the database can't efficiently handle that many concurrent queries. Start with the formula, measure, and adjust based on actual pool.active and pool.pending metrics.

Q: When should you use read replicas, and what are the pitfalls?

A: Read replicas duplicate data from a primary (write) database to one or more secondary (read-only) instances, scaling read capacity horizontally.

graph TB APP[Application] -->|Writes| PRIMARY[(Primary DB)] APP -->|Reads| REPLICA1[(Read Replica 1)] APP -->|Reads| REPLICA2[(Read Replica 2)] PRIMARY -->|Async Replication| REPLICA1 PRIMARY -->|Async Replication| REPLICA2

When to use read replicas:

  • Read-heavy workloads (e.g., agent queries for hotel availability, price lookups)
  • Reporting/analytics queries that shouldn't impact transactional performance
  • Geographic distribution (replica in each region for lower latency)

Replication lag awareness:

# Pattern: Read-your-writes consistency
class BookingService:
    def __init__(self, primary_db, replica_db):
        self.primary = primary_db
        self.replica = replica_db

    async def create_booking(self, data):
        # Write to primary
        booking = await self.primary.execute(
            "INSERT INTO bookings (...) VALUES (...) RETURNING *", ...
        )
        return booking

    async def get_booking(self, booking_id, user_id, just_created=False):
        # If user just created this booking, read from primary
        # to avoid "where did my booking go?" due to replication lag
        db = self.primary if just_created else self.replica
        return await db.fetch_one(
            "SELECT * FROM bookings WHERE id = $1", booking_id
        )

    async def search_hotels(self, query):
        # Search queries always go to replica - slight lag is OK
        return await self.replica.fetch_all(
            "SELECT * FROM hotels WHERE ...", ...
        )

Replication lag pitfalls:

  • Read-after-write inconsistency: User creates a booking, then immediately views "My Bookings" from a replica that hasn't replicated yet → booking appears missing. Fix: route post-write reads to primary for a short window.
  • Stale inventory: Room booked on primary but replica still shows "available" → user tries to book an unavailable room. Fix: critical availability checks must use primary.
  • Monitoring lag: Track pg_stat_replication (PostgreSQL) or Seconds_Behind_Master (MySQL). Alert if lag exceeds 5s.
