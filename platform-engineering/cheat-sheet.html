1. Platform Fundamentals

Modules 1 — Platform as product, Conway's Law, Team Topologies

Platform Eng vs SRE vs DevOps vs Infra Eng

RoleFocusCustomersKey Metric
Platform EngInternal Developer Platform (IDP) — golden paths, self-serviceInternal developersDeveloper productivity, adoption rate
SREReliability, SLOs, error budgets, incident responseEnd users (via uptime)SLO attainment, MTTR
DevOpsCI/CD, culture, breaking down silosDev + Ops teamsDeployment frequency, lead time
Infra EngCompute, storage, networking, bare metal/cloudAll engineeringCost efficiency, provisioning speed

Why this distinction matters: Interviewers test whether you understand role boundaries. Platform Eng builds self-service tools so developers don't need to file tickets — the value is removing friction. SRE owns reliability outcomes (SLOs), not just uptime. Confusing these roles signals you don't understand modern org design. At Agoda, Platform Eng owns the internal booking platform APIs that agent teams consume — knowing this framing shapes how you answer.

Key Concepts

  • Internal Developer Platform (IDP): Self-service layer over infra — templates, CI/CD, observability, secrets. Think Backstage, Humanitec.
  • Platform-as-Product: Treat the platform like a product with users (devs), feedback loops, SLOs, roadmaps, and adoption metrics.
  • Conway's Law: System architecture mirrors org communication structure. Use it intentionally (Inverse Conway Maneuver).
  • Team Topologies: Stream-aligned teams (deliver value), Platform teams (reduce cognitive load), Enabling teams (coach), Complicated-subsystem teams (deep expertise).
  • Golden Paths vs Golden Cages: Golden paths = recommended defaults that teams can deviate from. Golden cages = mandatory constraints. Prefer paths; use cages only for compliance/security.

Why "Platform-as-Product" wins: Teams that treat infra as a mandate get low adoption and shadow IT. Treating it as a product means you gather feedback, track NPS, and iterate. Spotify's Backstage adoption succeeded because teams chose it over alternatives — it solved real pain (service catalog fragmentation) and the team iterated based on internal feedback. Conway's Law matters because if your booking team and payment team can't communicate, their services won't integrate cleanly either — fix the org to fix the architecture.

Staff-Level Thinking

  • Build vs Buy vs Skip: Build only when you have unique requirements + team capacity. Buy when commodity. Skip when YAGNI.
  • Measure platform ROI: (Hours saved/team/week × teams × rate × 52) + incident reduction + compliance savings - platform team cost.
  • Adoption > Features: A platform nobody uses is a waste. Measure adoption, satisfaction (CSAT/NPS), and time-to-first-deploy.

2. API Design & Contracts

Module 2 — REST vs gRPC vs GraphQL, versioning, error handling

Protocol Comparison

AspectRESTgRPCGraphQL
FormatJSON (text)Protobuf (binary)JSON (text)
TransportHTTP/1.1+HTTP/2 (required)HTTP/1.1+
StreamingSSE (primary), chunked responsesBidirectionalSubscriptions (WS)
SchemaOpenAPI (optional)Protobuf (required)SDL (required)
Best ForPublic APIs, CRUD, browser clientsInternal microservices, low latencyMobile/frontend with varied data needs
VersioningURL path or headerPackage versioningSchema evolution (additive)

Why REST for agent APIs (Agoda context): External booking agents (MakeMyTrip, Booking.com) use REST because it's universally understood, works through all proxies/firewalls, and agents already have HTTP client libraries. gRPC would give ~3-10x smaller payloads (varies by data type) and bidirectional streaming, but requires protobuf tooling that external agents may not have. Why GraphQL isn't ideal here: Agents need predictable, documented endpoints with strict contracts — not flexible querying that could accidentally over-fetch sensitive data or create expensive queries.

API Versioning Strategies

  • URL Path: /v1/bookings — simple, visible, but hard to sunset. Best for public APIs.
  • Header: Accept: application/vnd.api.v2+json — cleaner URLs, harder to test in browser.
  • Query Param: ?version=2 — easy but pollutes caching.
  • Content Negotiation: Combine media type + version. Most RESTful but complex.

Why URL path versioning wins for booking agents: Agents integrate via documented URLs — /v1/bookings is self-describing, visible in logs/monitoring, and cacheable. Header versioning is "cleaner" in theory but agents will misconfigure it (missing headers silently get wrong version). When Agoda adds v2 with breaking changes, agents can migrate on their own schedule without downtime.

Error Handling Best Practices

  • Use standard HTTP status codes: 400 (bad input), 401 (unauthenticated), 403 (forbidden), 404 (not found), 409 (conflict), 422 (validation), 429 (rate limited), 500 (server error), 503 (unavailable).
  • Return structured error bodies: {"error": {"code": "BOOKING_CONFLICT", "message": "...", "details": [...]}}
  • Never leak stack traces or internal IDs in production error responses.
  • Use idempotency keys for POST/PUT to safely retry: Idempotency-Key: <uuid>

Why idempotency keys are non-negotiable for bookings: Network failures happen. An agent sends POST /v1/bookings, the server processes it, but the response is lost. The agent retries. Without an idempotency key, the customer gets double-booked and double-charged. With an idempotency key, the server returns the same response as the first call. Stripe requires this for payment endpoints. PayPal uses request IDs for similar deduplication. Booking systems like Agoda's benefit from this pattern.

Schema Evolution

  • Protobuf: Add fields (new tag numbers), never reuse deleted tags, use reserved.
  • Avro: Reader/writer schema resolution, supports defaults for new fields.
  • JSON Schema: Additive changes safe; removing/renaming fields = breaking.

3. Pagination, Rate Limiting & API Gateways

Module 3 — Cursor vs offset, rate limiting algorithms, gateway patterns

Pagination Strategies

StrategyProsConsBest For
OffsetSimple, random accessSkips/dupes on mutation, slow at deep offsets (OFFSET 100000)Admin dashboards, small datasets
Cursor (opaque)Stable with mutations, fastNo random page accessFeeds, timelines, infinite scroll
KeysetFast with index, stableRequires sortable unique columnLarge tables, time-series

Why cursor-based for agent booking APIs: An agent listing their bookings (GET /v1/bookings) may have millions of records. Offset pagination at page 10,000 forces the DB to scan and discard 100,000 rows before returning 10 — query time grows linearly with page depth. Cursor pagination uses an index seek (constant time regardless of position). It also avoids the "skipped/duplicate row" problem when new bookings are created between page fetches.

Rate Limiting Algorithms

AlgorithmHow It WorksProsCons
Token BucketTokens refill at fixed rate; each request costs 1 tokenAllows bursts, simpleMemory per user
Leaky BucketRequests queued, processed at fixed rateSmooth output rateBursts get queued/dropped
Fixed WindowCounter resets each window (e.g. per minute)Simple, low memoryBurst at window boundary (2x spike)
Sliding Window LogTrack timestamps of each requestPreciseMemory-heavy
Sliding Window CounterWeighted average of current + previous windowLow memory, smoothApproximate

Why token bucket is the default: Real traffic is bursty — an agent might send 50 requests in 1 second, then nothing for 10 seconds. Token bucket allows this burst (up to bucket capacity) while enforcing an average rate. Fixed window can't handle this — it either allows the burst and has no protection at window boundaries, or blocks legitimate burst traffic. Sliding window counter is the production upgrade (Cloudflare uses it) because it's O(1) memory and very accurate in practice, but token bucket is easier to explain in an interview and conceptually simpler.

API Gateway Patterns

  • Edge Gateway: Rate limiting, auth, TLS termination, request routing (Kong, AWS API Gateway).
  • BFF (Backend for Frontend): Per-client gateways (mobile BFF, web BFF) that aggregate/transform backend calls.
  • Service Mesh Sidecar: Envoy/Istio — mTLS, retries, circuit breaking at service-to-service layer.

Why an API gateway, not just a load balancer: A load balancer distributes traffic; a gateway understands traffic. For agent APIs, the gateway handles auth token validation (reject bad JWTs before they hit your app), per-agent rate limiting (MakeMyTrip gets 1000 RPM, small agents get 100), and request logging (which agent called what endpoint when). Without a gateway, every microservice reimplements these concerns — inconsistently. Why BFF for mobile vs web: A mobile client needs 1 API call returning hotel + pricing + availability (one round-trip), while the web app can make 3 parallel calls. BFF tailors the aggregation per client, avoiding over-fetching on mobile (saves bandwidth and battery).

4. Connectivity Patterns

Module 4 — Webhooks, polling, SSE, WebSockets

Connectivity Comparison

PatternDirectionLatencyComplexityBest For
Short PollingClient → ServerHigh (poll interval)LowSimple status checks, legacy systems
Long PollingClient → Server (held open)MediumMediumChat (fallback), notifications
SSEServer → Client (one-way)LowLowLive feeds, dashboards, stock tickers
WebSocketsBidirectionalVery lowHighChat, gaming, collaborative editing
WebhooksServer → Server (push)Near real-timeMediumPayment callbacks, CI/CD, integrations

Why webhooks for agent callbacks (not polling): After Agoda confirms a booking, the agent needs to know. Polling (GET /v1/bookings/{id}/status every 5s) wastes bandwidth and adds latency. Webhooks push the event to the agent's endpoint instantly. Why SSE over WebSockets for dashboards: SSE is HTTP-native (works through proxies, auto-reconnects, no special server infrastructure) and one-directional is all you need for live hotel availability dashboards. WebSockets add bidirectional complexity only justified when the client also sends data (chat, collaborative editing).

Webhook Design Checklist

  • HMAC Verification: Sign payload with shared secret; receiver verifies X-Signature-256 header.
  • Retry with Exponential Backoff: Retry on 5xx / timeout. Cap at ~5 retries. Use jitter.
  • Idempotency: Include unique event_id; receiver deduplicates using idempotency store.
  • Timeout: Expect response within 5-30s. If receiver needs longer, return 202 Accepted and process async.
  • Dead Letter Queue: After max retries, push to DLQ for manual inspection / replay.

Authentication Types (for API connectivity)

  • API Key: Simple, per-client key in header. Easy to implement, but lacks built-in scoping and expiration — you'd have to build these yourself. Use for internal/trusted services.
  • OAuth 2.0 + JWT: Token-based. Access tokens (short-lived) + refresh tokens (long-lived). Standard for user-facing APIs.
  • mTLS: Mutual TLS with client certificates. Strongest for service-to-service. Used in service meshes.
  • HMAC Signatures: Sign request body/timestamp with shared secret. Used by Stripe, GitHub webhooks.
  • Session-based: Server-side session with cookie. Stateful, doesn't scale horizontally without sticky sessions or shared session store (Redis).

Why OAuth 2.0 Client Credentials for agent APIs: API keys lack built-in scoping and expiration mechanisms — you'd have to build these yourself, whereas OAuth provides them as part of the protocol. OAuth Client Credentials gives each agent a client_id + secret, they exchange it for a JWT with specific scopes (bookings:write, inventory:read), and the token expires in 15 minutes. If an agent is compromised, revoke their client_id — new tokens can't be issued. Existing JWTs remain valid until expiry (15 min max), which is why short-lived access tokens are critical. For immediate revocation, use a token blocklist at the gateway. Why not mTLS for agents: Certificate management is operationally heavy for external partners who may not have TLS expertise. Reserve mTLS for internal service-to-service.

5. Message Brokers & Pub/Sub

Module 5 — Kafka vs RabbitMQ vs SQS, delivery semantics, event sourcing

Broker Comparison

FeatureKafkaRabbitMQSQS/SNS
ModelDistributed log (pull)Message queue (push)Managed queue (pull)
OrderingPer-partitionPer-queue (FIFO mode)FIFO queues available
ThroughputMillions/sec~50K/sec~3K/sec (FIFO, per group with batching)
RetentionDays/weeks (configurable)Until consumed14 days max
ReplayYes (offset reset)Limited (Streams feature supports offset-based replay since v3.9, but not as mature as Kafka)No
Best ForEvent streaming, analytics, CDCTask queues, routing, RPCServerless, simple async

Why Kafka for booking events (not RabbitMQ): Booking events need replay — when analytics reprocesses last month's data, or when a new service joins and needs historical events, Kafka's log retention provides this. Classic RabbitMQ queues delete messages after consumption (Streams support replay but are less mature). Kafka also handles millions of events/sec (hotel search queries, price updates) where RabbitMQ tops out at ~50K/sec. When RabbitMQ wins: Simple task queues (send email, generate PDF) where you need routing, priority queues, and message-level TTL — features Kafka doesn't natively support.

Delivery Semantics

  • At-most-once: Fire and forget. May lose messages. Fastest. Use for metrics/logs where loss is tolerable.
  • At-least-once: Retry until ack. May get duplicates. Most common in practice. Pair with idempotent consumers.
  • Exactly-once: Kafka Transactions + idempotent producer. Heavy. Use for financial/booking workflows.

Why at-least-once + idempotent consumers is the practical default: Exactly-once sounds ideal but requires Kafka Transactions, which add latency and complexity. In practice, at-least-once delivery + idempotent consumer achieves the same outcome more simply: the consumer uses a unique event_id to deduplicate. For bookings: if the "booking confirmed" event is delivered twice, the consumer checks IF NOT EXISTS booking_id before processing. This is how Stripe handles payment idempotency (well-documented). The pattern is standard across booking and payment systems.

Key Patterns

  • Event Sourcing: Store events as source of truth, derive state. Great for audit trails (bookings, payments).
  • CQRS: Separate read/write models. Write to event log, project into read-optimized views.
  • Outbox Pattern: Write event to DB outbox table in same transaction as business data. Poller/CDC publishes to broker. Solves dual-write problem.
  • DLQ (Dead Letter Queue): Failed messages after N retries go to DLQ. Alert, inspect, replay when fixed.

Why the outbox pattern is essential for booking systems: When a booking is confirmed, you need to (1) update the DB and (2) publish an event to Kafka. If you do these as separate operations, a crash between them means either the booking is saved but no event is published (agent never notified), or the event is published but the DB write failed (phantom notification). The outbox pattern writes the event to an outbox table in the same DB transaction as the booking, then a separate poller/CDC publishes to Kafka. This guarantees the event is published if and only if the booking committed.

6. Resilience Patterns

Module 6 — Retry, circuit breaker, bulkhead, idempotency

Pattern Quick Reference

PatternWhat It DoesWhen to Use
Retry + JitterRetry failed calls with exponential backoff + random jitterTransient failures (network blips, 503s)
Circuit BreakerStop calling failing service; fail fast. States: Closed → Open → Half-OpenPrevent cascade failures, protect downstream
BulkheadIsolate resources (thread pools, connection pools) per dependencyPrevent one slow service from starving others
TimeoutSet max wait time for external callsAlways. Every external call needs a timeout.
BackpressureSlow down producers when consumers can't keep upStreaming, queue-based systems
Idempotency KeyClient sends unique key; server deduplicatesPayment APIs, booking creation, any non-idempotent operation
Graceful DegradationReturn cached/partial data when dependency is downNon-critical features, read-heavy paths

Why circuit breakers prevent cascading failures: Without a circuit breaker, when the payment service is down (responding in 30s instead of 200ms), every booking request waits 30s, holding a thread/connection. With 100 concurrent bookings, all 100 threads are blocked waiting for payment, and now the booking service can't handle any requests — including search and inventory queries that don't need payment. The circuit breaker detects the failure (5 consecutive timeouts), opens the circuit, and fails fast (returns an error in 1ms) so the booking service stays alive for non-payment operations. Why timeouts must always be set: A missing timeout is an implicit "wait forever" — any external dependency can hold your resources indefinitely. Default: 3-5s for internal services, 10-30s for external APIs.

Retry Storm Prevention

  • Use exponential backoff: 1s, 2s, 4s, 8s... with full jitter (randomize between 0 and the full backoff value — AWS recommended).
  • Set max retries (typically 3-5) and a max backoff cap (e.g. 30s).
  • Circuit breaker prevents retries when service is known to be down.
  • Coordinate retry budgets across fleet (e.g. max 10% of requests can be retries).

Thundering Herd Mitigation

  • Jitter on cache TTL: Randomize expiry so not all keys expire simultaneously.
  • Request coalescing: Single-flight / singleflight pattern — one goroutine fetches, others wait.
  • Stale-while-revalidate: Serve stale cache while refreshing in background.

Why jitter is critical (not just backoff): Without jitter, if 1000 agents all fail at the same time and retry with backoff (1s, 2s, 4s), all 1000 retry simultaneously at t=1s, then t=3s, then t=7s — synchronized waves that repeatedly overwhelm the recovering service. Full jitter randomizes each retry between 0 and the backoff value, spreading the load. This is the difference between a service that recovers in 10s and one stuck in a failure loop for minutes.

7. Testing Strategy

Modules 7-9 — Pyramid, unit, integration, contract, E2E, chaos

Testing Shapes

ShapeDistributionBest For
PyramidMany unit > some integration > few E2EBackend services, microservices
TrophyFew unit, many integration, some E2EFull-stack apps, APIs (Kent C. Dodds)
DiamondFew unit, many integration, few E2EData pipelines, middleware

Why the trophy shape for booking APIs: Unit tests that mock the DB, cache, and payment gateway test mostly your mocking code, not real behavior. (But unit tests for pure business logic — pricing rules, date range validation, discount calculations — are still very valuable and fast.) Integration tests with Testcontainers (real Postgres, real Redis) catch the real bugs: "does this query actually work?", "does the transaction rollback correctly?", "does the optimistic lock retry?" The trophy shape invests testing time where bugs actually hide — at service boundaries and integration points.

By Level

  • Unit Tests: Test pure logic in isolation. Mock external deps. Fast (<1ms each). Use property-based testing for edge cases.
  • Integration Tests: Real DB (Testcontainers), real HTTP calls. Test service boundaries. Pact for consumer-driven contracts.
  • Contract Tests: Provider verifies consumer contracts. Prevents breaking API changes across teams.
  • E2E Tests: Full user flows (Playwright/Cypress). Expensive, flaky. Keep minimal; focus on critical paths.
  • Chaos Testing: Inject failures in production/staging (Toxiproxy, Chaos Monkey). Verify resilience patterns actually work.

Test Doubles

  • Stub: Returns canned responses. Use for simple dependency replacement.
  • Mock: Verifies interactions (was method X called with args Y?). Use sparingly — couples test to implementation.
  • Fake: Working implementation (in-memory DB, fake S3). Best for integration tests.
  • Spy: Records calls for later assertion. Middle ground between stub and mock.

Why contract tests matter for agent APIs: When Agoda changes GET /v1/bookings response format (e.g., renames hotel_name to property_name), contract tests catch this before deployment because each agent has a consumer contract describing expected fields. Without contract tests, the change ships, agents parse null for hotel_name, and bookings break silently across all partners. Why chaos testing for booking systems: "Does our circuit breaker actually work when the payment service times out?" is a question only chaos testing can answer. Unit tests mock the timeout; chaos tests inject real latency via Toxiproxy and verify the system degrades gracefully.

8. Code Review

Modules 10-11 — Correctness, performance, security, staff practices

Review Dimensions

DimensionWhat to Look For
CorrectnessOff-by-one errors, null handling, boundary conditions, race conditions, logic errors
PerformanceN+1 queries, missing indexes, unbounded collections, unnecessary allocations, O(n^2) hidden in loops
SecuritySQL injection, XSS, SSRF, hardcoded secrets, missing auth checks, insecure deserialization
MaintainabilityNaming, single responsibility, coupling, test coverage, dead code
DesignRight pattern? SOLID violations? Appropriate abstraction level? Extensibility needed?

Common Anti-Patterns to Spot

  • N+1 Query: Fetching related records in a loop instead of JOIN or batch fetch. Fix: eager loading or WHERE id IN (...).
  • Race Condition: Check-then-act without locking. Fix: optimistic locking (version column), pessimistic lock, or atomic operations.
  • God Class: One class doing everything. Fix: extract responsibilities into focused classes.
  • Swallowed Exceptions: Empty catch blocks. Fix: log, rethrow, or handle meaningfully.
  • Hardcoded Config: URLs, timeouts, feature flags in code. Fix: externalize to config/env vars.

Why swallowed exceptions are the #1 code review flag: An empty catch(Exception e) {} in a booking flow means a payment failure is silently ignored — the customer gets a "booking confirmed" response while their payment actually failed. In production, this surfaces as revenue loss weeks later when reconciliation fails. Why N+1 is critical for agent APIs: An agent fetching 500 bookings with N+1 queries generates 501 DB queries instead of 2 (one batch fetch + one join). At 100 agents polling every minute, that's 50,100 queries/min vs 200 — the difference between a healthy DB and connection pool exhaustion.

Staff-Level Review Practices

  • Review for architectural alignment — does this PR move us toward or away from target architecture?
  • Suggest design patterns where appropriate (Strategy, Observer, Factory) — don't just say "fix this."
  • Evaluate error handling strategy — is it consistent with the service's error contract?
  • Check observability — are there logs/metrics/traces for the new code path?
  • Consider rollback safety — can this change be reverted without data migration?

Why staff-level reviews focus on "what happens when this fails": Junior reviewers check if code is correct when things go well. Staff reviewers check what happens when the payment gateway returns garbage, the DB connection pool is exhausted, or a race condition hits. Automated tools (linters, formatters) handle style — humans should focus on failure modes, architectural fit, and operational impact. Asking "can this be deployed and rolled back independently?" is a staff-level question that prevents incidents.

9. Observability & Production Readiness

Module 12 — Logs, metrics, traces, SLI/SLO, alerting

Three Pillars

PillarWhatToolsWhen to Use
LogsStructured events (JSON). Include trace_id, user_id, request_id.ELK, Loki, CloudWatchDebugging, audit trails
MetricsNumeric time-series. Counters, gauges, histograms.Prometheus, Datadog, CloudWatchAlerting, dashboards, SLO tracking
TracesDistributed request flow across services. Spans with timing.Jaeger, Zipkin, OpenTelemetryLatency debugging, dependency mapping

SLI / SLO / Error Budget

  • SLI (Service Level Indicator): What you measure — e.g. "% of requests completing in <200ms", "% of requests returning non-5xx".
  • SLO (Service Level Objective): Target for SLI — e.g. "99.9% of requests succeed" (allows ~8.7 hours downtime/year).
  • Error Budget: 100% - SLO = budget for risk. When budget exhausted, freeze deployments and focus on reliability.
  • SLA (Service Level Agreement): External contract with consequences. SLO should be stricter than SLA.

RED & USE Methods

  • RED (for request-driven services): Rate (req/s), Errors (error rate), Duration (latency histogram).
  • USE (for resources): Utilization (% busy), Saturation (queue depth), Errors (error count).

Why RED over custom metrics: Every request-driven service has the same three failure modes: too many errors, too slow, or too little throughput. RED (Rate, Errors, Duration) standardizes this so you can build one dashboard template for all services. Custom metrics like "bookings per minute" are business metrics layered on top. Why SLO burn rate alerting, not threshold alerting: A threshold alert ("error rate > 1%") fires too late or too early. A burn rate alert says "at the current error rate, you'll exhaust your monthly error budget in 6 hours" — it tells you urgency, not just state. You can ignore a 2% error rate that's been stable for months (within budget) but must act on a 0.5% spike that's burning budget 10x faster than normal.

Production Readiness Checklist

  • Structured logging with correlation IDs
  • Health check endpoints (/health, /ready)
  • Dashboards for RED metrics per service
  • Alerts on SLO burn rate (not just thresholds)
  • Runbooks linked to each alert
  • Graceful shutdown handling (drain connections, finish in-flight requests)
  • Feature flags for safe rollout
  • Rollback plan documented

Real Interview Experience: Agoda Platform Round

Compiled from multiple verified candidate experiences (2024-2026) including staff, senior, and lead engineer levels. The platform round is a 1-hour assessment that combines system design review, connectivity/API management, and code review into a single integrated round.

Round Format & Philosophy

  • Duration: 60 minutes, conducted by a Staff/Principal engineer.
  • Format: You are given a pre-built "non-robust" system (typically a booking or data-fetching service). Your job is to review, identify gaps, and improve — not build from scratch.
  • Why this format: At staff level, evaluating and improving existing architecture is as important as greenfield design. This simulates real senior engineering work.
  • Assessment style: Extensive "how / what / why / why not" grilling. Interviewers continuously challenge assumptions and highlight gaps intentionally to see how you reason under pressure.
Key insight: Start with smaller problems first — this is the core of the round. Don't jump to big architectural changes before addressing obvious issues.

Sub-round 1: System Design — Improve a Given Design (~20 min)

Scenario: You're given an existing booking system architecture. The service handles hotel booking transactions in MySQL. The company is expanding to allow external booking agents (e.g. MakeMyTrip, Booking.com) to use the same booking service via REST APIs. The current design is intentionally naive.

What you're expected to identify and improve:

  • Load Balancing: Single server → introduce LB (L4/L7), discuss health checks, sticky sessions vs stateless.
  • Rate Limiting: No rate limiting on new agent APIs → add token bucket / sliding window at API gateway level. Discuss per-client vs global limits.
  • Message Queue: Synchronous booking flow → introduce async processing (Kafka/RabbitMQ) for non-critical paths (notifications, analytics, agent callbacks). Discuss when sync vs async is appropriate.
  • Caching: Every request hits DB → add read-through cache (Redis) for hotel inventory, price lookups. Discuss cache invalidation strategies (TTL, write-through, event-driven).
  • Database: Single MySQL → read replicas for agent queries, connection pooling, discuss sharding if scale warrants it.
  • Transaction Management: Race conditions on double-booking → optimistic locking (version column), pessimistic locking (SELECT FOR UPDATE), or reservation pattern (hold → confirm → expire).
What worked: Candidates who structured their improvements from edge (LB, rate limiter) to core (DB, transactions) and explained trade-offs at each layer performed best. Always explain WHY, not just WHAT.

Sub-round 2: Connectivity & REST API Management (~20 min)

Focus: How do you manage robust, secure API connectivity for the agent integration? Interviewers test knowledge of plain vanilla HTTP fundamentals (no framework abstractions).

Topics covered:

  • REST API Improvements: Missing versioning → add URL-path versioning (/v1/bookings). Missing pagination → cursor-based for listing endpoints. Missing idempotency → add idempotency keys for booking creation.
  • Authentication Types Discussion:
    • API Key — simple but hard to rotate, no scoping. Good for internal services.
    • OAuth 2.0 Client Credentials — machine-to-machine, supports scopes, token expiry. Best for agent APIs.
    • JWT — stateless validation, include claims (agent_id, permissions). Discuss access + refresh token lifecycle.
    • mTLS — strongest service-to-service auth. Discuss certificate management overhead.
  • Secure Session Management:
    • Stateless JWT vs stateful sessions (Redis-backed). Tradeoffs: JWT = scalable but can't revoke easily; sessions = revocable but need shared store.
    • Token rotation: short-lived access tokens (15 min) + refresh tokens (7 days) with rotation on each use.
    • Secure cookie flags: HttpOnly, Secure, SameSite=Strict.
    • CSRF protection for session-based auth.
  • Connectivity Robustness: Discuss retry with exponential backoff for agent-to-Agoda calls, circuit breaker on Agoda side for external supplier calls, timeouts on all external dependencies.
What worked: Discussing authentication as a spectrum (API Key → OAuth → mTLS) and recommending the right level for the agent use case (OAuth 2.0 Client Credentials + JWT). Showing awareness of token lifecycle management impressed interviewers.

Sub-round 3: Code Review — Booking API (~20 min)

Format: You're shown a basic booking API implementation (typically Java/Kotlin or Python). The code works but has many issues. You review it as you would a real PR.

Common issues to spot and suggest:

  • Strategy Pattern: Large if/else chains for different booking types (hotel, flight, package) → suggest Strategy pattern to encapsulate booking logic per type. Makes adding new types (agent bookings) a new class, not a code change.
  • Error/Exception Handling:
    • Swallowed exceptions (empty catch blocks) → log and either rethrow or return meaningful error.
    • Generic catch(Exception e) → catch specific exceptions, handle each appropriately.
    • Missing validation at API boundary → validate input DTOs before business logic.
    • No distinction between client errors (4xx) and server errors (5xx) in response mapping.
  • Database Issues:
    • N+1 queries (loading bookings then fetching hotel for each in a loop).
    • Missing transaction boundaries (booking + payment not atomic).
    • No connection pooling configuration.
  • Concurrency: No handling of concurrent booking for same room → suggest optimistic locking with version field or database-level constraints.
  • Observability: No logging, no metrics, no trace context → add structured logging with booking_id, agent_id; emit latency/error metrics.
  • Security: Missing input sanitization, no rate limiting at endpoint level, no auth middleware check.
What worked: Structuring feedback by severity (critical → major → minor), suggesting specific design patterns with reasoning (not just "use Strategy pattern" but explaining HOW it applies to the booking type problem), and connecting code issues to production impact (e.g. "this swallowed exception means we'll silently lose bookings").

@PostMapping("/bookings")
public ResponseEntity<BookingDTO> createBooking(@RequestBody BookingRequest req) {
    if (req.getCheckIn().isAfter(req.getCheckOut())) {
        return ResponseEntity.status(500).body(null);       // Bug: wrong status (should be 400/422)
    }

    try {
        paymentClient.charge(req.getPaymentInfo(), booking.getTotal());
    } catch (Exception e) { /* TODO: handle later */ }      // Bug: swallowed payment exception

    try {
        emailService.sendConfirmation(booking);
    } catch (Exception e) {
        log.error("Email failed");                          // Bug: no exception object, no booking ID
    }

    bookingRepository.save(booking);
    return ResponseEntity.ok(booking.toDTO());
}

Key issues: (1) 500 for validation error → use 422, (2) swallowed payment exception → booking saved but unpaid, (3) log.error missing e and booking.getId(), (4) no transaction boundary across two saves, (5) sync email in request path → move to async queue, (6) no concurrency control → double-booking possible.

General Tips & What Worked

  • Start small, go big: Begin with obvious low-hanging fruit (missing error handling, no rate limiter) before proposing architectural changes (event-driven migration, CQRS).
  • Communicate tradeoffs: For every suggestion, explain the tradeoff. "Adding a message queue decouples the booking confirmation from notification delivery, but adds operational complexity and potential consistency delay."
  • Depth over breadth: Agoda interviewers value understanding WHY a design choice matters. Saying "use Redis for caching" is weak; explaining cache invalidation strategy, TTL tuning, and what happens on cache failure is strong.
  • Respond well to pushback: The interviewer will intentionally challenge your suggestions. This tests how you handle disagreement. Acknowledge the concern, adjust if valid, or defend with evidence.
  • Proactively discuss complexity: Don't wait to be asked — mention time/space complexity of algorithms and O-notation of database operations.
  • Connect to metrics: Tie improvements back to measurable outcomes: "Adding circuit breakers would reduce cascade failures, improving our p99 latency SLO attainment from ~95% to >99%."
  • Know the booking domain: Understand reservation patterns (hold/confirm/expire), double-booking prevention, eventual consistency in distributed booking systems, and payment idempotency.
Common mistakes: Jumping to over-engineered solutions (microservices, event sourcing) before fixing basic issues. Not explaining WHY behind suggestions. Getting defensive when the interviewer challenges a decision. Ignoring the code review portion to spend too long on system design.
