1. The Greedy Strategy

When Does Greedy Work? ▼

A greedy algorithm makes the locally optimal choice at each step, hoping it leads to a globally optimal solution. This works when the problem has two properties:

  • Greedy Choice Property: A locally optimal choice is part of some globally optimal solution. You never need to reconsider past choices.
  • Optimal Substructure: An optimal solution to the problem contains optimal solutions to its subproblems (shared with DP).

Why greedy fails on some problems: Consider the coin change problem with denominations [1, 3, 4] and target 6. Greedy picks 4+1+1=3 coins, but optimal is 3+3=2 coins. The greedy choice (pick the largest coin) is NOT part of the optimal solution.

The Exchange Argument (Proof Technique)

To prove a greedy algorithm is correct, use the exchange argument:

  1. Assume an optimal solution O* that differs from greedy solution G
  2. Find the first place where they differ
  3. Show you can "exchange" O*'s choice for G's choice without worsening the solution
  4. Repeat until O* = G, proving greedy is also optimal

Example: For activity selection (pick max non-overlapping intervals), greedy picks the earliest-ending activity. If O* picks a different first activity a*, we can swap a* with greedy's pick g (which ends no later) without creating conflicts, since g frees up at least as much room for future activities.

Exchange Argument Walkthrough: Activity Selection Proof ▼

Let's walk through a rigorous exchange argument for the activity selection problem. We want to prove: always picking the earliest-finishing compatible activity produces a maximum-size set.

Setup: Activities sorted by finish time: a₁ ≤ a₂ ≤ ... ≤ aₙ (by finish time f₁ ≤ f₂ ≤ ... ≤ fₙ). Let G = {g₁, g₂, ...} be greedy's solution and O* = {o₁, o₂, ...} be any optimal solution, both sorted by start time.

Step 1 — Existence of a swap. Suppose |O*| > |G| (contradiction hypothesis). Let k be the first index where G and O* differ: g₁=o₁, g₂=o₂, ..., gₑ₋₁=oₑ₋₁, but gₑ ≠ oₑ. Step 2 — Greedy finishes no later. By greedy's rule, gₑ is the earliest-finishing activity compatible with {g₁...gₑ₋₁}, so: f(gₑ) ≤ f(oₑ) Step 3 — The swap is valid. Construct O' = (O* \ {oₑ}) ∪ {gₑ}. - gₑ starts after f(gₑ₋₁) = f(oₑ₋₁) — compatible with prefix. - oₑ₊₁ starts after f(oₑ) ≥ f(gₑ) — so gₑ doesn't conflict with suffix. Therefore O' is a valid compatible set. Step 4 — O' is no smaller. |O'| = |O*| (we swapped one element for another). Step 5 — Induction. Repeat: O' agrees with G on the first k elements now. After at most |O*| swaps, O* has been transformed into a set that agrees with G on all shared positions and |O*| ≤ |G|, contradicting our hypothesis. Conclusion: |G| = |O*|, so greedy is optimal.

Interview tip: You don't need this level of rigor in an interview. Instead, say: "I'll use the exchange argument — assume an optimal solution differs from greedy at some step. Since greedy picks the earliest-finishing option, swapping OPT's choice for ours leaves at least as much room for future activities, so OPT can't be better." That's sufficient for a staff-level interview.

Real-World Greedy Examples ▼

Greedy algorithms are not just competitive-programming curiosities — they appear throughout production systems:

Huffman Coding (zip, gzip, JPEG, PNG)

Huffman builds an optimal prefix-free binary code by greedily merging the two lowest-frequency symbols. Each merge step is the greedy choice: combining the rarest symbols costs the fewest extra bits. The resulting tree is provably optimal — no other prefix-free code achieves a shorter average codeword length. gzip achieves 60–80% compression on text because frequent English letters get 3-bit codes while rare ones get 12-bit codes.

TCP Congestion Control — AIMD

TCP's Additive Increase / Multiplicative Decrease (AIMD) is a greedy rate control policy. Each round-trip: if no loss detected, increase window by 1 MSS (greedy optimism). On loss, halve the window (greedy pessimism). The greedy insight: probe aggressively until the network signals congestion, then back off sharply. AIMD provably converges to a fair, efficient operating point without global coordination — each sender acts greedily on local feedback.

CDN Cache Eviction — LRU as Greedy Heuristic

LRU (Least Recently Used) eviction is a greedy approximation to the optimal offline algorithm (Belady's OPT: evict the page used furthest in the future). LRU's greedy insight is that past recency predicts future use. For workloads with temporal locality (most web traffic), LRU achieves within 5–10% of OPT hit rate. CDNs like Cloudflare and Fastly use LRU or SLRU (Segmented LRU) for this reason.

Dijkstra's Algorithm — Greedy on Shortest Paths

Dijkstra's is textbook greedy: always process the unvisited vertex with the smallest known distance. The greedy choice property holds because edge weights are non-negative — once a vertex is processed, its distance is final (no shorter path can arrive later through an already-processed vertex). This fails with negative edges (use Bellman-Ford instead). Google Maps uses a bidirectional Dijkstra variant to route ~10 billion queries/day.

Huffman (gzip) Merge two rarest symbols Provably minimizes average code length

2. Interval Problems

Merge Intervals (LC #56) ▼

Problem: Given an array of intervals, merge all overlapping intervals.

Key Insight: Sort by start time. Then scan left to right: if the current interval overlaps with the last merged one, extend; otherwise start a new merged interval.

def merge(intervals: list[list[int]]) -> list[list[int]]:
    intervals.sort(key=lambda x: x[0])
    merged = [intervals[0]]
    for start, end in intervals[1:]:
        if start <= merged[-1][1]:   # overlaps
            merged[-1][1] = max(merged[-1][1], end)
        else:
            merged.append([start, end])
    return merged
# Time: O(n log n)  Space: O(n) for output

import java.util.*;

public int[][] merge(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> a[0] - b[0]);  // sort by start
    List<int[]> merged = new ArrayList<>();
    merged.add(intervals[0]);

    for (int i = 1; i < intervals.length; i++) {
        int[] cur  = intervals[i];
        int[] last = merged.get(merged.size() - 1);
        if (cur[0] <= last[1]) {          // overlaps
            last[1] = Math.max(last[1], cur[1]);  // extend in-place
        } else {
            merged.add(cur);              // new separate interval
        }
    }
    return merged.toArray(new int[0][]);
}
// Time: O(n log n)  Space: O(n)

Why sort by start? After sorting, we only need to check overlap with the previous interval. Without sorting, every pair might need checking (O(n2)).

Non-Overlapping Intervals (LC #435) ▼

Problem: Find the minimum number of intervals to remove so that the rest are non-overlapping.

Key Insight: This is equivalent to finding the maximum number of non-overlapping intervals (classic activity selection). Sort by end time and greedily keep intervals that don't overlap with the last kept one.

def eraseOverlapIntervals(intervals: list[list[int]]) -> int:
    intervals.sort(key=lambda x: x[1])  # sort by END time
    kept = 0
    prev_end = float('-inf')
    for start, end in intervals:
        if start >= prev_end:  # no overlap
            kept += 1
            prev_end = end
    return len(intervals) - kept
# Time: O(n log n)  Space: O(1)

import java.util.*;

public int eraseOverlapIntervals(int[][] intervals) {
    Arrays.sort(intervals, (a, b) -> a[1] - b[1]);  // sort by END time
    int kept = 0;
    int prevEnd = Integer.MIN_VALUE;

    for (int[] interval : intervals) {
        if (interval[0] >= prevEnd) {  // no overlap — keep this interval
            kept++;
            prevEnd = interval[1];
        }
        // else: overlap — skip (remove) this interval
    }
    return intervals.length - kept;
}
// Time: O(n log n)  Space: O(1)

Why sort by end time, not start? Sorting by end time ensures we always pick the interval that leaves the most room for future intervals. This is the greedy choice property: finishing earliest is always at least as good as finishing later.

Meeting Rooms II (LC #253) ▼

Problem: Find the minimum number of conference rooms needed to host all meetings.

Key Insight: The answer equals the maximum number of overlapping meetings at any point. Use a sweep line: separate starts and ends, sort them, and track concurrent meetings.

import heapq

def minMeetingRooms(intervals: list[list[int]]) -> int:
    if not intervals:
        return 0
    # Approach 1: Min-heap of end times
    intervals.sort(key=lambda x: x[0])
    heap = [intervals[0][1]]  # end time of first meeting
    for start, end in intervals[1:]:
        if start >= heap[0]:   # room freed up
            heapq.heapreplace(heap, end)
        else:
            heapq.heappush(heap, end)
    return len(heap)

def minMeetingRooms_sweep(intervals: list[list[int]]) -> int:
    # Approach 2: Sweep line (often cleaner)
    events = []
    for start, end in intervals:
        events.append((start, 1))   # meeting starts
        events.append((end, -1))    # meeting ends
    events.sort()
    rooms = max_rooms = 0
    for _, delta in events:
        rooms += delta
        max_rooms = max(max_rooms, rooms)
    return max_rooms
# Both: Time O(n log n), Space O(n)

import java.util.*;

// Approach 1: Min-heap of end times
public int minMeetingRooms(int[][] intervals) {
    if (intervals.length == 0) return 0;
    Arrays.sort(intervals, (a, b) -> a[0] - b[0]);  // sort by start
    PriorityQueue<Integer> heap = new PriorityQueue<>();  // min-heap of end times
    heap.offer(intervals[0][1]);

    for (int i = 1; i < intervals.length; i++) {
        if (intervals[i][0] >= heap.peek()) {  // room freed up
            heap.poll();
        }
        heap.offer(intervals[i][1]);  // assign/reuse room
    }
    return heap.size();
}

// Approach 2: Sweep line
public int minMeetingRoomsSweep(int[][] intervals) {
    int n = intervals.length;
    int[] starts = new int[n], ends = new int[n];
    for (int i = 0; i < n; i++) {
        starts[i] = intervals[i][0];
        ends[i]   = intervals[i][1];
    }
    Arrays.sort(starts);
    Arrays.sort(ends);

    int rooms = 0, maxRooms = 0, j = 0;
    for (int i = 0; i < n; i++) {
        if (starts[i] < ends[j]) {
            rooms++;        // need a new room
        } else {
            j++;            // room freed (end pointer advances)
        }
        maxRooms = Math.max(maxRooms, rooms);
    }
    return maxRooms;
}
// Both: Time O(n log n), Space O(n)

Real-world: Same as connection pooling, thread scheduling, and cloud VM allocation.

3. Classic Greedy Problems

Jump Game I & II (LC #55, #45) ▼

Jump Game I (#55): Can you reach the last index? Track the farthest reachable index.

def canJump(nums: list[int]) -> bool:
    farthest = 0
    for i in range(len(nums)):
        if i > farthest:
            return False
        farthest = max(farthest, i + nums[i])
    return True

public boolean canJump(int[] nums) {
    int farthest = 0;
    for (int i = 0; i < nums.length; i++) {
        if (i > farthest) return false;          // stuck — unreachable
        farthest = Math.max(farthest, i + nums[i]);
    }
    return true;
}
// Time: O(n)  Space: O(1)

Jump Game II (#45): Minimum jumps to reach end. Use a BFS-like greedy: track the current level's boundary and the farthest you can reach.

def jump(nums: list[int]) -> int:
    jumps = 0
    cur_end = 0       # end of current jump range
    farthest = 0      # farthest we can reach
    for i in range(len(nums) - 1):
        farthest = max(farthest, i + nums[i])
        if i == cur_end:       # must jump
            jumps += 1
            cur_end = farthest
    return jumps
# Time: O(n)  Space: O(1)

public int jump(int[] nums) {
    int jumps = 0, curEnd = 0, farthest = 0;
    for (int i = 0; i < nums.length - 1; i++) {
        farthest = Math.max(farthest, i + nums[i]);
        if (i == curEnd) {      // must jump — end of current level
            jumps++;
            curEnd = farthest;
        }
    }
    return jumps;
}
// Time: O(n)  Space: O(1)

Why greedy works here: Within each "jump level," we explore all reachable positions and pick the one that gets us farthest. This is optimal because jumping further never hurts.

Gas Station (LC #134) ▼

Problem: N gas stations in a circle with gas[i] fuel and cost[i] to reach the next station. Find the starting station to complete the circuit, or -1 if impossible.

Key Insight: If total gas ≥ total cost, a solution exists. To find it: if running out of fuel at station j when starting from i, then no station between i and j works either. Start fresh from j+1.

def canCompleteCircuit(gas: list[int], cost: list[int]) -> int:
    if sum(gas) < sum(cost):
        return -1
    tank = 0
    start = 0
    for i in range(len(gas)):
        tank += gas[i] - cost[i]
        if tank < 0:
            start = i + 1  # everything before i+1 fails
            tank = 0
    return start
# Time: O(n)  Space: O(1)

public int canCompleteCircuit(int[] gas, int[] cost) {
    int totalSurplus = 0, tank = 0, start = 0;
    for (int i = 0; i < gas.length; i++) {
        int net = gas[i] - cost[i];
        totalSurplus += net;
        tank += net;
        if (tank < 0) {          // failed starting from 'start'
            start = i + 1;       // skip ahead — all stations i..j fail
            tank = 0;
        }
    }
    return totalSurplus >= 0 ? start : -1;
}
// Time: O(n)  Space: O(1)

Why the skip is valid: If you run out at j starting from i, it means cumulative surplus was positive from i to some point but went negative by j. Any start between i+1..j would have less cumulative surplus (since station i had positive surplus), so they all fail too.

Task Scheduler (LC #621) ▼

Problem: Schedule tasks with cooldown n between same tasks. Minimize total time (including idles).

Key Insight: The most frequent task determines the structure. Place it first and fill gaps with other tasks.

from collections import Counter

def leastInterval(tasks: list[str], n: int) -> int:
    freq = Counter(tasks)
    max_freq = max(freq.values())
    # count how many tasks have the max frequency
    max_count = sum(1 for v in freq.values() if v == max_freq)
    # Formula: (max_freq - 1) frames of size (n+1), plus final group
    result = (max_freq - 1) * (n + 1) + max_count
    # If tasks fill all gaps, answer is just len(tasks)
    return max(result, len(tasks))
# Time: O(n)  Space: O(1) (26 letters max)

import java.util.*;

public int leastInterval(char[] tasks, int n) {
    int[] freq = new int[26];
    for (char t : tasks) freq[t - 'A']++;

    int maxFreq = 0;
    for (int f : freq) maxFreq = Math.max(maxFreq, f);

    // How many tasks share the max frequency?
    int maxCount = 0;
    for (int f : freq) if (f == maxFreq) maxCount++;

    // (maxFreq - 1) full frames + the last partial frame
    int result = (maxFreq - 1) * (n + 1) + maxCount;
    return Math.max(result, tasks.length);
}
// Time: O(n)  Space: O(1) — 26 fixed slots

Partition Labels (LC #763) ▼

Problem: Partition a string so each letter appears in at most one part. Maximize partition count.

def partitionLabels(s: str) -> list[int]:
    last = {c: i for i, c in enumerate(s)}  # last occurrence
    start = end = 0
    result = []
    for i, c in enumerate(s):
        end = max(end, last[c])
        if i == end:             # all chars in partition accounted for
            result.append(end - start + 1)
            start = i + 1
    return result
# Time: O(n)  Space: O(1) (26 letters)

import java.util.*;

public List<Integer> partitionLabels(String s) {
    int[] last = new int[26];
    for (int i = 0; i < s.length(); i++) {
        last[s.charAt(i) - 'a'] = i;  // record last occurrence of each char
    }

    List<Integer> result = new ArrayList<>();
    int start = 0, end = 0;
    for (int i = 0; i < s.length(); i++) {
        end = Math.max(end, last[s.charAt(i) - 'a']);
        if (i == end) {              // safe cut point reached
            result.add(end - start + 1);
            start = i + 1;
        }
    }
    return result;
}
// Time: O(n)  Space: O(1)

Why greedy: We must extend each partition to include the last occurrence of every character we've seen. Once we reach that boundary, we know it's safe to cut.

4. Greedy in Graph Algorithms (MST)

Kruskal's & Prim's MST Overview ▼

Minimum Spanning Tree algorithms are textbook greedy. Both produce optimal results because of the cut property: the lightest edge crossing any cut must be in some MST.

AlgorithmStrategyTimeBest For
Kruskal'sSort edges, add smallest that doesn't form cycle (Union-Find)O(E log E)Sparse
Prim'sGrow tree, always add cheapest edge to new vertex (min-heap)O(E log V)Dense
 
# Kruskal's MST (simplified)
class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))
        self.rank = [0] * n
    def find(self, x):
        if self.parent[x] != x:
            self.parent[x] = self.find(self.parent[x])
        return self.parent[x]
    def union(self, x, y):
        px, py = self.find(x), self.find(y)
        if px == py: return False
        if self.rank[px] < self.rank[py]: px, py = py, px
        self.parent[py] = px
        if self.rank[px] == self.rank[py]: self.rank[px] += 1
        return True

def kruskal(n, edges):  # edges = [(weight, u, v)]
    edges.sort()
    uf = UnionFind(n)
    mst_weight = 0
    for w, u, v in edges:
        if uf.union(u, v):
            mst_weight += w
    return mst_weight

// Kruskal's MST — Union-Find with path compression + union by rank
class UnionFind {
    private int[] parent, rank;

    public UnionFind(int n) {
        parent = new int[n];
        rank   = new int[n];
        for (int i = 0; i < n; i++) parent[i] = i;
    }

    public int find(int x) {
        if (parent[x] != x) parent[x] = find(parent[x]);  // path compression
        return parent[x];
    }

    public boolean union(int x, int y) {
        int px = find(x), py = find(y);
        if (px == py) return false;           // already in same component
        if (rank[px] < rank[py]) { int tmp = px; px = py; py = tmp; }
        parent[py] = px;
        if (rank[px] == rank[py]) rank[px]++;
        return true;
    }
}

public int kruskal(int n, int[][] edges) {
    // edges[i] = {weight, u, v}
    Arrays.sort(edges, (a, b) -> a[0] - b[0]);  // sort by weight
    UnionFind uf = new UnionFind(n);
    int mstWeight = 0;
    for (int[] e : edges) {
        if (uf.union(e[1], e[2])) {
            mstWeight += e[0];
        }
    }
    return mstWeight;
}
// Time: O(E log E)  Space: O(V)

7. Interview Follow-Up Questions

Common Follow-Ups at Staff Level ▼
Q: How would you prove this greedy algorithm is correct? Walk me through the exchange argument.
A: Assume an optimal solution O* differs from greedy G at position k. Since G made the locally optimal choice at step k (e.g., picked earliest-ending interval), G's choice finishes no later than O*'s. Swap O*[k] for G[k]: the solution remains valid (earlier finish can't create new conflicts) and is no worse. Repeat until O* = G, proving |G| = |O*|.
Q: What if intervals have weights/priorities? Does greedy still work for maximum weight non-overlapping intervals?
A: No — greedy breaks here. Consider intervals [(0,10,weight=5), (0,4,weight=3), (5,9,weight=3)]: greedy picks the earliest-ending = (0,4), then (5,9) for total weight 6. But (0,10) alone gives weight 5. Even that's wrong: the two shorter ones give 6. But with weight (0,10,weight=100): greedy misses it. You need Weighted Interval Scheduling DP: sort by end time, for each interval i, find the last compatible interval p(i), then dp[i] = max(dp[i-1], w[i] + dp[p(i)]). This runs O(n log n) with binary search for p(i).
Q: Can you solve Meeting Rooms II without a heap?
A: Yes — use the two-sorted-arrays sweep line. Separately sort start times and end times. Use two pointers: advance the start pointer one at a time. If the current start < earliest end, increment rooms needed. Otherwise, the earliest-ending meeting has finished, so advance the end pointer (room reused) without incrementing the counter. This runs in O(n log n) time and O(n) space, avoids heap overhead, and is often cleaner to write under pressure.
Q: What's the relationship between Activity Selection and Maximum Independent Set on interval graphs?
A: Activity Selection is exactly Maximum Independent Set (MIS) on an interval graph — where vertices are intervals and edges connect overlapping pairs. MIS on general graphs is NP-hard, but interval graphs have special structure (they're perfect graphs) that allows polynomial-time solutions. The greedy earliest-end algorithm exploits this structure. This is why greedy works on intervals but not on general scheduling/graph problems.
Q: How would you handle the Gas Station problem if there were multiple valid starting points? Return all of them.
A: The single-pass greedy finds the first valid start. To find ALL valid starts, observe: a station i is a valid start if and only if the prefix sum of (gas - cost) from station i wrapping around is non-negative at every point. You can find all valid starts in O(n) by computing the suffix minimum of cumulative sums and checking each candidate — or by running the greedy from each "candidate start" identified when tank drops negative. In practice, if a solution exists, it may be unique (provable under certain conditions), but if multiple exist, the suffix-minimum approach identifies them in O(n).

Q1
What two properties must a problem have for greedy to work?
Greedy Choice Property: local optimum leads to global optimum (never need to reconsider).
Optimal Substructure: optimal solution contains optimal sub-solutions.
Both are needed. Optimal substructure alone only justifies DP.
Q2
Why sort by END time (not start) for Activity Selection / Non-Overlapping Intervals?
Finishing earliest leaves maximum room for future activities. This is the greedy choice — it never blocks a better option. An activity ending at time t frees the schedule at t; an activity ending at t' > t can only block more futures. Formally proven via exchange argument.
Q3
What is the exchange argument proof technique?
Assume an optimal solution O* differs from greedy G. Show you can swap O*'s first differing choice for G's without worsening the solution. Repeat until O* = G. The key is showing the swap is: (1) feasible, (2) no worse in cost/value. After n swaps, O* has been transformed to G, proving G is also optimal.
Q4
Why does greedy fail for 0/1 Knapsack but work for Fractional Knapsack?
In fractional, you can take partial items — best value/weight ratio first is always optimal. In 0/1, you must take whole items: greedy by ratio may waste capacity (e.g., ratio-best item weighs 10, leaving 1 unit of capacity vs. two items of weight 5 each filling it). The local choice (best ratio) is NOT part of every optimal 0/1 solution.
Q5
In Jump Game II, why is the greedy BFS-like approach O(n)?
Each index is visited exactly once. We track level boundaries (cur_end, farthest) without re-examining earlier indices. When i reaches cur_end, we increment jumps and advance cur_end = farthest. No nested loops, no revisiting — the loop runs n-1 times total. DP is O(n²) because for each position, it scans all predecessors.
Q6
In Gas Station, why can you skip all stations between i and j when you fail at j?
If cumulative surplus goes negative at j starting from i: any start between i+1..j has even less surplus at j, because station i had positive surplus (it helped). Formally: surplus(k→j) = surplus(i→j) - surplus(i→k-1) < surplus(i→j) < 0 for any k in (i, j]. So all intermediate starts also fail at j.
